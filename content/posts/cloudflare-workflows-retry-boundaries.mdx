AI가 자료를 읽고 요약문까지 만들었습니다. 이제 게시 API를 호출하면 끝인데, 응답을 기다리다 타임아웃이 발생합니다. 다시 실행하면 될까요? 서버에는 이미 게시물이 만들어졌을 수도 있습니다.

이때 필요한 것은 더 좋은 프롬프트보다 **어디까지 끝났는지 확인하고, 같은 일을 두 번 처리하지 않는 실행 구조**입니다. Cloudflare Workflows는 이런 다단계 작업의 상태 저장과 재시도를 맡아주는 서비스입니다. 그런데 외부 서비스에서 일어난 일까지 모두 한 번만 실행되도록 보장해주는 것은 아닙니다.

이번 글은 **2026년 9월 12일에 확인한 공식 문서를 바탕으로 한 설계 분석**입니다. Cloudflare에 워크플로를 배포하거나 유료 AI API를 호출한 실사용 후기는 아닙니다. 아래 장애 상황은 동작 경계를 설명하기 위한 가정이며, 실제 장애를 재현한 측정 결과와는 구분합니다.

## Cron 다음에 직접 만들어야 했던 것들

[기존 Supabase Cron 글](/blog/supabase-cron-job)에서는 매일 정해진 시간에 사용량 테이블을 비우는 작업을 다뤘습니다. 이런 단일 SQL 작업에는 스케줄러만으로도 충분할 수 있습니다.

하지만 작업이 `자료 수집 → AI 요약 → 사람의 승인 → 게시`로 길어지면 관리할 것이 늘어납니다. 요약은 끝났는데 게시만 실패했을 때, 전체 작업을 다시 돌리면 이미 받은 요약을 또 생성하게 됩니다. 승인이 늦어지면 프로세스를 계속 켜놓거나, 대기 상태를 DB에 저장하고 나중에 이어서 실행하는 로직도 필요합니다.

Cron은 실행 시점을 정합니다. 그 뒤의 복구까지 하려면 애플리케이션이 완료 단계와 결과를 기록해야 합니다. 큐를 붙여도 메시지 재전달과 여러 단계의 진행 상태를 어떻게 연결할지는 별도 설계로 남습니다.

[Cloudflare Workflows](https://developers.cloudflare.com/workflows/)는 이를 Workers 위에서 관리형 기능으로 제공합니다. `step.do()`로 작업을 나누고 결과를 저장하며, 실패한 단계에는 재시도 정책을 적용할 수 있습니다. `step.sleep()`으로 기다리거나 `step.waitForEvent()`로 외부 이벤트를 기다리는 기능도 있습니다.

달라지는 부분은 함수를 호출하는 문법보다 **실행 상태를 보관하고 다시 이어가는 책임을 플랫폼에 맡길 수 있다는 점**입니다. 물론 기존에 DB와 큐로 복구를 잘 구현해둔 서비스라면, 같은 문제를 해결하기 위해 굳이 플랫폼을 옮길 이유는 적습니다.

## 단계 저장과 외부 API 실행 사이의 빈틈

Workflows의 [작성 규칙](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)은 API와 바인딩 호출을 멱등하게 만들 것을 권장합니다. 멱등성은 같은 작업을 반복해도 첫 실행 이후 결과가 추가로 바뀌지 않는 성질입니다. 같은 게시 요청을 재전송했을 때 새 게시물이 계속 생기지 않게 만드는 것이 한 예입니다.

문서가 이런 조건을 강조하는 데는 이유가 있습니다. 외부 서비스가 요청을 처리했더라도, Workflows 쪽에는 완료 결과가 남지 않을 수 있기 때문입니다.

예를 들어 게시 API가 요청을 처리한 직후 네트워크가 끊겼다고 가정해보겠습니다. 게시물은 생겼지만 응답을 받지 못한 단계는 실패로 처리될 수 있습니다. 다음 시도에서 똑같은 게시 API를 호출하면, 수신측에 중복 방지 장치가 없는 경우 게시물이 하나 더 생깁니다.

여기서 구분할 것은 두 가지입니다.

- Workflows가 완료 결과를 저장한 단계는 실행을 이어갈 때 그 결과를 재사용할 수 있습니다.
- **아직 완료로 저장되지 않은 단계가 외부에 남긴 변경까지 없던 일로 돌아가는 것은 아닙니다.**

공식 문서도 결제 처리 예제로 같은 문제를 설명합니다. 단계가 재시도될 수 있으므로, 이미 처리됐는지 확인한 뒤 작업하라는 것입니다. 다만 운영 설계에서는 조회 후 실행만으로 충분하다고 단정하면 곤란합니다. 동시 요청이 모두 '아직 처리되지 않음'을 읽을 수도 있으니까요.

수신 API가 멱등성 키를 지원한다면 같은 업무 작업에 같은 키를 보내는 방식부터 검토할 만합니다. 직접 관리하는 DB라면 고유 제약과 트랜잭션으로 중복 판정과 상태 변경을 함께 처리할 수 있는지 살펴봐야 합니다. **로컬 DB에 플래그를 저장하는 것만으로 별도 SaaS의 변경까지 같은 트랜잭션이 되지는 않습니다.**

대상 서비스가 중복 억제도 결과 조회도 지원하지 않는다면, 응답이 불명확한 쓰기 작업을 자동 재시도하지 않고 수동 확인 대상으로 보내는 편이 안전할 수 있습니다.

## AI 요약과 게시를 한 단계에 넣지 않기

다음은 실행 결과가 아니라, 같은 콘텐츠 처리 업무를 단계로 나누는 설계 예시입니다.

| 단계 | 완료 결과로 남길 것 | 다시 실행할 때의 확인점 |
| --- | --- | --- |
| 자료 수집 | 원문 버전, 저장 위치 | 원문이 바뀌어도 같은 입력으로 볼 것인가 |
| AI 요약 | 생성된 초안 또는 초안 저장 위치 | 응답 유실 시 재호출 비용과 내용 변경을 허용할 것인가 |
| 승인 대기·검증 | 승인한 초안 버전, 승인자와 판단 | 승인되지 않은 버전을 게시하지 않는가 |
| 외부 게시 | 외부 게시물 ID, 업무 작업 키 | 같은 요청을 재전송해도 중복 게시가 억제되는가 |

Cloudflare는 [서로 무관한 API 호출을 작은 단계로 나누라](https://developers.cloudflare.com/workflows/build/rules-of-workflows/#make-your-steps-granular)고 권장합니다. 요약과 게시를 한 단계에 묶으면 게시 실패 때문에 요약 호출까지 반복될 수 있습니다. 두 단계를 분리하고 요약 결과가 저장됐다면, 이후 게시 단계의 재시도에서 그 결과를 다시 활용할 수 있습니다.

다만 **단계 분리가 AI 호출 자체의 중복 과금까지 없애주지는 않습니다.** 모델 제공자가 추론을 마쳤는데 결과를 받기 전에 연결이 끊긴 경우, 요약 단계도 다시 호출될 수 있습니다. 제공자의 요청 조회·중복 처리 정책과 비용을 함께 확인해야 합니다. 이번 글에서는 특정 모델 API가 멱등성 키를 지원한다고 가정하지 않습니다.

업무 작업 키도 실행할 때마다 새로 만들면 곤란합니다. 같은 초안을 같은 채널에 게시하는 재시도라면 같은 업무로 식별해야 합니다. 반대로 수정한 새 버전을 게시하는 요청까지 무조건 같은 키로 묶으면 정상적인 변경을 막을 수 있습니다. 작업 키에 어떤 업무와 버전을 담을지, 수신측이 키를 얼마나 오래 보관하는지까지 맞춰야 합니다.

## 메모리의 변수는 복구 기록이 아니다

Workflows를 일반적인 장시간 실행 함수처럼 생각하면 또 다른 실수가 생깁니다. 단계 안에서 바깥 배열에 결과를 `push`해놓고, 나중에 그 배열을 읽는 방식입니다.

공식 문서는 Workflows가 대기 중에 hibernate하면서 메모리 상태를 잃을 수 있다고 설명합니다. 다시 실행을 이어갈 때 완료 단계의 콜백은 재실행되지 않고 저장된 결과를 사용하므로, 바깥 배열을 수정했던 효과가 다시 만들어진다고 기대해서는 안 됩니다.

상태는 **단계의 반환값으로 남기고, 이후 로직이 그 반환값을 사용하도록** 구성해야 합니다. 처음 받은 `event.payload`를 수정해 진행 상황을 기록하는 방식도 피해야 합니다. [이벤트 문서](https://developers.cloudflare.com/workflows/build/events-and-parameters/)에서는 그런 변경이 단계나 재시작을 거쳐 보존되지 않는다고 안내합니다.

자료를 많이 다루는 AI 작업이라면 반환값의 크기도 확인할 필요가 있습니다. 현재 [제한 문서](https://developers.cloudflare.com/workflows/reference/limits/)에서 비스트림 단계 반환값의 한도는 **1 MiB**입니다. 큰 문서나 결과물은 R2 같은 외부 저장소에 넣고 위치와 버전을 반환하는 설계를 검토할 수 있습니다.

이 한도를 모든 출력에 그대로 일반화하면 안 됩니다. JavaScript Workflows는 바이트 스트림 반환도 지원합니다. 스트림 역시 인스턴스 저장량에는 포함되므로, 큰 출력이 저장 비용과 보관 정책에서 자유로워지는 것은 아닙니다.

## 승인을 기다려주는 것과 승인을 검증하는 것

`step.waitForEvent()`를 쓰면 사람이 승인할 때까지 기다렸다가 후속 작업으로 넘어갈 수 있습니다. 그러나 **이벤트를 받았다는 사실만으로 그 사람이 승인 권한을 가졌다고 판단하면 안 됩니다.**

예를 들어 승인 요청을 받은 HTTP 핸들러에서 사용자 권한을 검증하고, 승인 대상의 초안 버전이 실제 게시하려는 버전과 일치하는지 확인하도록 설계해야 합니다. 초안 A를 보고 승인했는데 기다리는 사이 초안 B로 바뀌었다면, 같은 글 ID라는 이유만으로 게시하면 안 되겠죠.

[이벤트 문서](https://developers.cloudflare.com/workflows/build/events-and-parameters/#wait-for-events)에 따르면 승인 대기에도 타임아웃을 설정할 수 있고, 대기가 만료되면 오류가 발생합니다. 이 오류를 잡아 다른 작업을 이어갈 수는 있지만, 콘텐츠 게시처럼 승인이 필요한 작업에서는 '승인 없음'을 '자동 승인'으로 처리하지 않는 편이 낫습니다.

재시도 역시 오류 종류에 따라 달라져야 합니다. 일시적인 네트워크 오류와 잘못된 인증 정보는 같은 방식으로 다룰 문제가 아닙니다. [재시도 문서](https://developers.cloudflare.com/workflows/build/sleeping-and-retrying/)는 단계별 재시도와 타임아웃 설정을 제공하며, 재시도로 해결되지 않을 오류에는 `NonRetryableError`를 사용할 수 있다고 설명합니다.

그래도 '타임아웃이니 실패했고, 아무 일도 일어나지 않았다'고 결론 내리지는 말아야 합니다. 외부 쓰기 결과가 불명확한 상황은 앞에서 본 중복 실행 문제로 돌아갑니다. 재시도 횟수를 정하기 전에 결과를 조회할 방법부터 준비해야 하는 이유입니다.

## 이제 단계 개수도 비용에 들어간다

복구 단위를 잘게 나누면 실패한 작업만 다시 처리하기 편합니다. 그렇다고 변수 계산 하나까지 전부 단계로 만드는 것이 좋은 설계는 아닙니다. 저장할 상태와 관찰할 단계가 늘고, 과금에도 영향을 주기 때문입니다.

2026년 9월 12일 확인한 [공식 Pricing](https://developers.cloudflare.com/workflows/reference/pricing/)은 Workflows 과금 항목을 **요청, CPU 시간, 저장소, 단계**로 설명합니다. 7월 7일 변경 공지는 단계 과금을 추가하고 단계·저장소 과금을 8월 10일보다 이르지 않게 시작한다고 안내했으며, 현재 Pricing은 8월 10일부터 적용한다고 명시합니다. 개별 계정의 실제 청구 내역을 확인한 것은 아닙니다.

요금표에서 Workers Paid의 단계 사용량은 월 500,000단계 포함, 초과 100,000단계당 **$0.80**입니다. 저장소는 1 GB-month 포함, 초과 GB-month당 **$0.20**으로 안내합니다. 이는 Workflows 전체 이용료가 아니라 각각의 과금 항목이며, Workers 기본 요금과 요청·CPU 시간, 외부 AI API 비용까지 합친 금액은 아닙니다.

기다리는 동안 CPU 시간을 소비하지 않는다는 설명도 '모든 대기가 무료'라는 뜻은 아닙니다. [변경 공지](https://developers.cloudflare.com/changelog/post/2026-07-07-workflows-billing-updates/)는 sleep과 이벤트 대기 같은 단계 작업도 단계 과금에 포함한다고 설명합니다. 저장소 사용량에는 대기하거나 완료된 인스턴스의 상태도 들어갑니다. 반면 현재 Pricing은 재시도와 롤백 핸들러를 단계 과금 개수에서 제외한다고 명시합니다. 재시도로 외부 API 비용이나 CPU 사용이 전혀 늘지 않는다는 의미는 아닙니다.

따라서 단계 수를 줄이려고 요약과 게시를 합치기보다는, **독립적으로 복구해야 하는 외부 작업을 우선 분리하고 불필요한 중간 데이터 저장을 줄이는 쪽**이 낫다고 봅니다. 금전적 비용보다 중복 게시나 잘못된 승인을 복구하는 비용이 더 클 수도 있으니까요.

## 도입 전에 실패 경로부터 확인하기

Workflows는 외부 API가 여러 개 연결되고, 승인이나 긴 대기가 있으며, 중간 결과를 유지해야 하는 작업에서 검토할 가치가 있습니다. 기존 Workers 서비스를 쓰고 있다면 연결할 지점도 비교적 명확합니다.

반대로 하루 한 번 끝나는 짧은 작업이고, 실패하면 전체를 다시 실행해도 부작용이 없다면 Cron과 작은 스크립트로 충분할 수 있습니다. 이미 운영 중인 큐·DB 기반 작업 시스템이 복구와 관측을 잘 처리한다면, Workflows API와 상태 보관 방식으로 옮기는 비용도 고려해야 합니다. 특정 플랫폼의 단계·이벤트 모델에 로직이 결합된다는 점은 전환 비용으로 남습니다.

실제 도입 검증에서는 정상 실행보다 아래 상황을 먼저 확인해보면 좋겠습니다. **아직 수행하지 않은 테스트 목록**입니다.

- 요약 완료 결과를 저장한 뒤 게시 단계만 실패시켰을 때, 요약 API를 다시 호출하지 않는가.
- 게시 서버가 요청을 처리한 뒤 응답을 끊었을 때, 같은 업무 작업 키로 중복 게시를 막거나 결과를 조회할 수 있는가.
- 승인된 버전과 게시할 버전이 다르거나 승인 기한이 지났을 때, 게시를 멈추는가.
- 재시도 한도를 소진했을 때, 운영자가 업무 작업 키와 외부 결과 ID로 후속 처리를 판단할 수 있는가.
- 오래 대기한 뒤 다시 실행해도 필요한 상태가 남아 있고, 외부 서비스의 중복 방지 키 보관 기간도 유효한가.

개인적으로 이런 도구의 가치는 'Agent가 알아서 복구한다'는 설명보다, **어느 작업을 다시 실행하고 어느 작업은 확인 후 멈출지 코드로 정할 수 있다는 점**에 있다고 봅니다. Workflows가 실행 상태를 맡아줘도, 중복 실행을 허용할지와 승인 조건을 어떻게 지킬지는 서비스를 만드는 쪽에서 결정해야 합니다.
