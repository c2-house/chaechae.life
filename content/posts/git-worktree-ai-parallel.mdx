AI에게 기능 구현을 맡겨놓고, 다른 세션에서는 테스트를 고치고 싶을 때가 있습니다. 터미널을 두 개 열고 각자 다른 브랜치를 쓰라고 하면 괜찮을까요? **두 세션이 같은 폴더에서 실행된다면 브랜치 이름만으로 작업이 분리되지는 않습니다.** 한쪽에서 바꾼 파일을 다른 쪽이 읽거나, 브랜치를 전환하면서 상대의 작업 환경까지 바꿀 수 있습니다.

Git worktree는 하나의 저장소에 작업 디렉터리를 추가하는 기능입니다. 작업마다 파일과 스테이징 영역을 따로 둘 수 있어 AI 코딩 세션을 나눌 때 유용합니다. 다만 컨테이너처럼 실행 환경 전체를 격리하는 기능은 아닙니다. **편집할 공간은 나눠주지만, 작업 배분과 통합 검증까지 대신해주지는 않습니다.**

2026년 9월 16일, Windows 빌드 26200과 Git `2.54.0.windows.1`에서 별도 임시 저장소를 만들어 확인해봤습니다. 아래 결과는 자동화 스크립트로 실제 Git 명령을 실행한 관찰입니다. 여러 AI 모델을 동시에 실행해 코딩 품질이나 속도를 비교한 실험은 아닙니다.

## 브랜치와 작업 폴더의 차이

브랜치는 커밋 이력의 한 지점을 가리킵니다. 같은 폴더에서 브랜치를 바꾸면 그 폴더의 작업 트리와 인덱스도 전환 대상이 됩니다. 터미널마다 별도의 브랜치가 배정되는 구조가 아닙니다.

더 헷갈리는 부분은 커밋하지 않은 변경입니다. [Git switch 문서](https://git-scm.com/docs/git-switch)에 따르면 브랜치 전환에 항상 깨끗한 작업 트리가 필요한 것은 아닙니다. 로컬 변경이 손실되는 전환은 기본적으로 중단하지만, 그렇지 않으면 변경을 남긴 채 전환할 수 있습니다.

실제로 같은 초기 커밋에서 `ai/one` 브랜치를 만들고 `app.txt`에 `agent-a-draft`를 적었습니다. 커밋하지 않은 상태에서 `main`을 기준으로 `ai/two`를 만들며 전환했더니, 현재 브랜치는 `ai/two`인데 파일에는 여전히 `agent-a-draft`가 남아 있었습니다.

이 동작 자체가 Git의 오류는 아닙니다. 다만 여러 세션이 같은 폴더를 쓰면서 “내 브랜치니까 내 변경만 있다”고 생각하면 곤란해집니다. **동시에 작업할 때 필요한 것은 브랜치 이름뿐 아니라 별도의 작업 폴더**입니다.

## 작업마다 별도 디렉터리 만들기

[Git worktree 문서](https://git-scm.com/docs/git-worktree)는 하나의 저장소에서 여러 작업 트리를 관리하는 방법을 설명합니다. 추가한 worktree는 자체 `HEAD`와 인덱스를 가지면서 저장소의 커밋 데이터 등을 공유합니다. 인덱스는 다음 커밋에 넣을 변경을 고르는 스테이징 영역이라고 생각하면 됩니다.

실험에서는 초기 커밋과 `main` 브랜치가 있는 `demo` 저장소에서 다음 명령을 실행했습니다. `ai/auth`, `ai/tests` 브랜치와 대상 경로는 아직 없는 상태였습니다.

```bash
git worktree add -b ai/auth ../demo-auth main
git worktree add -b ai/tests ../demo-tests main
git worktree list
```

`-b` 뒤는 새 브랜치 이름, 그다음은 만들 디렉터리, 마지막 `main`은 출발점입니다. 원래 `demo` 폴더는 그대로 두고 형제 디렉터리 두 개가 생깁니다. 하나의 폴더에서 브랜치를 번갈아 바꾸는 대신, 각 세션을 해당 폴더에서 시작하는 방식입니다.

여기서 출발점을 생략하지 않는 편이 좋습니다. 일반적인 `git worktree add -b`에서 출발점을 생략하면 현재 `HEAD`를 기준으로 만듭니다. 작업 중인 기능 브랜치에서 시작하면 그 기능의 커밋도 따라옵니다. 위 명령의 `main`도 **로컬 main의 현재 커밋**이지 원격의 최신 상태를 자동으로 가져온다는 뜻은 아닙니다. 일반적인 [fetch](https://git-scm.com/docs/git-fetch)는 원격 추적 브랜치를 갱신하며 로컬 `main`까지 자동으로 갱신하지는 않습니다. 원격 기준으로 시작하려면 fetch 후 갱신된 `origin/main` 등 의도한 참조를 출발점으로 지정해야 합니다.

AI를 실행하기 전에는 `git worktree list`로 경로와 브랜치를 맞춰보세요. 세션의 시작 디렉터리가 여전히 원래 저장소라면 worktree를 만든 의미가 없습니다.

## 파일과 스테이징 분리 결과

두 worktree에서 같은 이름의 `app.txt`를 서로 다르게 수정하고, `ai/auth` 쪽에서만 `git add app.txt`를 실행했습니다. 이후 각 폴더의 파일과 스테이징 상태를 읽어 비교했습니다.

| 확인 항목 | 원래 `demo` | `demo-auth` | `demo-tests` |
| --- | --- | --- | --- |
| 현재 브랜치 | `main` | `ai/auth` | `ai/tests` |
| `app.txt` 내용 | `base` | `auth-draft` | `tests-draft` |
| 스테이징된 파일 | 없음 | `app.txt` | 없음 |

원래 폴더의 파일은 바뀌지 않았고, 한쪽에서 스테이징해도 다른 쪽의 인덱스에는 들어가지 않았습니다. 이 차이가 AI 코딩에서 중요합니다. 세션마다 수정 중인 파일과 커밋 후보를 따로 확인할 수 있기 때문입니다.

Git의 기본 보호 동작도 확인했습니다. 이미 `demo-auth`에서 사용 중인 `ai/auth` 브랜치를 다른 worktree에서 다시 체크아웃하려고 하자 명령이 종료 코드 `128`로 거절됐습니다. 같은 브랜치를 두 작업 공간이 동시에 움직이지 않도록 막는 동작입니다. 이때는 강제 옵션으로 뚫기보다 **작업마다 다른 브랜치를 쓰는 편이 낫습니다.**

그렇다고 결과물이 자동으로 합쳐지지는 않습니다. 같은 파일의 같은 부분을 각각 고쳤다면 나중에 통합할 때 충돌이 생길 수 있습니다. worktree가 줄이는 것은 작업 도중 같은 파일을 덮어쓰는 문제이지, 서로 다른 구현의 충돌까지 없애는 것은 아닙니다.

## 공유 데이터와 별도 실행 환경

### 커밋 이력과 저장소 설정

`demo-auth`에서 변경을 커밋한 뒤 그 커밋 해시를 `demo-tests`의 `git show`에 전달했습니다. 별도의 fetch 없이 `auth-draft` 내용을 읽을 수 있었습니다. 반면 `demo-tests`의 작업 파일은 여전히 `tests-draft`였습니다. **커밋이 저장소에 존재하는 것과 현재 작업 파일에 반영되는 것은 별개**입니다.

저장소 설정도 기본적으로 공유됩니다. 테스트용 `git config --local` 값을 한 worktree에서 기록하니 다른 worktree에서도 같은 값이 조회됐습니다. 공식 문서는 worktree별 설정을 위한 별도 확장도 설명하지만, 기본값이 완전 분리라고 가정하면 안 됩니다. 원격 저장소 주소 같은 공통 설정 변경은 다른 세션에도 영향을 줄 수 있습니다.

보안도 별도 문제입니다. 이번 실험에서는 같은 OS 사용자로 실행한 스크립트가 상대 worktree의 파일을 경로로 읽을 수 있었습니다. worktree를 만들었다고 파일시스템 접근 권한이 나뉜 것은 아닙니다. 신뢰하기 어려운 코드 실행이나 운영 자격증명 접근을 제한해야 한다면 Agent의 권한 설정과 별도 샌드박스를 함께 검토해야 합니다.

### 환경 파일과 실행 자원

원래 폴더에는 `.gitignore`로 제외한 테스트용 `.env`와 `node_modules` 디렉터리를 두었습니다. 새 worktree에는 둘 다 생기지 않았습니다. `node_modules`는 실제 패키지를 설치한 것이 아니라 복사 여부를 확인하기 위한 표식 파일만 넣은 디렉터리였습니다.

새 작업 공간에서 “원래 되던 실행이 왜 안 되지?” 싶다면 이 부분부터 확인할 필요가 있습니다. 의존성은 프로젝트의 잠금 파일과 설치 절차에 맞춰 준비하고, 환경 변수는 테스트에 필요한 값만 따로 제공하는 편이 좋겠습니다. 편하다고 운영 `.env`를 모든 작업 폴더에 복사하는 것은 추천하지 않습니다.

포트, 데이터베이스, 외부 API 계정도 worktree가 자동으로 나눠주는 대상이 아닙니다. 두 개발 서버는 서로 다른 포트를 쓰도록 정하고, 테스트가 데이터를 변경한다면 DB나 스키마도 분리해야 합니다. 폴더는 달라도 같은 DB를 가리키면 서로의 테스트에 영향을 줄 수 있습니다. API를 쓰는 AI 세션의 호출 비용 역시 폴더 분리만으로 줄어들지는 않습니다.

## AI 세션에 맡길 작업 범위

worktree를 만들고 나서 가장 먼저 정할 것은 “Agent를 몇 개 띄울까”보다 “어디까지 독립적으로 끝낼 수 있을까”입니다. 예를 들어 기존 API 계약을 바꾸지 않는 내부 리팩터링과 별도 문서의 오탈자 수정은 나눠 맡기기 쉽습니다. 반대로 한쪽이 응답 구조를 바꾸는데 다른 쪽은 이전 구조를 기준으로 테스트를 작성한다면, 폴더를 분리해도 다시 맞추는 시간이 필요합니다.

요청에는 작업 경로, 기준 브랜치나 커밋, 수정 범위, 완료 조건을 같이 적어두는 편이 좋습니다. 다음은 이번 실험에서 Agent에게 실행한 요청이 아니라 실제 작업에 적용할 때 쓸 수 있는 예시입니다.

```text
작업 디렉터리: demo-auth
브랜치: ai/auth
대상: 인증 모듈의 내부 리팩터링
유지 조건: 공개 API와 응답 형식 변경 금지
완료 조건: 변경 파일 목록, 실행한 테스트와 결과, 남은 위험 보고
다른 worktree 수정, 원격 push, 병합은 하지 않기
```

이 요청 문구 자체가 권한 통제 수단은 아닙니다. 하지만 각 세션이 무엇을 맡았는지 확인하고, 결과물을 검토하는 기준으로는 쓸 수 있습니다. 여러 Agent에게 같은 기능 전체를 각각 맡기는 경우라면 결과를 모두 합칠 작업인지, 서로 다른 구현을 비교한 뒤 하나를 고를 작업인지도 먼저 구분해야 합니다.

### Claude Code의 worktree 지원

이 방식은 특정 Agent만의 아이디어가 아닙니다. [Claude Code의 병렬 세션 문서](https://code.claude.com/docs/en/worktrees)는 `--worktree` 또는 `-w`로 별도 작업 공간에서 세션을 시작하는 기능을 안내합니다. Git으로 worktree를 직접 만든 뒤 그 디렉터리에서 Claude를 시작하는 방식도 설명합니다.

다만 Agent 제품이 붙여주는 동작과 Git 자체의 동작을 구분할 필요가 있습니다. 같은 문서는 main checkout을 향한 일부 파일 편집과 명령을 차단하는 검사도 설명합니다. 이는 **Claude Code가 추가한 검사**이지 Git worktree 자체가 제공하는 OS 수준의 격리가 아닙니다. 이번에는 Git의 분리 동작을 검증했으며 Claude 세션의 차단 기능은 실행하지 않았습니다.

또한 `.worktreeinclude`로 Git에서 제외한 파일을 복사하는 기능은 Claude Code의 편의 기능입니다. 일반 `git worktree add`가 이 파일을 읽고 환경을 복제해주는 것은 아닙니다. 도구가 worktree 생성과 정리를 자동화하더라도 무엇이 복사되고 어디에 권한이 남는지 공식 문서를 확인하는 편이 좋겠습니다.

## 검토와 작업 공간 정리

각 세션이 끝나면 변경 파일과 테스트 결과를 worktree별로 검토합니다. 코드가 커밋돼 있다는 이유만으로 끝났다고 판단하지 않고, 합쳐질 기준 브랜치와 비교해야 합니다. 특히 각각의 테스트가 통과해도 **변경을 통합한 상태에서 다시 테스트하는 단계**는 남아 있습니다.

작업 공간을 지우기 전에는 결과를 커밋하고, 필요한 원격 보관이나 PR 절차까지 마쳤는지 확인해야 합니다. 커밋하지 않은 변경과 새 파일은 물론, 일반적인 `git status`에 나타나지 않는 `.gitignore` 제외 파일도 따로 살펴보세요. 필요한 환경 파일이나 산출물이 남아 있을 수 있습니다. Git이 삭제를 허용한다고 보관할 것을 모두 챙겼다는 뜻은 아닙니다.

실험에서는 수정 중인 `demo-tests`를 `git worktree remove`로 지우려 했더니 종료 코드 `128`로 거절됐고 변경 파일도 그대로 남았습니다. 이후 두 worktree의 변경을 각각 커밋해 깨끗한 상태로 만든 뒤, 원래 `demo` 디렉터리에서 다음 명령으로 제거했습니다.

```bash
git worktree remove ../demo-auth
git worktree remove ../demo-tests
git worktree list
```

작업 디렉터리는 없어졌지만 `ai/auth`, `ai/tests` 브랜치는 남아 있었습니다. 즉, **Git의 worktree 제거와 브랜치 삭제는 별도 작업**입니다. 실험은 원격이 없는 임시 저장소에서 수행했으며 브랜치와 커밋은 결과 확인용으로 보존했습니다.

삭제가 거절됐을 때 `--force`부터 붙이지는 않는 편이 좋습니다. 다른 세션이 아직 쓰고 있는지, 남은 파일이 필요한지 먼저 확인해야 합니다.

또한 Git 공식 문서는 submodule 지원이 불완전하며, **submodule을 포함한 상위 저장소의 다중 checkout을 권장하지 않는다**고 명시합니다. 그런 프로젝트라면 이번의 단순한 저장소 실험만으로 도입을 결정하지 말고, 별도 clone 등 대안을 먼저 검토하는 편이 좋겠습니다.

## 병렬 작업을 시작할 기준

저라면 독립적인 코드 변경 두 개를 동시에 진행하거나, 한쪽의 미완성 변경을 그대로 둔 채 다른 작업을 해야 할 때 worktree를 선택하겠습니다. 브랜치 전환과 stash를 반복하지 않고 각 폴더에서 작업을 이어갈 수 있다는 점이 가장 실용적입니다.

반면 한 작업의 결과가 다음 작업의 입력이 되거나, 모든 수정이 같은 파일과 API 계약에 몰려 있다면 순서대로 진행하는 쪽이 단순할 수 있습니다. 읽기 전용 조사만 병렬로 나누는 상황에서도 별도 checkout이 꼭 필요한 것은 아닙니다. worktree마다 의존성·빌드 산출물·개발 서버를 준비하는 비용도 있기 때문입니다.

처음에는 많은 세션보다 두 개의 작은 작업으로 시작하는 것을 추천합니다. 각자 다른 디렉터리와 브랜치를 사용하는지, 환경과 테스트 데이터는 준비됐는지, 마지막 통합 검토는 누가 하는지부터 정해보세요. **worktree의 가치는 AI를 더 많이 실행하는 데 있지 않고, 동시에 진행하는 변경을 따로 검토할 수 있게 만드는 데 있습니다.**
