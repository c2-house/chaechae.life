`.env.local`을 `.gitignore`에 추가했는데도 VS Code의 변경 목록에 계속 나타나거나, GitHub에서 파일이 그대로 보일 때가 있습니다. 무시 규칙을 잘못 썼을 수도 있지만, **이미 Git이 추적하는 파일에는 `.gitignore`가 적용되지 않는다는 점**부터 확인해야 합니다.

이 경우에는 로컬 파일을 지울 필요가 없습니다. 무시 규칙을 확인하고 `git rm --cached`로 해당 파일만 추적 대상에서 빼면 됩니다. 다만 이 작업은 **다음 커밋에서 파일을 제외하는 것**이지, 과거 커밋이나 이미 노출된 API 키를 없애는 작업은 아닙니다.

아래에서는 저장소 루트의 `.env.local`을 예로 듭니다. 실제 문제가 `.env`나 `apps/web/.env.local`이라면 명령의 경로를 그 파일에 맞게 바꿔주세요. 2026년 9월 26일 공식 문서를 확인하고, Windows의 Git `2.54.0.windows.1`에서 실제 비밀값이 없는 별도 저장소로 추적 해제와 다른 복제본의 반영 결과를 확인했습니다.

**서버 비밀키나 비밀번호가 이미 원격 저장소에 올라갔다면, 아래 Git 정리만 끝내고 기다리지 마세요.** 서비스 제공자의 절차에 따라 노출된 자격 증명을 폐기하거나 교체하는 대응을 먼저 진행해야 합니다. 구체적인 구분은 뒤의 ‘이미 노출된 비밀값’에서 설명합니다.

## 삭제 전 추적 상태 확인

먼저 프로젝트의 최상위 폴더에서 다음 명령을 실행합니다. VS Code를 쓴다면 해당 프로젝트를 연 뒤 터미널에서 실행하면 됩니다. 아래 명령은 파일 내용을 출력하지 않습니다.

```bash
git status --short
git ls-files -- .env.local
```

`git ls-files`의 기본 출력은 인덱스에 있는 파일 목록입니다. 인덱스는 다음 커밋에 담을 파일 상태를 준비하는 공간으로, 스테이징 영역이라고도 부릅니다.

- `.env.local`이 출력되면 Git의 추적 대상에 들어 있습니다. 이미 커밋했거나 `git add`로 추가한 상태일 수 있습니다.
- 아무것도 출력되지 않으면 현재 인덱스에는 없습니다. 다만 경로를 잘못 입력한 경우도 같으니 실제 파일 위치를 먼저 확인합니다.
- `not a git repository` 오류가 나오면 프로젝트의 Git 저장소 안에서 실행하고 있는지 확인합니다.

이제 무시 규칙을 별도로 확인합니다.

```bash
git check-ignore -v --no-index -- .env.local
```

예를 들어 `.gitignore`의 두 번째 줄이 `.env.*`라면 다음처럼 나옵니다. 아래는 테스트 저장소에서 실제로 확인한 출력입니다.

```text
.gitignore:2:.env.*	.env.local
```

왼쪽부터 규칙 파일, 줄 번호, 적용된 패턴, 확인한 경로입니다. 여기서 `--no-index`는 **이미 추적 중인지와 관계없이 규칙만 확인하기 위한 옵션**입니다. 추적을 해제하거나 파일을 변경하지 않습니다.

이 구분이 꽤 중요합니다. [공식 `git check-ignore` 문서](https://git-scm.com/docs/git-check-ignore)에 따르면 기본 동작은 추적 중인 파일을 출력하지 않습니다. 실제로 추적 중인 `.env.local`에 `git check-ignore -v`만 실행했을 때는 출력이 없었지만, `--no-index`를 붙이면 위 규칙이 나왔습니다. 출력이 없다고 곧바로 `.gitignore`가 틀렸다고 판단하면 안 됩니다.

| 확인 결과 | 다음 행동 |
| --- | --- |
| 추적 중이고 무시 패턴도 일치함 | 규칙을 유지하고 해당 파일만 추적 해제 |
| 추적 중인데 일치하는 무시 패턴이 없음 | 규칙을 먼저 수정한 뒤 추적 해제 |
| 추적하지 않으며 무시 패턴이 일치함 | 현재 인덱스 상태는 정상. GitHub에 보인다면 브랜치·커밋 확인 |
| 추적하지 않으며 규칙도 일치하지 않음 | 경로·파일 이름·규칙의 적용 위치 확인 |

`-v` 출력의 패턴이 `!.env.example`처럼 `!`로 시작한다면 제외가 아니라 **다시 포함하는 예외 규칙**입니다. 단순히 출력이 있다는 이유만으로 무시되고 있다고 판단하지 마세요.

## 무시할 파일과 예외 규칙

환경 파일은 공유하지 않고, 값이 비어 있는 예제 파일만 공유하는 프로젝트라면 루트 `.gitignore`에 다음 규칙을 사용할 수 있습니다. 기존 내용을 지우고 교체하는 것이 아니라, 현재 규칙과 충돌하는지 확인하면서 추가합니다.

```gitignore
.env
.env.*
!.env.example
```

이 규칙에서는 `.env`, `.env.local`, `.env.production` 등을 제외하고 `.env.example`은 예외로 둡니다. `.env.example`에는 변수 이름과 설명용 값만 넣어야 합니다. **실제 키가 있는 파일의 이름만 `.env.example`로 바꿔 공유하면 안 됩니다.**

이 설정은 프로젝트의 환경 파일을 모두 비공개로 관리할 때의 예시입니다. 팀이 비밀값 없는 `.env.production` 기본 설정을 의도적으로 공유한다면, 그 파일까지 무시할지 먼저 합의해야 합니다.

[Git의 패턴 규칙](https://git-scm.com/docs/gitignore)에 따르면 `/`가 없는 패턴은 하위 폴더에도 적용될 수 있습니다. 위 `.env.*`는 `apps/web/.env.local`에도 적용됩니다. 반대로 `/.env.local`은 해당 `.gitignore`가 있는 위치의 `.env.local`로 범위를 좁힙니다.

규칙을 넣었는데도 예상과 다르면 다음을 확인합니다.

- 파일이 실제로 `.gitignore`인지, `.gitignore.txt`로 저장하지 않았는지 확인합니다.
- 규칙을 대상 파일과 같은 폴더나 상위 폴더의 `.gitignore`에 넣었는지 확인합니다. 관련 없는 다른 폴더의 규칙은 적용되지 않습니다.
- 같은 파일 안의 뒤쪽 패턴이나, 대상에 더 가까운 하위 `.gitignore`가 앞선 규칙을 바꾸고 있지 않은지 봅니다.
- `git check-ignore -v --no-index`가 가리키는 파일과 줄 번호를 확인합니다. 원인은 전역 설정이나 `.git/info/exclude`일 수도 있습니다.

앞의 세 줄만 둔 테스트에서는 `.env.local`과 `nested/.env.local`이 무시됐고, `.env.example`은 무시되지 않았습니다. 예외 규칙이 있어도 부모 폴더 전체가 제외된 경우에는 파일만 다시 포함할 수 없으므로, 복잡한 규칙은 경로별로 확인하는 편이 낫습니다.

## 로컬 파일을 남기는 추적 해제

여기부터는 인덱스를 바꿉니다. 필요한 환경 파일은 저장소 밖의 안전한 위치에 보관하고, 처음 확인한 `git status --short`에 작업 중이던 변경이 있다면 함께 커밋하지 않도록 구분합니다. 특히 이미 스테이징된 다른 변경은 나중의 `git commit`에 포함될 수 있습니다.

### 대상 파일 미리 확인

앞에서 `.env.local`이 추적 중이고 무시 규칙도 맞는 것을 확인했다면, 먼저 적용 대상을 미리 봅니다.

```bash
git rm --cached --dry-run -- .env.local
```

테스트에서는 `rm '.env.local'`이 출력됐습니다. `--dry-run`은 실제로 제거하지 않고 대상을 보여줍니다. 경로가 맞는 것을 확인한 뒤 실행합니다.

```bash
git rm --cached -- .env.local
```

[공식 `git rm` 문서](https://git-scm.com/docs/git-rm)의 `--cached`는 인덱스에서만 경로를 제거하고 작업 폴더의 파일은 남깁니다. 출력에 `rm`이 보이더라도 이 옵션을 사용했다면 로컬 파일 삭제 명령과는 다릅니다.

`pathspec ... did not match any files`가 나오면 경로가 틀렸거나 인덱스에 없는 파일일 수 있습니다. `git ls-files -- .env.local`부터 다시 확인하세요. 스테이징된 내용이 현재 파일과 마지막 커밋 양쪽 모두와 다르다는 오류가 나오면, 중간에 준비해둔 변경이 있는 상태입니다. **`-f`를 붙여 밀어붙이지 말고, 그 변경을 보존한 뒤 스테이징 상태부터 정리해야 합니다.** 별도 테스트에서도 이 상태의 추적 해제는 거절됐고 로컬 파일은 유지됐습니다.

### 파일 보존과 제외 상태 확인

명령을 실행한 뒤 편집기나 파일 탐색기에서 `.env.local`이 그대로 있는지 확인합니다. 키를 터미널에 출력할 필요는 없습니다. 이어서 다음 명령을 실행합니다.

```bash
git ls-files -- .env.local
git check-ignore -v -- .env.local
git status --short --ignored -- .env.local
```

정상적으로 처리됐다면 첫 번째 명령은 출력이 없고, 두 번째 명령은 무시 규칙을 보여줍니다. 이제 추적을 해제했으므로 `--no-index` 없이 확인합니다.

이미 커밋했던 파일로 진행한 테스트에서 세 번째 명령은 다음처럼 나왔습니다.

```text
D  .env.local
!! .env.local
```

두 줄이 같이 나와도 모순이 아닙니다. `D`는 **다음 커밋에 기록할 삭제 변경**이고, `!!`는 **작업 폴더에 남은 파일이 무시되고 있다는 표시**입니다. 이전 커밋에 없고 `git add`만 했던 파일이라면 결과는 다를 수 있습니다.

### 커밋할 변경 검토

무시 규칙도 다른 복제본에 전달해야 하므로 `.gitignore`를 스테이징합니다.

```bash
git add -- .gitignore
git diff --cached --name-status
```

새 `.gitignore`를 만든 테스트에서는 `.env.local`의 삭제와 `.gitignore`의 추가만 나왔습니다. 기존 `.gitignore`를 수정했다면 추가 대신 수정으로 표시됩니다. **관계없는 변경이 함께 보이면 여기서 멈추고 커밋 범위를 정리합니다.**

파일 이름과 상태만 확인하는 위 명령과 달리, 옵션 없는 `git diff --cached`는 삭제되는 파일의 비밀값까지 출력할 수 있습니다. 내용을 검토해야 한다면 본인의 안전한 로컬 환경에서 확인하고, 결과를 AI 채팅·공개 이슈·공유 로그에 그대로 붙이지 마세요.

기존 커밋이 있고, 검토한 변경만 스테이징된 상태라면 다음처럼 커밋할 수 있습니다.

```bash
git commit -m "chore: stop tracking local environment file"
```

원격 반영은 팀에서 사용하는 작업 브랜치와 PR 절차를 따릅니다. 이미 비밀값을 커밋해둔 저장소라면, 추적 해제 커밋을 하나 더 만들었다는 이유만으로 안전하게 push할 수 있는 상태라고 판단해서는 안 됩니다. 앞선 커밋도 함께 전송될 수 있습니다.

## 커밋 이력과 팀원 작업 폴더

커밋까지 마친 뒤에는 현재 커밋에 파일이 없는지 확인합니다.

```bash
git ls-tree -r --name-only HEAD -- .env.local
git status --short --ignored -- .env.local
```

첫 명령은 출력이 없어야 합니다. 테스트에서 두 번째 명령에는 `!! .env.local`만 남았습니다. 로컬 파일은 보존됐고, 현재 커밋에서는 빠졌으며, 이후 일반적인 추가 대상에서도 제외된 상태입니다.

그런데 같은 테스트의 바로 이전 커밋을 조회하니 `.env.local` 경로가 여전히 있었습니다. **현재 커밋에서 삭제해도 이전 커밋의 내용은 사라지지 않습니다.** GitHub에서 파일이 보인다면 지금 보고 있는 브랜치에 삭제 커밋이 반영됐는지, 과거 커밋을 보고 있지는 않은지 구분해야 합니다.

팀원에게 미치는 영향도 다릅니다. `--cached`가 남겨주는 것은 **명령을 실행한 작업 폴더의 파일**입니다. 삭제 전 커밋을 복제해둔 별도 폴더에서, 로컬 수정 없이 삭제 커밋을 `pull`했더니 그 폴더의 `.env.local`은 실제로 없어졌습니다. 새로 clone하는 사람에게도 해당 파일은 제공되지 않습니다.

그래서 팀 저장소에서는 삭제 커밋을 공유하기 전에 필요한 로컬 설정을 안전하게 보관하도록 알리고, 비밀값 없는 `.env.example`과 설정 방법을 함께 준비하는 것이 좋습니다. 팀원의 미커밋 변경이 있으면 반영이 거절되는 등 상황이 달라질 수 있으므로, 같은 결과를 강제로 만들려고 파일을 덮어쓰지 않습니다.

## 이미 노출된 비밀값과 재발 방지

`.gitignore`는 앞으로의 추적을 조절하는 규칙이지 접근 통제 장치가 아닙니다. 이미 GitHub에 올라간 서버 API 키·비밀번호·토큰이라면 [GitHub의 민감정보 제거 안내](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)에 따라 **노출된 자격 증명의 폐기 또는 교체가 첫 대응**입니다. 파일 삭제나 비공개 저장소 전환만으로 이미 복사된 키를 무효화할 수는 없습니다.

반대로 공개 사용을 전제로 설계된 키나 비밀값 없는 기본 설정까지 모두 같은 사고로 취급할 필요는 없습니다. 해당 서비스의 키 종류와 권한을 확인해야 합니다. 예를 들어 Supabase 키의 구분은 [publishable key 전환 글](/blog/supabase-publishable-key-migration)에서 따로 설명했습니다.

이력 정리가 필요한지는 별도로 판단합니다. GitHub는 키 폐기·교체만으로 위험을 해소할 수 있다면 이력을 다시 쓰는 작업까지 필요하지 않을 수 있다고 설명합니다. 비밀번호가 아닌 개인정보처럼 교체로 해결되지 않는 데이터가 남아 있거나 별도 삭제 의무가 있다면, 저장소 담당자와 공식 제거 절차를 검토해야 합니다.

이력 재작성은 커밋 해시와 PR에 영향을 주고, 다른 복제본에서 과거 이력이 다시 들어올 위험도 있습니다. 원격 이력을 바꿔도 다른 사람의 clone·fork까지 자동으로 지워지지 않습니다. 이 글의 추적 해제 절차에 이력 재작성이나 강제 push를 한 줄 더 붙이는 방식으로 처리하지 않는 이유입니다.

마지막으로 재발 방지는 무시 규칙과 커밋 검토를 함께 가져가는 편이 좋습니다. 파일 하나를 제외하려고 저장소 전체를 인덱스에서 제거한 뒤 다시 추가할 필요는 없습니다. 경로를 지정해 변경하고, 커밋할 파일을 확인하고, 실제 키 대신 예제 파일을 공유하면 됩니다.

**완료 기준은 변경 목록에서 안 보이는 것 하나가 아닙니다.** 필요한 로컬 파일이 남아 있고, 인덱스와 새 커밋에는 없으며, 무시 규칙이 적용되는지까지 확인해야 합니다. 이미 비밀값이 노출됐다면 그 대응은 이 Git 작업과 별도로 끝내야 합니다.
