`compose.yaml`에 `env_file`을 지정했고, 그 파일에도 값이 들어 있는데 다음 경고가 나올 때가 있습니다.

```text
The "DEMO_COLOR" variable is not set. Defaulting to a blank string.
```

파일을 못 읽는 문제처럼 보이지만, **Compose 파일의 `${변수}`를 채우는 일과 컨테이너에 환경변수를 전달하는 일은 서로 다릅니다.** 서비스의 `env_file`은 두 번째 역할입니다. 여기에 `environment`로 같은 변수를 다시 선언하면, 치환에 실패한 빈 값이 파일의 정상 값을 덮어쓸 수도 있습니다.

이 글에서는 그 상황을 작은 예제로 확인하고, 값을 어디에 쓸 것인지에 따라 수정 방법을 나눠보겠습니다. 2026년 10월 4일 공식 문서를 확인했으며, Windows 11의 Docker Compose `v5.1.4`에서 별도 폴더로 설정 해석을 테스트했습니다. 컨테이너를 실행하거나 이미지를 내려받지 않고 `docker compose config`로 확인한 결과입니다.

## env_file과 --env-file의 역할

먼저 파일 이름보다 **그 파일을 어디에서 지정했는지**를 봐야 합니다. `app.env`라는 같은 파일도 두 곳에서 각각 사용할 수 있습니다.

| 지정 위치 | 역할 | 주의할 점 |
| --- | --- | --- |
| CLI의 `--env-file app.env` | Compose 파일 안의 `${변수}`를 채울 값 제공 | 파일의 모든 변수를 컨테이너에 자동 전달하지는 않음 |
| 서비스 아래 `env_file: ./app.env` | 해당 컨테이너에 전달할 환경변수 제공 | Compose 파일의 치환 입력을 대신하지는 않음 |
| 서비스 아래 `environment` | 컨테이너에 전달할 값을 직접 지정 | 같은 변수를 선언하면 `env_file` 값보다 우선 |

[Docker의 변수 치환 안내](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)에서 말하는 **interpolation**은 `${DEMO_COLOR}` 같은 자리를 실제 값으로 바꾸는 과정입니다. Compose를 실행한 셸의 환경변수나 `--env-file`로 지정한 파일 등이 이 과정의 입력이 됩니다.

일반적인 프로젝트 루트에 `compose.yaml`과 `.env`를 함께 두고 실행하면 `.env`도 치환 값의 기본 입력으로 사용할 수 있습니다. 다만 `.env`에 값을 적는 것만으로 그 값이 컨테이너의 환경변수가 되는 것은 아닙니다. 컨테이너에 전달할 `environment`나 `env_file` 등의 설정이 별도로 필요합니다.

## 빈 값으로 덮어쓰는 최소 예제

기존 서비스가 아닌 빈 폴더에 다음 두 파일을 만듭니다. 이 예제에는 비밀번호 대신 `DEMO_COLOR`라는 테스트용 변수를 사용합니다. 같은 폴더에 별도 `.env` 파일을 두지 않고, 실행하는 셸에도 `DEMO_COLOR`가 설정되지 않은 상태를 기준으로 합니다.

`app.env`의 내용입니다.

```dotenv
DEMO_COLOR=blue
```

같은 폴더의 `compose.yaml`에는 다음 내용을 넣습니다.

```yaml
services:
  app:
    image: alpine:3.22
    env_file:
      - ./app.env
    environment:
      DEMO_COLOR: ${DEMO_COLOR}
```

`alpine:3.22`는 설정에 쓴 이미지 참조일 뿐, 여기서는 실행하지 않습니다. **실제 프로젝트에서는 `config` 출력에 비밀값이 포함될 수 있습니다.** 아래처럼 가짜 값으로 재현하거나, 출력을 혼자 확인하고 공개 이슈·AI 대화·CI 로그에는 원문을 남기지 않는 편이 안전합니다.

두 파일이 있는 폴더에서 다음 명령을 실행합니다.

```bash
docker compose config
```

테스트에서는 변수 누락 경고가 나왔고, 출력의 해당 부분은 다음과 같았습니다. 네트워크 등 나머지 출력은 생략했습니다.

```yaml
services:
  app:
    environment:
      DEMO_COLOR: ""
    image: alpine:3.22
```

이 결과는 두 규칙이 겹쳐서 생깁니다.

1. `${DEMO_COLOR}`를 치환할 입력이 없어서 경고와 함께 빈 문자열로 바뀝니다.
2. `environment`의 값은 `env_file`보다 우선합니다. 따라서 `app.env`의 `blue` 대신 빈 문자열이 최종 설정에 남습니다.

[공식 서비스 명세](https://docs.docker.com/reference/compose-file/services/#env_file)에는 `environment`가 **비어 있거나 정의되지 않은 값이어도** `env_file`의 값을 덮어쓴다고 명시돼 있습니다. 파일에 값을 다시 저장하거나 이미지 빌드 캐시를 지우는 것으로 해결할 문제가 아닌 셈입니다.

이 상태에서도 `config`의 종료 코드는 `0`이었습니다. 명령 성공만 보고 값까지 정상이라고 판단하면 놓칠 수 있습니다.

## 목적에 따른 두 가지 수정 방법

### 컨테이너에만 전달할 값

애플리케이션이 컨테이너 안에서 `DEMO_COLOR`를 읽기만 하면 된다면, 중복된 `environment` 항목을 없애는 쪽이 간단합니다.

```yaml
services:
  app:
    image: alpine:3.22
    env_file:
      - ./app.env
```

`app.env`는 그대로 두고 다시 `docker compose config`를 실행합니다. 이 구성에서는 변수 누락 경고 없이 다음 값이 나왔습니다.

```yaml
environment:
  DEMO_COLOR: blue
```

여러 변수 중 하나만 중복됐다면 `environment` 블록 전체가 아니라 해당 항목만 정리합니다. 다른 항목까지 지우면 의도한 설정을 잃을 수 있습니다.

### Compose 파일에서도 참조할 값

반대로 이미지 태그, 포트 매핑, `environment` 안의 조합된 문자열처럼 **Compose 파일 자체에서 `${변수}`를 사용해야 한다면**, 치환 단계에도 값을 공급해야 합니다.

처음의 `environment`가 있는 예제를 유지하고 다음처럼 실행합니다.

```bash
docker compose --env-file app.env config
```

테스트에서는 경고가 사라지고 `DEMO_COLOR: blue`가 나왔습니다. `--env-file`은 `config` 앞에 둔 Compose 공통 옵션입니다. 서비스의 `env_file`과 철자가 비슷하지만 같은 설정을 다른 표기로 쓴 것은 아닙니다.

이때 같은 `app.env`를 두 번 지정한 이유는 역할이 두 개이기 때문입니다. CLI에서는 치환 입력으로, 서비스에서는 컨테이너 환경변수의 입력으로 사용합니다. 이 예제처럼 `environment`가 필요한 값을 모두 전달한다면 서비스의 `env_file`은 생략할 수도 있습니다. 실제 프로젝트에서는 어떤 경로로 어떤 값을 전달할지 정하고 중복을 줄이는 편이 관리하기 좋습니다.

**`config`에서만 `--env-file`을 붙이고 실제 실행에서 빼면 같은 조건이 아닙니다.** 실행·검증에 사용하는 Compose 파일, 환경 파일, 프로젝트 지정 옵션을 맞춰야 합니다.

## 파일 내용과 결과가 다를 때의 확인 순서

### 셸의 같은 이름 변수

`app.env`에는 `blue`인데 결과가 `red`라면 셸에 이미 같은 변수가 있는지 확인합니다. 공식 문서에 따르면 **셸의 환경변수가 `--env-file`의 값보다 치환 우선순위가 높습니다.**

별도 테스트 프로세스에만 `DEMO_COLOR=red`를 넣고 `--env-file app.env`를 함께 전달했더니 최종 값은 `red`였습니다. 파일을 읽지 않은 것이 아니라 더 높은 우선순위의 값이 적용된 결과입니다. 이 설명은 `${DEMO_COLOR}`의 치환에 대한 것이며, 셸의 모든 변수가 서비스의 `env_file` 값을 자동으로 덮어쓴다는 뜻은 아닙니다.

치환에 사용되는 값은 다음 명령으로 확인할 수 있습니다. 셸에서 전달된 다른 값도 함께 나올 수 있으므로, 필요한 변수만 로컬에서 확인하고 전체 출력을 공유하지 마세요.

```bash
docker compose --env-file app.env config --environment
```

이 출력은 **실행 중인 컨테이너의 환경변수 목록이 아니라 Compose의 치환 입력**입니다.

의도하지 않은 셸 값이 있다면 어디에서 설정됐는지 확인한 뒤 해당 터미널 세션이나 CI 설정에서 필요한 항목만 수정합니다. 컴퓨터의 환경변수를 통째로 지우거나 운영용 설정을 테스트 값으로 덮어쓸 필요는 없습니다.

### 파일 경로와 덮어쓰기 항목

이 글처럼 Compose 파일 하나를 사용하는 구성에서는 경로 기준도 구분해야 합니다.

- CLI의 `--env-file` 상대 경로는 명령을 실행한 현재 디렉터리를 기준으로 합니다.
- 서비스의 `env_file` 상대 경로는 Compose 파일이 있는 디렉터리를 기준으로 합니다.
- 서비스에 `env_file`을 여러 개 적었다면 같은 변수는 뒤에 적은 파일의 값이 우선합니다.
- 같은 서비스의 `environment`에도 해당 변수가 있는지 확인합니다.

따라서 다른 폴더에서 `-f`로 Compose 파일만 지정할 때는 `--env-file app.env`가 어느 파일을 가리키는지도 다시 확인해야 합니다. 여러 `-f` 파일을 합치는 프로젝트라면 실행 명령 전체와 병합 결과를 함께 봅니다. 파일 하나만 읽고 최종 값을 추측하기는 어렵습니다.

비슷한 이름의 파일을 계속 추가하기보다 치환 입력은 `config --environment`, 최종 서비스 설정은 `config`로 나누어 확인하는 편이 원인을 좁히기 좋습니다.

## 필수 값의 누락 방지

없으면 실행을 멈춰야 하는 값이라면 `${DEMO_COLOR}` 대신 다음처럼 필수 값 문법을 사용할 수 있습니다.

```yaml
environment:
  DEMO_COLOR: ${DEMO_COLOR:?Set DEMO_COLOR}
```

이 코드는 기존 서비스의 `environment` 부분을 바꾸는 예제입니다. [공식 치환 문법](https://docs.docker.com/reference/compose-file/interpolation/)에서 `:?`는 변수가 없거나 빈 문자열이면 오류로 처리하도록 합니다.

처음의 재현 구성에서 해당 한 줄을 바꾸고, 치환 값을 공급하지 않은 상태로 다음 명령을 실행했습니다.

```bash
docker compose config --quiet
```

종료 코드가 `1`로 바뀌었고 다음 오류가 나왔습니다.

```text
error while interpolating services.app.environment.DEMO_COLOR: required variable DEMO_COLOR is missing a value: Set DEMO_COLOR
```

`--env-file app.env`를 다시 지정하면 검증은 종료 코드 `0`으로 통과했습니다. 셸에서 빈 문자열을 전달한 경우에도 `:?`는 오류로 처리했습니다.

이 검사는 **값의 존재 여부**를 확인합니다. 잘못된 API 주소나 권한 없는 키까지 올바르게 바꿔주는 검사는 아닙니다. 또한 서비스의 `env_file`만으로 값을 전달하는 모든 변수에 자동 적용되는 것도 아닙니다. Compose 파일에서 필수로 치환하는 항목에 사용하는 장치입니다.

## 설정 검증과 실제 적용의 구분

이번 설정 테스트에서 확인한 차이는 다음과 같습니다. 모두 `config`가 해석한 결과이며, 실행 중인 앱의 응답을 측정한 표는 아닙니다.

| 구성 | 확인한 결과 |
| --- | --- |
| 서비스 `env_file`과 값 없는 `${DEMO_COLOR}`를 함께 사용 | 경고 발생, 최종 값은 빈 문자열 |
| 서비스 `env_file`만 사용 | 최종 값은 `blue` |
| `${DEMO_COLOR}`를 유지하고 CLI `--env-file` 추가 | 최종 값은 `blue` |
| CLI 파일과 셸의 `red`를 함께 제공 | 최종 값은 `red` |
| `.env`만 두고 서비스의 환경변수 전달 설정은 생략 | 서비스 설정에 `DEMO_COLOR` 없음 |
| `:?`를 사용하고 치환 값은 누락 | 설정 검증 실패 |

설정이 원하는 값으로 해석된 뒤에는 실제 서비스에 적용할 차례입니다. [Docker의 `restart` 문서](https://docs.docker.com/reference/cli/docker/compose/restart/)는 환경변수 등 Compose 설정 변경이 단순 재시작으로 반영되지 않는다고 설명합니다. [공식 `up` 문서](https://docs.docker.com/reference/cli/docker/compose/up/)에 따르면 설정이 바뀐 서비스는 컨테이너를 다시 만들어 변경을 반영합니다.

실제 적용은 해당 프로젝트에서 사용하는 `docker compose up` 명령에 검증 때와 같은 `--env-file`·`-f`·프로젝트 지정 옵션을 유지하는 방식으로 진행합니다. 위 Alpine 예제는 설정 확인용이므로, 그것을 그대로 앱 운영 명령으로 사용하지는 마세요.

운영 서비스라면 재생성으로 중단이 생길 수 있으므로 정상 설정을 보관하고, 프로젝트의 배포·복구 절차 안에서 적용해야 합니다. 변수 문제를 해결하려고 볼륨 삭제나 전체 정리 명령부터 실행하지 마세요.

완료 여부는 다음 두 단계로 나눠 확인하면 됩니다.

1. **설정 단계:** 실제 실행과 같은 옵션으로 `config`를 확인했을 때 변수 경고가 없고, 해당 서비스의 값이 의도와 일치합니다.
2. **실행 단계:** 변경된 설정으로 서비스가 재생성됐는지 확인하고, 그 변수를 사용하는 기능이 정상 동작하는지 테스트합니다. 비밀키를 화면이나 로그에 출력하는 대신 안전한 기능 호출 결과로 확인합니다.

설정은 정상인데 앱만 이전 값을 읽는다면 다른 Compose 프로젝트의 컨테이너를 보고 있는지, 앱이 자체 설정 파일이나 기본값을 따로 읽는지 확인할 차례입니다. `config`가 정상이라는 이유로 앱의 실행 결과까지 확인됐다고 볼 수는 없습니다.

파일을 어디에 두느냐보다 먼저 볼 것은 **그 값을 Compose가 사용할지, 컨테이너 안의 앱이 사용할지**입니다. 이 둘을 나누면 `env_file`을 추가했는데도 변수가 없다는 경고가 나는 이유와, 수정할 위치가 훨씬 분명해집니다.
