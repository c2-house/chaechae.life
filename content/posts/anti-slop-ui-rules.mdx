AI에게 웹페이지를 만들어 달라고 했는데, 서비스 이름만 바꾸면 다른 사이트에도 그대로 쓸 수 있을 것 같은 화면이 나올 때가 있습니다. 보라색 그라데이션과 카드가 문제라기보다 **왜 그 구성이 필요한지 설명이 없고, 실제로 없는 후기나 작동하지 않는 버튼까지 들어가는 것**이 더 큰 문제입니다.

[miqdadbadjuber/anti-slop](https://github.com/miqdadbadjuber/anti-slop)은 이런 결과물을 줄이기 위해 AI 코딩 에이전트가 읽는 규칙 모음입니다. 별도의 디자인 생성 서비스가 아니라, 지금 쓰는 에이전트에게 줄 Markdown 문서와 skill 패키지에 가깝습니다. 원하는 디자인은 직접 정하고, anti-slop은 그 위에서 불필요한 표현과 미완성 요소를 걸러내는 역할입니다.

이번에는 **프로젝트에 파일을 놓고, 필요한 작업에서 읽도록 연결하고, 결과를 검수하는 방법**에 집중했습니다. 2026년 10월 9일 확인한 커밋 `388cbe3` 기준입니다. Windows의 격리 폴더에서 원본 다운로드와 파일 구성을 확인했으며, 에이전트로 UI를 생성한 전후 품질 비교는 하지 않았습니다.

## anti-slop의 역할과 현재 구성

현재 저장소는 UI뿐 아니라 문구, 접근성, 반응형 레이아웃, 코드 주석을 위한 skill도 제공합니다. 핵심은 **38개 규칙과 결과를 내놓기 전의 Delivery Gate**입니다. Delivery Gate는 에이전트에게 항목별 PASS·FAIL과 구체적인 근거를 보고하도록 요구하는 체크리스트입니다. 파일을 추가하면 CI가 자동으로 화면을 검사해주는 도구는 아닙니다.

규칙은 세 묶음으로 나뉩니다.

| 구분 | 판단 기준 | 대표 예시 |
| --- | --- | --- |
| Hard Gate | 어기면 실패로 보는 항목 | 출처 없는 수치, 가짜 후기, 작동하지 않는 버튼, 모바일 깨짐 |
| Purpose-Gate | 기법을 쓴 목적을 설명하는 항목 | 그라데이션, 아이콘, 배경 패턴, 그림자, 애니메이션 |
| Quality Locks | 결과의 일관성과 완성도를 맞추는 항목 | 콘텐츠에 맞는 배치, 구체적인 버튼 문구, 색상 체계, 디자인 선택 이유 |

그래서 “그라데이션은 전부 금지”로 이해하면 원래 의도와 달라집니다. 브랜드 색을 드러내거나 정보의 우선순위를 구분하기 위한 그라데이션이라면 목적을 적어두는 쪽입니다. 반대로 없는 고객 수를 채워 넣는 것은 예쁘게 보인다는 이유로 정당화할 수 없습니다.

**오래된 소개와 현재 파일 이름도 구분해야 합니다.** 검색 결과에는 대문자 `ANTISLOP.md`와 UI 전용 3파일 구성이 남아 있었지만, 확인한 최신 커밋의 단일 파일은 소문자 `antislop.md`입니다. README에는 핵심 `antislop`과 다섯 개의 전문 skill, 설치 프로그램, during·after 모드가 안내되어 있습니다. 예전 다운로드 주소를 그대로 복사하지 않는 편이 좋습니다.

## 디자인 방향과 필터의 분리

anti-slop 원문은 자신을 **스타일 가이드가 아닌 필터**라고 설명합니다. “무엇을 없애야 하는가”만 정해놓으면 정작 무엇을 보여줄지는 비어 있기 때문입니다.

<Image src="/anti-slop-ui-rules/01-direction.png" alt="anti-slop 원문에서 DESIGN.md, AGENTS.md, antislop.md의 역할을 구분한 부분" caption="방향은 DESIGN.md, 읽을 파일의 연결은 에이전트 지침, 검수 규칙은 antislop.md가 맡습니다. 출처: miqdadbadjuber/anti-slop, MIT." />

프로젝트에서 세 파일의 역할은 다음처럼 나누면 이해하기 쉽습니다.

- `DESIGN.md`: 대상 독자, 분위기, 색상, 글자, 정보 순서 등 **이 프로젝트가 원하는 방향**
- `AGENTS.md` 같은 에이전트 지침: 어떤 작업에서 어떤 문서를 읽을지 알려주는 **연결 지침**
- `antislop.md`: 방향을 구현하는 과정에서 지킬 **필터와 검수 기준**

여기서 `DESIGN.md`는 이 저장소가 제공하는 완성 디자인 파일을 내려받는다는 뜻이 아닙니다. 내 서비스의 방향을 담는 문서입니다. 이미 팀의 브랜드 가이드가 있다면 그것을 연결해도 됩니다. 파일 이름만 만들어놓고 내용이 비어 있으면 방향이 생기지는 않습니다.

원문에는 ENERGY, RHYTHM, MOTION이라는 세 가지 다이얼도 있습니다. 각각 시각적인 강도, 섹션 구성의 변화, 움직임의 정도를 1~3으로 표현합니다. 품질 점수가 아니라 **어떤 화면을 만들지 맞추는 표현**입니다. 공공 안내 페이지라고 해서 세 값이 모두 높을 이유는 없습니다.

## 프로젝트에 연결하는 순서

처음이라면 모든 에이전트에 전역 설치하기보다 **작은 프로젝트 하나에 단일 파일로 연결하는 방법**을 권합니다. 무엇을 읽고 무엇이 바뀌는지 확인하기 쉽기 때문입니다. 아래는 Codex의 프로젝트 지침 파일인 `AGENTS.md`를 사용하는 예시입니다.

### 원본 파일 준비

1. 작업할 프로젝트를 별도로 준비합니다. 기존 프로젝트라면 먼저 Git 변경 상태를 확인하고 현재 지침 파일을 보존합니다.
2. [확인한 커밋의 antislop.md](https://github.com/miqdadbadjuber/anti-slop/blob/388cbe3b6c37d5175b9f460015bb092ef9e34894/antislop.md)를 열어 Raw 원문을 저장합니다. 이름은 `antislop.md`로 맞춥니다.
3. 같은 커밋의 LICENSE도 함께 보존합니다. 이 프로젝트는 MIT 라이선스로, 복사본을 배포할 때 저작권 및 허가 고지를 남겨야 합니다.

터미널을 사용한다면 **테스트 프로젝트 폴더 안에서** 다음 명령으로 같은 원본을 받을 수 있습니다. Windows에서는 Git Bash 기준입니다. 같은 이름의 파일이 이미 있으면 덮어쓰므로 먼저 확인하세요.

```bash
curl -fL -o antislop.md https://raw.githubusercontent.com/miqdadbadjuber/anti-slop/388cbe3b6c37d5175b9f460015bb092ef9e34894/antislop.md
curl -fL -o ANTISLOP-LICENSE.txt https://raw.githubusercontent.com/miqdadbadjuber/anti-slop/388cbe3b6c37d5175b9f460015bb092ef9e34894/LICENSE
```

이 명령은 고정된 커밋의 파일을 받습니다. 매번 최신 내용을 받는 주소가 아닙니다. 실제로 두 파일을 내려받아 원본과 바이트가 같은지 확인했습니다. 규칙을 읽어보는 단계에서 별도의 패키지 실행이나 전역 설치는 필요하지 않습니다.

### 프로젝트의 방향 작성

`DESIGN.md`에는 “예쁘게 만들어줘” 대신 대상과 작업을 적습니다. 다음은 **동네 도서관 행사 안내라는 가상 프로젝트**를 위한 예시입니다. 실제 서비스의 요구사항으로 바꿔 사용하세요.

```markdown
# 동네 도서관 행사 안내

- 대상: 휴대폰으로 행사 일정과 신청 방법을 찾는 주민
- 첫 화면의 목적: 가장 가까운 행사와 신청 위치 확인
- 분위기: 조용하고 읽기 편한 지역 소식지
- 색상: 밝은 바탕과 짙은 본문, 신청 링크에만 녹색 강조
- 글자: 한글 본문이 잘 읽히는 시스템 글꼴, 행사명과 날짜의 크기 구분
- 구성: 행사 일정이 먼저, 위치와 문의 방법은 그다음
- 움직임: 버튼 상태 변화 정도만 사용
- Dial: ENERGY 1 / RHYTHM 2 / MOTION 1
```

이 정도만 있어도 배경 효과를 얼마나 넣을지보다 **행사명과 날짜를 먼저 읽을 수 있는지**가 판단의 중심이 됩니다. 실제 행사 정보와 신청 주소는 별도로 제공해야 합니다. 정보가 없다는 이유로 AI가 그럴듯한 행사나 후기를 만들어 채우게 두지 않습니다.

### 읽을 파일의 연결

아래 블록은 단일 파일만 쓰는 `core only` 구성에 맞춘 예시입니다. 기존 `AGENTS.md`가 있다면 전체를 교체하지 말고, 중복되는 anti-slop 지침이 없는지 확인한 다음 필요한 부분만 합칩니다.

```markdown
<!-- antislop:start -->
## UI 작업
UI를 만들거나 수정할 때 DESIGN.md의 방향을 확인하고 antislop.md를 읽습니다.
이번 프로젝트는 core only로 사용합니다. 추가 skill이나 전역 설정을 설치하지 않습니다.
이번 세션의 antislop 모드는 요청자가 during 또는 after로 명시합니다.
규칙과 브랜드 요구가 충돌하면 바꾸기 전에 충돌 항목을 설명하고 확인받습니다.
결과를 전달할 때 Delivery Gate의 각 항목에 실제 검증 근거를 붙입니다.
<!-- antislop:end -->
```

파일 구성은 이렇게 됩니다.

```text
sample-project/
├── AGENTS.md
├── DESIGN.md
├── antislop.md
└── ANTISLOP-LICENSE.txt
```

**모든 에이전트가 AGENTS.md를 똑같이 자동으로 읽는 것은 아닙니다.** [Codex 공식 문서](https://developers.openai.com/codex/guides/agents-md/)는 작업 시작 전 지침을 읽되, 전역 지침과 프로젝트 경로의 지침을 합치고 `AGENTS.override.md`를 우선하는 동작을 설명합니다. 다른 도구라면 그 도구가 읽는 프로젝트 지침에 같은 취지의 연결 문구를 넣어야 합니다. `DESIGN.md`와 `antislop.md`는 이름만으로 자동 적용된다고 가정하지 않습니다.

여기서 필요한 작업에만 파일을 읽게 하는 것이 온디맨드 연결입니다. 긴 규칙 전체를 공통 지침에 붙여넣는 대신 위치와 적용 조건을 남깁니다. 다만 **현재 공식 skill 설치 방식은 핵심 skill을 항상 로드하고 전문 skill을 작업에 따라 읽는 구성**이므로, 이 수동 예시와 로딩 방식까지 같다고 보면 안 됩니다.

새 세션을 열어 실제 읽기 기록과 경로를 확인하고, R-26의 의미와 `DESIGN.md`의 방향을 설명해 달라고 요청해보세요. 답변이 그럴듯한 것만으로는 충분하지 않습니다. 다른 폴더의 파일을 읽었거나 파일 읽기가 실패했다면 경로와 권한부터 바로잡습니다.

## 새 작업과 기존 화면 점검

현재 anti-slop에는 적용 시점이 다른 두 모드가 있습니다. **during은 작업 중 적용, after는 이미 있는 결과의 점검**입니다. 기본적으로 모드를 묻지만, 현재 세션에서 명시한 선택이나 저장된 전역 설정이 있으면 그에 따라 결정합니다.

### 새 UI를 만드는 during

파일을 연결한 뒤에는 범위를 좁혀 시작하는 편이 좋습니다. 다음은 실행 결과가 아니라 요청 예시입니다.

```text
이번 세션은 antislop during 모드로 진행해줘. core only로 사용해줘.
DESIGN.md와 antislop.md를 읽고, 행사 목록 화면 하나만 만들어줘.
실제 행사 정보와 신청 주소는 내가 제공한 자료만 사용해줘.
자료가 없으면 먼저 물어보고, 행사·후기·이용자 수를 만들지 마.
이미지는 생성하지 마.
완료 시 Delivery Gate와 버튼별 실제 동작 확인 결과를 보고해줘.
```

처음부터 홈페이지 전체를 바꾸기보다 목록 화면 하나나 신청 영역 하나를 정하면 규칙의 효과와 비용을 판단하기 쉽습니다. 디자인 방향이 비어 있다면 먼저 채웁니다. 원문도 방향 없이 만든 화면은 완성본이 아니라 `draft without direction`으로 표시하도록 요구합니다.

### 기존 화면을 점검하는 after

이미 만든 화면이 있다면 바로 고치게 하지 않고 발견 사항부터 받습니다.

```text
이번 세션은 antislop after 모드로 진행해줘. core only로 사용해줘.
현재 행사 목록 화면을 점검하고, 위반 규칙 번호와 이유를 목록으로 정리해줘.
아직 파일을 수정하지 마. 내가 승인한 항목만 수정해줘.
```

원문의 after 흐름은 번호가 붙은 발견 사항을 보고하고, 사용자가 고칠 번호를 승인하면 해당 항목을 수정한 뒤 후속 보고를 남기는 방식입니다. “검토해줘”라는 말만으로 after 모드가 선택된다고 기대하지 말고 **모드 이름을 명시**하는 편이 분명합니다.

브랜드 방향과 규칙이 부딪히는 경우도 있습니다. 예를 들어 브랜드 문구에 특정 표현을 유지해야 하는데 필터가 그것을 막는다면, 에이전트가 몰래 지우거나 그대로 통과시키기보다 충돌한 규칙과 선택지를 보여주게 해야 합니다.

## Delivery Gate와 실제 화면 검수

규칙을 읽었다는 답변보다 중요한 것은 결과물입니다. 원문 R-35는 앱을 실행하거나 빌드하고, 인터랙션을 하나씩 작동시킨 기록을 요구합니다. “모든 버튼 정상”이라는 한 줄보다 **어떤 버튼을 눌렀고 무엇이 일어났는지**가 있어야 판단할 수 있습니다.

행사 안내 화면이라면 다음 순서로 직접 확인할 수 있습니다.

1. **링크와 버튼:** 신청 버튼이 실제 신청 위치로 이동하는지, 메뉴가 열리고 닫히는지 확인합니다. `href="#"`만 넣은 버튼은 목적지 확인을 대신하지 못합니다.
2. **모바일:** 좁은 폭에서 페이지를 새로 열어 가로 넘침, 잘린 날짜, 겹치는 메뉴를 확인합니다. 데스크톱 화면을 작게 축소한 것과 반응형 배치는 다릅니다.
3. **키보드:** Tab으로 이동할 때 현재 위치가 보이는지, 링크와 버튼이 해당 컨트롤의 키보드 조작으로 작동하는지, 대화상자가 Escape로 닫히는지 봅니다.
4. **데이터 상태:** 데이터를 불러오는 화면이라면 빈 목록, 로딩, 실패 상태를 각각 확인합니다. 오류가 났는데 계속 로딩 중으로 보이면 완료로 처리하지 않습니다.
5. **내용의 근거:** 행사 날짜, 신청 조건, 후기, 수치가 실제 자료와 일치하는지 대조합니다. 코드를 실행했다고 내용까지 사실이 되는 것은 아닙니다.

검수 기록에는 사용한 화면 폭, 실행한 명령, 실제 동작, 남은 문제를 붙이면 됩니다. 브라우저 실행 권한이 없어 코드만 확인했다면 클릭 검증을 한 것처럼 PASS를 쓰지 않아야 합니다.

### 접근성 기준의 주의점

원문의 수치를 표준 문서 대신 그대로 쓰지는 않는 편이 좋습니다. 확인한 커밋의 R-25에는 큰 글자를 `18px+`로 적어둔 부분이 있습니다. 하지만 [WCAG의 큰 글자 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)은 일반 글자 18pt 이상 또는 굵은 글자 14pt 이상입니다. **18px와 18pt는 다른 단위**입니다. 일반 텍스트 4.5:1, 큰 텍스트 3:1이라는 대비 기준을 적용할 때 이 차이를 놓치면 안 됩니다.

anti-slop은 검수할 질문을 모으는 데 쓸 수 있지만, 접근성 인증이나 자동 검증기를 대신하지는 않습니다. 팀의 접근성 기준과 충돌한다면 표준 문서를 근거로 프로젝트 지침을 보완하고 실제 화면을 검사해야 합니다.

## skill 설치와 유지 관리

단일 파일로 흐름을 이해한 뒤 반복해서 쓸 계획이라면 공식 설치 경로를 검토할 수 있습니다. [현재 GUIDE](https://github.com/miqdadbadjuber/anti-slop/blob/388cbe3b6c37d5175b9f460015bb092ef9e34894/GUIDE.md)는 Node.js 18 이상과 다음 명령을 안내합니다.

```bash
npx antislop-ai
```

설치 프로그램은 전문 skill, 설치 범위, 사용할 에이전트를 선택하고 파일을 복사합니다. 첫 적용에서는 `This project`를 선택해 변경 범위를 확인하는 편이 안전합니다. 이 글에서는 이 설치 프로그램이나 에이전트별 플러그인을 실행하지 않았으므로, 위 경로는 **공식 안내에 따른 선택지**입니다.

핵심 `antislop` 외에 전문 skill은 다음처럼 나뉩니다. skill은 특정 작업의 지침을 담은 `SKILL.md`와 관련 파일의 묶음입니다.

- `antislop-ui`: 배치, 색상, 컴포넌트, 장식과 움직임
- `antislop-copywriting`: 제목, 버튼 문구, 어조와 근거 없는 수치
- `antislop-human`: 대비, 키보드, 포커스와 상태
- `antislop-layoutmobile`: 화면 폭에 따른 배치, 넘침과 터치 영역
- `antislop-code`: 불필요한 AI식 코드 주석 정리

파일을 복사하는 설치, skills 디렉터리 도구, 에이전트 플러그인은 관리 방식이 다릅니다. 여러 경로를 겹쳐 설치하지 말고 하나를 선택하세요. 특히 공식 안내의 `npx antislop-ai --update`는 **현재 프로젝트뿐 아니라 홈 디렉터리에서 찾은 설치본도 갱신**할 수 있습니다. 프로젝트 하나만 고친다고 생각하고 실행하지 않아야 합니다. 수동 단일 파일 방식이라면 새 버전과 기존 파일을 비교한 뒤 교체하고, 기존 에이전트 세션도 새로 시작합니다.

저라면 처음부터 금지 항목을 더 추가하기보다 **내 서비스의 방향, 실제 콘텐츠, 완료 확인 방법부터 정리**하겠습니다. anti-slop은 그 기준을 에이전트와 공유할 때 쓸 만한 출발점입니다. 다만 규칙 파일을 넣는 것과 결과가 좋아졌다는 것은 다른 이야기입니다. 팀의 디자인 시스템과 테스트가 이미 충분하다면 전체 규칙을 중복으로 도입하기보다 빠진 검수 항목만 비교해보는 것으로도 충분합니다.
