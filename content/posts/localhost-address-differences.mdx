### 목차

## 개발 화면과 공유 주소

AI가 만든 웹앱이 PC의 `http://localhost:5173`에서는 잘 열리는데, 같은 주소를 휴대폰에 보내면 열리지 않는 상황이 있습니다. 찾아보면 `127.0.0.1`로 바꾸라는 답도 있고, `0.0.0.0`을 쓰라는 답도 나옵니다. 숫자만 바꾸면 될 것 같지만, 세 표현은 역할이 다릅니다.

**localhost와 127.0.0.1은 접속하는 쪽의 자기 자신을 가리키고, 서버 설정의 0.0.0.0은 연결을 받을 IPv4 주소의 범위를 뜻합니다.** 휴대폰에서 localhost를 열면 개발 중인 PC가 아니라 휴대폰 자신을 찾습니다. 서버를 0.0.0.0으로 실행했다고 그 주소가 다른 사람에게 보낼 웹사이트 주소가 되는 것도 아닙니다.

2026년 11월 1일 공식 문서를 확인하고, Windows에서 로컬 시험 서버를 실행해 주소별 브라우저 저장소도 비교해봤습니다. 먼저 **어디로 접속하는지**와 **어디에서 연결을 받는지**를 나눠보겠습니다.

## localhost와 127.0.0.1

`localhost`는 자기 컴퓨터의 루프백(loopback) 주소를 가리키는 특별한 이름입니다. 루프백은 네트워크 요청을 외부 기기로 보내는 대신 자기 쪽으로 돌려주는 경로라고 생각하면 됩니다. IPv4에서 흔히 쓰는 주소가 `127.0.0.1`이고, IPv6에서는 `::1`입니다.

[RFC 6761의 localhost 정의](https://www.rfc-editor.org/rfc/rfc6761.html#section-6.3)는 localhost 이름의 IPv4·IPv6 주소 조회가 각각의 루프백 주소를 반환하도록 설명합니다. 따라서 localhost를 무조건 `127.0.0.1`이라는 문자열의 다른 표기라고만 외우면 IPv6 환경에서 헷갈릴 수 있습니다.

예를 들어 아래 주소는 모두 **접속하는 프로그램이 속한 환경의 자기 자신**을 대상으로 합니다.

```text
http://localhost:5173
http://127.0.0.1:5173
http://[::1]:5173
```

IPv6 주소를 URL에 넣을 때는 주소 부분을 대괄호로 감쌉니다. 세 주소가 실제로 모두 열리려면 서버도 해당 주소 체계에서 연결을 받아야 합니다. 서버가 IPv4의 `127.0.0.1`에서만 기다리는데 클라이언트가 IPv6의 `::1`로 접속하면 같은 결과가 아닐 수 있습니다. [Vite 공식 문서](https://vite.dev/config/server-options#server-host)도 localhost의 주소 해석과 서버가 기다리는 주소가 달라지는 경우를 별도로 설명합니다.

뒤의 `5173`은 **포트**입니다. 같은 컴퓨터에서 여러 서버가 실행될 때 어느 연결 지점으로 갈지 구분합니다. 주소가 맞아도 포트가 다르거나 서버가 종료돼 있으면 원하는 화면은 열리지 않습니다. 특히 Vite는 지정한 포트가 이미 사용 중이면 다른 포트를 시도할 수 있으므로, 예제의 숫자보다 실행 직후 터미널에 표시된 실제 주소를 확인해야 합니다.

### 접속하는 기기에 따른 의미

PC에서 `localhost:5173`을 열면 PC의 서버를 찾습니다. 휴대폰에서 같은 문자열을 열면 휴대폰의 서버를 찾습니다. 동료의 노트북도 마찬가지입니다. **localhost 링크를 전달하는 것은 내 PC의 위치를 알려주는 일이 아닙니다.**

또 하나 놓치기 쉬운 경우가 AI 도구입니다. 브라우저 자동화 도구가 원격 서버나 컨테이너 안에서 실행된다면, 그 도구의 localhost가 내 PC를 뜻하지 않을 수 있습니다. 주소를 전달하기 전에 브라우저와 개발 서버가 실제로 어디에서 실행되는지부터 확인해야 합니다.

## 0.0.0.0과 서버 바인딩

서버는 시작할 때 어떤 로컬 주소에서 연결을 받을지 정합니다. 이를 **바인딩**(binding)이라고 합니다. 여기서 쓰는 주소와 브라우저 주소창에 넣는 목적지는 구분해야 합니다.

| 서버가 연결을 받는 주소 | 의미 |
| --- | --- |
| `127.0.0.1` | 자기 환경의 IPv4 루프백에서 연결을 받음 |
| 특정 LAN IP | 그 컴퓨터에 할당된 해당 IPv4 주소에서 연결을 받음 |
| `0.0.0.0` | 그 환경의 모든 로컬 IPv4 주소에서 연결을 받음 |
| `::` | IPv6의 모든 로컬 주소에서 연결을 받는 표현. IPv4도 함께 받는지는 환경·설정에 따라 다름 |

`0.0.0.0`의 ‘모든 주소’는 **이 서버가 속한 환경의 주소들**입니다. 전 세계 컴퓨터를 가리키는 주소가 아닙니다. [Node.js 문서](https://nodejs.org/docs/latest-v22.x/api/net.html#serverlistenport-host-backlog-callback)는 host를 생략하면 IPv6 사용 가능 여부에 따라 `::` 또는 `0.0.0.0`에서 연결을 받는다고 설명합니다. 즉, 주소를 생략했다고 항상 로컬 전용이 되는 것도 아닙니다. 기본값은 도구마다 확인해야 합니다.

Vite의 `server.host` 기본값은 `localhost`입니다. 공식 안내에서 `--host 0.0.0.0`은 LAN과 공인 주소를 포함한 모든 주소에서 연결을 받게 하는 옵션입니다. 이것은 **접속이 안 될 때 무조건 붙이는 옵션이 아니라, 서버의 연결 범위를 넓히는 선택**입니다.

### 다른 기기에서 사용할 목적지

설명용으로 PC의 LAN IP가 `192.168.1.25`, 서버 포트가 `5173`이라고 가정해보겠습니다. 휴대폰에서 사용할 후보 주소는 다음과 같습니다.

```text
http://192.168.1.25:5173
```

이 IP는 예시이므로 실제 PC의 주소로 바꿔야 합니다. `http://0.0.0.0:5173`을 공유하는 것이 아닙니다. 어떤 환경에서 0.0.0.0으로 접속이 되더라도, 다른 기기가 내 PC를 찾아갈 목적지로 의존하면 안 됩니다.

여기에는 조건이 더 있습니다. PC의 서버가 LAN 쪽 연결을 받아야 하고, 휴대폰에서 그 PC로 가는 네트워크 경로가 있어야 하며, 방화벽과 앱의 접근 정책도 요청을 허용해야 합니다. 같은 Wi-Fi 이름에 연결돼 있어도 게스트 네트워크처럼 기기 사이 통신이 차단된 경우가 있습니다.

**0.0.0.0 바인딩은 인터넷 배포와 같지 않습니다.** 공유기·방화벽·포트 전달 등의 조건이 따로 있습니다. 반대로 공인 네트워크에 연결된 서버에서는 의도보다 넓게 노출될 수 있으므로, ‘내 PC에서 실행했으니 비공개’라고 판단해서도 안 됩니다.

## 같은 서버와 다른 브라우저 저장소

localhost와 127.0.0.1이 같은 서버로 연결되더라도 브라우저가 같은 출처로 취급하는 것은 아닙니다. 브라우저의 **출처**(origin)는 프로토콜, 호스트, 포트의 조합입니다. [MDN의 동일 출처 정책](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)은 이 세 가지가 같아야 동일 출처라고 설명합니다.

```text
http://localhost:4317
http://127.0.0.1:4317
http://127.0.0.1:4318
```

첫 번째와 두 번째는 호스트가 다르고, 두 번째와 세 번째는 포트가 다릅니다. 같은 PC에서 같은 화면을 보여줘도 서로 다른 origin입니다. 반면 `http://localhost:4317/another-path`는 경로만 달라서 첫 번째와 origin이 같습니다.

### 로컬 저장소 비교

Windows와 Node.js 22.23.2, Chromium 계열 브라우저 153.0.8010.36에서 작은 시험 페이지를 실행했습니다. 서버는 `127.0.0.1`의 두 포트에서만 연결을 받도록 했고, 외부 네트워크에는 공개하지 않았습니다.

시험 페이지에는 현재 `location.origin`과 `localStorage`의 시험값을 표시했습니다. 브라우저 자동화로 `http://localhost:4317`의 저장 버튼을 실행해 `LOCAL-DEMO`라는 값을 저장했습니다.

<Image src="/localhost-address-differences/00.png" alt="직접 만든 로컬 시험 페이지에서 localhost:4317의 origin과 저장된 LOCAL-DEMO 값을 확인한 화면" caption="실제 실행한 시험 페이지입니다. 특정 제품의 공식 UI나 로그인 화면이 아닙니다." />

이어서 같은 브라우저로 주소를 바꿔 접속했습니다. [localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)는 문서의 origin에 속하는 저장소이므로, 다른 origin에서는 방금 저장한 값이 보이지 않았습니다.

| 접속한 호스트·포트와 경로 | 시험값 조회 결과 |
| --- | --- |
| `localhost:4317` | `LOCAL-DEMO` |
| `127.0.0.1:4317` | 값 없음 |
| `127.0.0.1:4318` | 값 없음 |
| `localhost:4317/another-path` | `LOCAL-DEMO` |

<Image src="/localhost-address-differences/01.png" alt="127.0.0.1:4317로 접속하자 같은 시험 페이지에서 저장된 값 없음이 표시된 화면" caption="호스트를 127.0.0.1로 바꾼 결과입니다. localhost에 저장한 값을 삭제한 것은 아닙니다." />

이 결과로 확인한 것은 **localStorage의 출처 분리**입니다. 실제 서비스의 로그인 방식까지 시험한 것은 아닙니다. 쿠키에는 Domain·Path 등 별도의 규칙이 있고 [포트로 분리되지도 않으므로](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5), 이 표를 모든 로그인 동작에 그대로 적용하면 안 됩니다.

개발 도중 주소를 바꾼 뒤 설정이나 저장값이 사라진 것처럼 보인다면, 데이터를 지우거나 인증 코드를 고치기 전에 **원래 쓰던 프로토콜·호스트·포트와 같은지**부터 확인하는 편이 좋습니다.

## 로컬 확인과 다른 기기 공유

주소를 고를 때는 먼저 누가 접속해야 하는지 정하는 편이 좋습니다.

| 필요한 작업 | 선택할 방향 | 완료 확인 |
| --- | --- | --- |
| 내 PC에서만 개발 화면 확인 | 루프백에서 연결을 받도록 설정하고 같은 PC에서 접속 | 실제 실행 주소와 포트에서 의도한 화면 확인 |
| 신뢰하는 같은 네트워크의 휴대폰에서 확인 | 필요한 LAN 연결을 허용하고 PC의 실제 LAN IP 사용 | 휴대폰에서 화면뿐 아니라 필요한 API 요청까지 확인 |
| 다른 장소의 동료에게 전달 | 인증·접근 제한을 갖춘 미리보기 배포 등 별도 공유 방식 검토 | 상대 환경에서 의도한 권한으로 접속되는지 확인 |

휴대폰이 모바일 데이터에 연결돼 있다면 PC의 사설 LAN 주소만 보내는 방식으로는 보통 연결되지 않습니다. 개발 서버를 띄우는 것과 외부에서 접근 가능한 미리보기 환경을 준비하는 것은 다른 작업입니다.

페이지가 열리는데 데이터만 안 나온다면, 프런트엔드가 호출하는 API 주소도 봐야 합니다. 예를 들어 **휴대폰 브라우저에서 실행되는 JavaScript**가 `http://localhost:8000`을 호출하면 그 요청은 PC가 아니라 휴대폰 자신을 향합니다. 서버 측 코드가 보내는 요청인지, 브라우저가 보내는 요청인지 구분하면 바꿀 위치를 좁힐 수 있습니다.

### WSL과 가상 환경의 경계

WSL2에서 실행하는 서버는 일반 Windows 프로세스와 네트워크 조건이 다를 수 있습니다. [Microsoft의 WSL 네트워크 문서](https://learn.microsoft.com/en-us/windows/wsl/networking)는 NAT 방식과 mirrored 방식, Windows에서 Linux 앱으로 접속하는 경우와 반대 방향을 구분합니다. Vite 문서도 **WSL2에서는 host를 켜는 것만으로 LAN 접속이 충분하지 않을 수 있다**고 안내합니다.

따라서 Windows 브라우저에서 localhost가 열린다는 사실만으로 휴대폰에서도 같은 방식으로 접근할 수 있다고 결론 내리면 안 됩니다. WSL·가상 머신·원격 개발 환경이라면 서버가 실행되는 위치와 네트워크 모드를 먼저 확인하세요. 여기서의 저장소 비교는 Windows의 로컬 Node 서버를 대상으로 했으며, 휴대폰·WSL의 실제 연결 성공을 검증한 결과는 아닙니다.

## 개발 서버의 접근 제한

접속 문제를 해결하려고 방화벽을 통째로 끄거나 개발 서버의 모든 접근 검사를 해제하는 방법은 피하는 편이 좋습니다. 서버가 연결을 받는 주소, 허용할 호스트 이름, 브라우저가 다른 출처의 응답을 읽도록 하는 CORS는 서로 다른 설정입니다.

Vite는 `server.allowedHosts: true`가 DNS rebinding 공격을 통해 소스 코드와 콘텐츠를 노출할 수 있다고 경고합니다. `server.cors: true`도 모든 웹사이트가 개발 서버의 응답을 읽을 수 있게 하는 위험을 안내합니다. **0.0.0.0 설정과 함께 두 검사를 모두 끄는 것을 기본 해결책으로 삼으면 안 됩니다.**

저라면 주소를 바꾸기 전에 다음 순서로 정리하겠습니다.

1. **실행 위치:** 개발 서버와 접속할 브라우저가 같은 PC·같은 환경에 있는지 확인합니다.
2. **실제 주소:** 터미널에 표시된 호스트와 포트, 서버의 실행 상태를 확인합니다.
3. **필요한 범위:** 혼자 볼지, 신뢰하는 LAN에서 볼지, 외부에 공유할지 결정합니다.
4. **최소 변경:** 필요한 연결만 허용하고, 확인이 끝나면 임시 공유 설정을 되돌리거나 시험 서버를 종료합니다.

localhost는 내 앱의 고유 주소가 아니라 접속하는 쪽을 기준으로 한 이름입니다. 0.0.0.0은 공유 링크가 아니라 서버의 연결 범위입니다. 이 둘을 구분하면 AI가 제안한 주소나 옵션도 그대로 복사하기보다, **누가 어디에서 이 서버에 접속해야 하는지**를 기준으로 선택할 수 있습니다.
