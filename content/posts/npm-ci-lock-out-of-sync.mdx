### 목차

## 들어가며

AI에게 기능을 추가하도록 맡긴 뒤 로컬 개발 서버는 실행되는데, GitHub Actions나 배포 서비스에서 설치가 멈출 때가 있습니다. 로그에 `npm ci`와 함께 `package.json and package-lock.json ... are in sync`라는 문구가 보인다면 캐시부터 지울 일은 아닙니다.

**먼저 `package.json`의 의존성 변경이 의도한 것인지 확인하고, 그 조건에 맞는 lockfile이 수정 커밋에 포함돼 있는지 봐야 합니다.** `npm ci`는 어긋난 lockfile을 고쳐주는 명령이 아니라, 이미 정해진 의존성을 새로 설치하는 명령입니다. 로컬에서 `npm install`이 성공했다는 것과 CI가 같은 파일·옵션으로 설치할 수 있다는 것은 별개입니다.

이 글은 npm의 `package-lock.json`을 사용하는 프로젝트를 대상으로 합니다. 2026년 10월 11일 공식 문서를 확인하고, Windows 11 빌드 26200·Node.js `22.23.2`·npm `10.9.8`의 별도 폴더에서 불일치와 복구를 재현했습니다. pnpm이나 Yarn 프로젝트의 lockfile을 npm 것으로 바꾸는 안내는 아닙니다.

## 오류 메시지와 두 파일의 역할

이번 재현에서 `npm ci`는 종료 코드 `1`과 함께 다음 오류를 출력했습니다. 관련 부분만 발췌했습니다.

```text
npm error code EUSAGE
npm error `npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync. Please update your lock file with `npm install` before continuing.
npm error Invalid: lock file's is-number@7.0.0 does not satisfy is-number@6.0.0
```

여기서는 프로젝트가 `is-number`의 `6.0.0`을 요구하지만, lockfile에는 `7.0.0`이 기록돼 있다는 뜻입니다. 오류의 마지막 `Invalid`나 `Missing` 줄을 읽어야 어떤 패키지에서 어긋났는지 좁힐 수 있습니다. `EUSAGE`라는 코드만으로 원인을 하나로 단정하지는 마세요.

- `package.json`은 필요한 패키지와 허용할 버전 조건을 선언합니다.
- `package-lock.json`은 구체적인 의존성 트리를 기록합니다.
- `node_modules`는 현재 컴퓨터에 실제로 설치된 결과입니다.

[npm ci 공식 문서](https://docs.npmjs.com/cli/v10/commands/npm-ci)에 따르면 lockfile이 있어야 하고, 의존성이 선언과 맞지 않으면 파일을 갱신하는 대신 오류로 종료합니다. 설치를 진행할 때는 기존 `node_modules`를 제거하고 다시 설치하며, `package.json`과 lockfile에는 쓰지 않습니다.

따라서 개발 서버가 이전 `node_modules`로 실행된다고 두 파일이 정상이라는 뜻은 아닙니다. 반대로 **두 파일에 적힌 버전 문자열이 다르다고 무조건 오류인 것도 아닙니다.** 예를 들어 선언이 `^6.0.0`이고 lockfile의 실제 버전이 `6.0.0`이면 허용 범위 안입니다. 이번 테스트에서도 이 조합의 `npm ci`는 성공했습니다.

## 파일을 바꾸기 전 확인 순서

먼저 실패한 CI 실행의 커밋과 작업 디렉터리를 확인합니다. 저장소 안에 앱이 여러 개라면 로컬에서 고친 앱과 CI가 설치하는 앱이 다를 수 있습니다. 아래 명령은 **설치 대상의 `package.json`이 있는 폴더**에서 실행합니다. npm workspaces를 쓴다면 루트의 lockfile과 CI의 작업 위치도 함께 확인해야 합니다.

```bash
node --version
npm --version
git status --short
git diff HEAD -- package.json package-lock.json
git ls-files -- package-lock.json
```

확인할 것은 다음과 같습니다.

1. **의존성 변경 의도:** 기능 추가에 필요한 변경인지, AI 편집이나 병합 중 실수로 바뀐 것인지 diff로 확인합니다.
2. **lockfile의 존재와 전달 상태:** 파일이 로컬에 있는 것과 원격 커밋에 포함된 것은 다릅니다. `git ls-files`는 Git 인덱스에 등록된 경로를 보여줄 뿐, push나 CI 전달까지 증명하지 않습니다. 실패한 커밋의 GitHub 파일 화면도 확인합니다.
3. **Node.js·npm 버전:** 로컬 출력과 CI 로그를 대조합니다. 다르다는 이유만으로 원인을 확정하지는 않되, 프로젝트가 사용하는 버전으로 맞춰 재현해야 합니다.
4. **패키지 관리자:** 저장소가 npm을 쓰는지 먼저 확인합니다. 다른 도구의 lockfile만 있는데 CI에서 `npm ci`를 실행한다면 설치 명령과 프로젝트 규칙부터 어긋난 것입니다.

파일이 있는데도 안 읽힌다면 경로와 파일명도 봐야 합니다. 루트에 `npm-shrinkwrap.json`이 함께 있으면 [공식 우선순위](https://docs.npmjs.com/cli/v10/configuring-npm/package-lock-json)에 따라 그것이 `package-lock.json`보다 우선합니다. `node_modules/.package-lock.json`은 npm의 내부용 파일이므로 저장소 루트의 lockfile을 대신해서 제출하는 파일이 아닙니다.

로그를 공유할 때는 private registry 주소나 토큰을 먼저 제거하세요. `.npmrc` 전체를 공개하거나 AI 대화에 그대로 붙여 넣을 필요는 없습니다.

## 변경 의도에 따른 lockfile 복구

### 필요한 의존성 변경인 경우

변경한 패키지와 버전 범위가 맞다면 프로젝트에서 사용하는 npm 버전으로 lockfile을 갱신합니다. 일반적으로는 `npm install`을 실행하고 diff를 확인하면 됩니다. 다만 설치 상태를 바꾸기 전에 **lockfile 변경부터 검토**하고 싶다면 다음 방법을 사용할 수 있습니다.

```bash
npm install --package-lock-only --ignore-scripts --no-audit --no-fund
git diff HEAD -- package.json package-lock.json
```

[공식 npm install 문서](https://docs.npmjs.com/cli/v10/commands/npm-install)는 `--package-lock-only`가 `node_modules`를 설치하는 대신 lockfile만 갱신하는 옵션이라고 설명합니다. 이 명령도 의존성 해석을 위해 레지스트리 접근이 필요할 수 있으며, 오프라인 전용 명령은 아닙니다.

여기서 `--ignore-scripts`는 검토 단계에서 패키지의 설치 스크립트를 실행하지 않으려고 붙였습니다. `--no-audit`와 `--no-fund`는 해당 호출의 감사 요청과 후원 안내를 생략합니다. **이 옵션들이 패키지의 안전성이나 앱의 정상 동작을 검증해주는 것은 아닙니다.**

diff에 의도하지 않은 의존성 변경이 크게 생겼다면 바로 커밋하지 말고, npm 버전·설정·변경한 버전 범위를 다시 확인합니다. 직접 의존성 하나를 바꿔도 연결된 하위 의존성은 함께 바뀔 수 있으므로 줄 수만으로 잘못됐다고 판단할 필요는 없습니다.

### 실수로 선언을 바꾼 경우

원래 의존성을 유지해야 한다면 잘못 바뀐 `package.json` 항목부터 되돌립니다. 전체 파일을 강제로 복구하면 다른 작업까지 사라질 수 있으니 변경 부분을 확인해 필요한 항목만 수정하세요.

그다음 기존 lockfile과 다시 설치할 수 있는지 확인합니다. 오류를 없애려고 lockfile을 새 선언에 맞추면, **원하지 않은 패키지 변경을 정식으로 확정하는 결과**가 될 수 있습니다.

### lockfile이 없는 경우

팀에서 관리하던 lockfile을 빠뜨렸다면 먼저 정상 커밋의 파일을 찾는 편이 좋습니다. 새 npm 프로젝트라서 처음부터 없던 경우에는 `npm install`로 생성하고 저장소에 포함합니다. 이미 pnpm·Yarn을 쓰는 프로젝트라면 npm lockfile부터 새로 만들 것이 아니라 CI의 설치 명령을 확인해야 합니다.

lockfile 삭제 후 전체 재생성은 기본 해법으로 권하지 않습니다. 허용된 버전 범위 안에서 더 많은 패키지가 새로 선택될 수 있어, 설치 오류 수정과 의존성 업데이트가 한꺼번에 섞이기 때문입니다. 필요한 변경만 검토하는 쪽이 원인 추적과 되돌리기에 유리합니다.

## 실제 재현에서 달라진 설치 상태

별도 테스트 프로젝트에 `is-number@7.0.0`을 설치한 뒤, `package.json`의 요구사항만 `6.0.0`으로 변경해봤습니다. 작은 패키지로 조건을 단순하게 만든 실험이며, 이 버전들을 앱에 쓰라는 추천은 아닙니다.

| 단계 | package.json의 요구 | lockfile의 버전 | 확인 결과 |
| --- | --- | --- | --- |
| 정상 설치 뒤 `npm ci` | `7.0.0` | `7.0.0` | 성공 |
| 선언만 바꾼 뒤 `npm ci` | `6.0.0` | `7.0.0` | `EUSAGE`, 종료 코드 1 |
| `--package-lock-only`로 갱신 | `6.0.0` | `6.0.0` | lockfile 갱신 성공, 설치본은 여전히 7.0.0 |
| 갱신 뒤 다시 `npm ci` | `6.0.0` | `6.0.0` | 성공, 실제 설치본도 6.0.0 |

실패 전후의 lockfile 해시는 같았습니다. `npm ci`가 몰래 파일을 고쳐주지 않았다는 뜻입니다. 또한 lockfile만 갱신한 직후에는 `node_modules`의 `is-number`가 여전히 `7.0.0`이었습니다.

이후 같은 테스트 폴더에서 다음 명령으로 재설치와 실제 버전을 확인했습니다.

```bash
npm ci --ignore-scripts --no-audit --no-fund
node -p "require('is-number/package.json').version"
```

버전 출력은 `6.0.0`이었습니다. 실험에서는 패키지 설치 스크립트를 실행하지 않도록 모든 설치 명령에 `--ignore-scripts`를 사용했습니다. 실제 앱은 필요한 설치 스크립트가 있을 수 있으므로, 이 실험용 옵션을 CI에 그대로 추가하고 앱까지 검증됐다고 판단해서는 안 됩니다.

**lockfile 갱신 성공과 실제 설치 성공을 따로 확인하는 것**이 이 재현에서 중요한 부분입니다. 실제 프로젝트에서는 그다음 빌드와 테스트까지 통과해야 합니다.

## 로컬만 성공할 때의 설치 옵션

두 파일을 함께 올렸는데 CI에서만 실패한다면 설치 옵션을 확인할 차례입니다. npm 공식 문서는 `--legacy-peer-deps`나 `--install-links`처럼 의존성 트리 형태에 영향을 주는 옵션으로 lockfile을 만들었다면, `npm ci`에도 같은 옵션을 전달해야 한다고 안내합니다.

전체 설정을 출력하기보다 아래처럼 필요한 항목만 로컬과 CI에서 비교하면 됩니다.

```bash
npm config get legacy-peer-deps
npm config get install-links
```

로컬에서는 `true`, CI에서는 `false`라면 프로젝트의 `.npmrc`, 사용자 `.npmrc`, 환경변수, CI 명령에 직접 붙인 옵션을 대조합니다. [npm 설정 문서](https://docs.npmjs.com/cli/v10/configuring-npm/npmrc)에 따르면 설정은 여러 위치에서 읽힙니다. 명령에 직접 붙인 플래그도 함께 봐야 하므로, 위 출력만 같다고 모든 실행 조건이 같아지는 것은 아닙니다.

다만 오류를 없애려고 무조건 `--legacy-peer-deps`를 켜지는 마세요. 이 옵션은 peer dependency 관계를 무시하는 방식이어서, 호환성 문제 자체를 해결해주는 것이 아닙니다. 기존 프로젝트가 그 설정을 의도적으로 쓰는지 확인하고, 공유해야 한다면 **토큰을 제외한 프로젝트 설정만** 버전 관리합니다. 사설 레지스트리 인증은 CI의 비밀값 관리 기능으로 따로 전달해야 합니다.

계속 실패한다면 다음처럼 나눠보면 좋습니다.

| 관찰한 상황 | 다음 확인 대상 |
| --- | --- |
| 로컬에서도 같은 `Invalid`·`Missing` 오류 | 변경 의도, lockfile 갱신 결과, 설치 대상 폴더 |
| 로컬은 성공하지만 CI만 같은 오류 | 실패 커밋의 파일, Node.js·npm 버전, 설치 옵션 |
| `ERESOLVE`로 의존성 충돌 발생 | 패키지별 peer dependency와 호환 버전 |
| 인증·네트워크·레지스트리 오류 | 접근 권한과 연결 상태. lockfile 삭제로 해결할 문제가 아님 |
| 설치는 끝났지만 빌드·테스트 실패 | 앱 코드, 설치 스크립트, 런타임·개발 의존성 선택 |

같은 파일·버전·옵션으로도 문제가 남으면 최소 재현과 민감정보를 제거한 로그를 준비해 npm 이슈나 해당 배포 서비스의 지원 경로로 확인합니다. CI에서 `npm ci`를 `npm install`로 바꿔 오류를 지나가게 하는 것만으로는, 커밋한 lockfile이 올바르다는 검증이 되지 않습니다.

## CI에서의 복구 완료 확인

수정한 프로젝트를 신뢰할 수 있고 필요한 설치 스크립트도 검토했다면, **CI와 같은 옵션의 `npm ci`로 깨끗하게 설치한 뒤 프로젝트의 빌드·테스트를 실행**합니다. 기존 `node_modules`가 교체되므로 실행 중인 개발 작업은 먼저 정리하고, 보존할 변경사항은 따로 남겨두세요.

완료 기준은 로컬의 성공 메시지 하나가 아닙니다.

1. 의도한 `package.json`과 그에 맞는 lockfile의 diff를 검토합니다.
2. 서로 맞는 두 파일이 담긴 커밋을 전달합니다. 항상 두 파일을 모두 수정해야 한다는 뜻은 아닙니다. 선언이 이미 맞다면 lockfile만 바뀔 수 있습니다. 공유할 설치 설정이 있다면 비밀값 없이 함께 검토합니다.
3. CI가 그 커밋과 올바른 작업 폴더를 사용했는지 확인합니다.
4. `npm ci`뿐 아니라 이어지는 빌드·테스트 결과도 확인합니다.

[GitHub Actions의 재실행](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-workflow-runs/re-running-workflows-and-jobs)은 원래 이벤트의 커밋 SHA와 Git ref를 사용합니다. 새 파일을 올렸다면 이전 실행을 반복하기보다 **수정 커밋을 대상으로 한 실행인지**를 먼저 보세요.

AI에게 수정을 맡길 때도 “설치 오류를 없애줘”보다 “의존성 변경 의도를 확인하고, lockfile diff와 같은 조건의 clean install·테스트 결과를 보여줘”라고 완료 조건을 구체화하는 편이 좋습니다. 오류를 통과시키는 것보다, 다른 환경에서도 같은 의존성을 다시 설치할 수 있게 만드는 것이 목표입니다.
