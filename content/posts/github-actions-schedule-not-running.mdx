GitHub Actions에서 **Run workflow로 실행하면 성공하는데 예약한 시간이 지나도 아무 기록이 없는 경우**가 있습니다. 이때 작업 코드나 토큰 권한부터 바꾸면 확인할 것이 오히려 늘어납니다. 먼저 `schedule`로 만들어진 실행 기록이 있는지부터 나눠보는 편이 좋습니다.

실행 기록 자체가 없다면 기본 브랜치, 워크플로 활성 상태, 예약 시간 설정을 확인합니다. 기록은 있는데 대기하거나 실패했다면 그다음부터 실행 환경과 작업 로그를 보는 순서입니다. **수동 실행 성공과 예약 실행 정상 동작은 서로 다른 확인 항목**입니다.

이 글은 2026년 10월 8일 확인한 GitHub.com 공식 문서를 기준으로 정리했습니다. 아래 진단용 YAML은 독자의 저장소에 적용할 예시이며, 이 글을 위해 운영 워크플로를 변경하거나 새 예약 작업을 실행하지는 않았습니다.

## 실행 기록 유무에 따른 확인 순서

저장소의 **Actions 탭에서 문제가 있는 워크플로를 선택**하고, 예상 시간대의 실행을 찾아봅니다. 다른 워크플로의 성공 기록이나 수동 실행 기록을 예약 실행으로 착각하지 않는 것이 먼저입니다.

| 보이는 상태 | 먼저 확인할 항목 |
| --- | --- |
| `schedule` 실행 기록이 없음 | 기본 브랜치의 파일, 활성 상태, cron과 시간대 |
| 실행 기록은 있으나 대기 중 | runner 할당, 승인 대기, 동시 실행 설정 |
| 실행 안의 job이나 step이 건너뛰어짐 | 해당 단계의 `if` 조건과 이전 단계 결과 |
| 실행 기록이 실패로 끝남 | 실패한 step의 로그, 인증·네트워크·명령 오류 |
| 실행은 성공했지만 결과물이 없음 | 실제 작업 수행 여부와 결과가 저장되는 위치 |

초록색 성공 표시만으로 외부 서비스의 업데이트까지 완료됐다고 판단할 수는 없습니다. 반대로 실행 기록이 없는 상태에서 애플리케이션의 오류 로그를 찾으려고 해도 볼 로그가 아직 없을 수 있습니다.

### 공개 저장소의 API 확인

화면에서 구분하기 어렵다면 공개 저장소는 브라우저로 다음 API 주소를 열어 확인할 수 있습니다. `OWNER`, `REPO`, `WORKFLOW_FILE`을 각각 소유자, 저장소 이름, `daily-check.yml` 같은 **파일명**으로 바꿉니다. 전체 파일 경로를 넣는 자리가 아닙니다.

워크플로 상태를 확인하는 주소입니다.

```text
https://api.github.com/repos/OWNER/REPO/actions/workflows/WORKFLOW_FILE
```

응답의 `state`를 봅니다. `active`는 활성 상태이고, `disabled_fork`, `disabled_inactivity`, `disabled_manually`는 각각 fork, 활동 없음, 수동 비활성 상태를 구분하는 값입니다. 다만 `active` 자체가 다음 예약의 실행을 보장하는 것은 아닙니다.

같은 워크플로에서 예약으로 생성된 실행만 조회하는 주소는 다음과 같습니다.

```text
https://api.github.com/repos/OWNER/REPO/actions/workflows/WORKFLOW_FILE/runs?event=schedule&per_page=10
```

`workflow_runs` 안의 `event`, `created_at`, `status`, `conclusion`을 확인하면 어떤 이벤트로 언제 생성된 실행인지 구분할 수 있습니다. `created_at`의 끝이 `Z`라면 UTC 시각입니다. 위 주소는 한 페이지에 최대 10개를 반환하므로, 확인하려는 시간대가 포함되지 않았다면 주소 끝에 `&page=2`를 붙여 다음 페이지도 확인합니다.

**HTTP 200 응답에서 배열이 비어 있는 것과, 조회가 403·404로 실패한 것은 다릅니다.** 인증이나 API 호출 한도 문제를 예약 실패로 해석하지 않습니다.

이 두 조회 경로는 공개 저장소에서 실제 HTTP 200 응답을 확인했습니다. 비공개 저장소는 적절한 인증과 읽기 권한이 필요하므로 로그인한 Actions 화면부터 확인하는 편이 간단합니다. 오래된 실행 기록이 삭제됐다면 API에 없을 수도 있으니, 과거 전체가 아니라 지금 놓친 예약 시간대를 기준으로 비교합니다.

## 기본 브랜치와 워크플로 활성 상태

GitHub의 예약 실행은 **기본 브랜치에 있는 워크플로 파일을 기준으로, 그 브랜치의 최신 커밋에서 실행**됩니다. 기본 브랜치 이름이 반드시 `main`인 것은 아닙니다.

먼저 다음 두 가지를 확인합니다.

1. 저장소의 실제 기본 브랜치에 `.github/workflows/파일명.yml`이 있는지 확인합니다. 작업 브랜치에만 올려두거나 PR만 만든 상태라면 아직 예약 대상이 아닙니다.
2. 그 파일에 의도한 `on.schedule` 설정이 들어 있는지 확인합니다. 로컬 파일이나 작업 브랜치의 YAML이 아니라 **원격 기본 브랜치의 내용**을 봅니다. 문법 오류가 표시되어 있다면 그 오류부터 수정합니다.

수동 실행에서는 다른 브랜치를 선택할 수 있습니다. 따라서 작업 브랜치로 Run workflow를 실행해 성공한 결과를 기본 브랜치의 예약 설정 검증으로 대신할 수 없습니다.

그다음 Actions 탭의 해당 워크플로에서 비활성 안내나 **Enable workflow** 버튼이 있는지 확인합니다. 공식 문서에는 특히 다음 조건이 명시되어 있습니다.

- 공개 저장소를 fork하면 예약 워크플로는 기본적으로 비활성화됩니다.
- 공개 저장소에서 **60일 동안 저장소 활동이 없으면** 예약 워크플로가 자동 비활성화됩니다.
- 사용자가 워크플로를 직접 비활성화한 경우에도 다시 활성화해야 합니다.

재활성화하기 전에는 그 파일이 무엇을 실행하는지 먼저 읽어봅니다. fork한 프로젝트에 배포, 알림 발송, 데이터 변경 작업이 들어 있을 수 있습니다. 의도한 작업인지 확인한 뒤 권한이 있는 계정으로 Actions → 해당 워크플로 → Enable workflow 순서로 활성화합니다.

## cron 표현식과 시간대

시간이 다르게 설정되어 있으면 아직 실행할 시간이 오지 않았는데 멈췄다고 생각하기 쉽습니다. 현재 GitHub.com 문서는 **기본 시간대가 UTC이며, `timezone`에 IANA 시간대 이름을 지정할 수도 있다**고 안내합니다. 따라서 모든 예약이 무조건 UTC로만 동작한다고 설명하는 오래된 안내와 구분해야 합니다.

예를 들어 한국 시간으로 매일 오전 9시 17분에 실행하려면 다음처럼 설정할 수 있습니다.

```yaml
on:
  schedule:
    - cron: '17 9 * * *'
      timezone: 'Asia/Seoul'
```

같은 시각을 `timezone` 없이 표현하면 `cron: '17 0 * * *'`입니다. 한국 시간 09:17은 UTC 00:17에 해당합니다. **시간대를 한국으로 지정하면서 시각까지 UTC로 바꾸면 이중으로 보정한 설정**이 되므로 두 방법 중 하나만 사용합니다.

GitHub Actions의 cron은 초 단위가 없는 다섯 필드 형식이며, 가장 짧은 지원 간격은 5분입니다. `@daily`, `@hourly`, `@reboot` 같은 별칭도 지원하지 않습니다. cron 문자열은 따옴표로 감싸고 `timezone`은 해당 `cron`과 같은 목록 항목 아래에 둡니다. 서버가 한국에 있거나 runner에 `TZ` 환경변수를 설정했다는 사실만으로 예약 시간대가 바뀌지는 않습니다.

이 예시는 GitHub.com 기준입니다. 별도로 운영하는 GitHub Enterprise Server라면 사용 중인 버전의 문서에서 `timezone` 지원 여부를 확인해야 합니다.

## 예약 지연과 계정 변경

예약 시간이 정확해도 매번 해당 분에 즉시 시작하는 것은 아닙니다. GitHub는 Actions 부하가 높은 시간에 예약 이벤트가 지연될 수 있으며, 부하가 충분히 크면 대기 중인 일부 작업이 누락될 수도 있다고 설명합니다. 특히 **매시 정각은 부하가 높은 시간대**에 포함됩니다.

정각 실행이 필수가 아니라면 `0`분 대신 다른 분으로 옮기는 것이 지연 가능성을 낮추는 방법입니다. 앞의 예제에서 17분을 사용한 이유도 이것입니다. 다만 17분이 특별히 보장된 시간이라는 뜻은 아닙니다. 정해진 시각의 실행이 중요한 업무라면 시작 시각뿐 아니라 마지막 성공 시각과 결과물 누락도 별도로 감시하는 편이 좋습니다.

한 번 늦었다는 이유로 cron을 계속 바꾸지는 않습니다. 마지막 수정 시각과 그 이후 기대한 예약 시간을 기록하고, [GitHub Status](https://www.githubstatus.com/)의 Actions 상태도 함께 확인합니다. 장애 공지가 없다는 이유만으로 개별 저장소의 예약이 정상이라고 확정할 수는 없습니다.

### Enterprise Managed Users의 actor 상태

회사에서 Enterprise Managed Users를 사용하고, 담당자 계정이 정지·삭제된 뒤 예약이 멈췄다면 워크플로와 연결된 `actor` 계정 상태도 확인할 필요가 있습니다. 공식 문서는 해당 계정이 활성 상태여야 예약이 실행된다고 명시합니다.

단순히 조직 구성원에서 빠진 경우와 계정 자체가 비활성화된 경우는 다릅니다. 기본 브랜치를 변경한 사용자, 또는 비활성 예약의 cron을 변경하는 커밋을 만든 쓰기 권한 사용자가 해당 예약의 actor가 됩니다. 계정 문제를 의심한다면 관리자와 이 변경 이력을 먼저 확인하는 것이 좋습니다.

## 외부 작업 없는 진단용 워크플로

조건을 확인했는데도 판단이 어렵다면 **기존 배포·발송 작업을 더 자주 실행하도록 바꾸기보다**, 로그만 남기는 작은 워크플로를 분리하는 편이 안전합니다. 예약이 갑자기 다시 동작했을 때 운영 작업이 반복 실행되는 상황을 피할 수 있습니다.

아래는 GitHub.com에서 사용할 진단용 예시입니다. 저장소 코드를 체크아웃하지 않고, API 호출이나 배포 없이 이벤트 종류와 UTC 시각만 출력합니다. 다만 runner를 사용하므로 저장소와 계정의 Actions 사용량·과금 조건은 적용됩니다.

본인에게 수정 권한이 있는 테스트 저장소에서 `.github/workflows/schedule-check.yml`로 추가하고, 그 저장소의 검토 절차를 거쳐 기본 브랜치에 반영합니다.

```yaml
name: Schedule check

on:
  workflow_dispatch:
  schedule:
    - cron: '17 9 * * *'
      timezone: 'Asia/Seoul'

permissions: {}

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 2
    steps:
      - name: Record trigger
        env:
          TRIGGER_EVENT: ${{ github.event_name }}
        run: |
          printf 'event=%s\n' "$TRIGGER_EVENT"
          date -u '+started_at=%Y-%m-%dT%H:%M:%SZ'
```

여기서는 새 진단용 파일 전체를 보여준 것입니다. 기존 워크플로를 수정한다면 `on:`을 파일 아래에 또 추가하지 말고 기존 이벤트 설정에 합쳐야 합니다.

확인은 두 단계로 나눕니다.

1. **수동 확인:** Actions → Schedule check → Run workflow에서 기본 브랜치를 선택합니다. 버튼을 사용하려면 기본 브랜치에 `workflow_dispatch`를 설정한 파일이 있어야 하며, 실행에는 저장소 쓰기 권한이 필요합니다. 예제대로 실행되면 로그의 이벤트 값은 `workflow_dispatch`여야 합니다.
2. **예약 확인:** 다음 예약 시간이 지난 뒤, 새 실행 기록이 생겼는지 확인합니다. 그 실행의 이벤트 값이 `schedule`인지 보고, `Record trigger` 단계가 끝났는지도 확인합니다. 수동 기록이 한 번 더 생긴 것을 예약 성공으로 세지 않습니다.

위 로그 값은 **확인해야 할 예상 값**이지, 이번 글에서 새 예약을 실행해 얻은 출력은 아닙니다. 수동 확인만 통과했다면 runner에서 해당 명령을 실행할 수 있다는 범위까지 확인한 것이고, 예약 확인은 아직 남아 있습니다. 또 별도 진단 파일의 예약이 동작한다고 기존 운영 워크플로까지 복구된 것은 아닙니다.

## 복구 확인과 문의 자료

설정을 고친 뒤에는 원래 워크플로에 **새로운 `schedule` 실행 기록이 생성되는지**, 해당 작업이 성공하는지, 필요한 결과물이 실제로 남는지를 순서대로 봅니다. 활성화 버튼을 눌렀거나 수동 실행이 성공했다는 것만으로 복구 완료라고 표시하지 않습니다.

계속 예약 기록이 없다면 토큰 권한을 무작정 늘리거나 운영 cron을 5분 간격으로 바꾸지 말고, 다음 자료를 모아 관리자나 GitHub Support에 전달하는 편이 낫습니다.

- 문제가 있는 워크플로 파일명과 기본 브랜치
- 현재 활성 상태와 cron·timezone 설정
- 마지막 변경 시각, 그 이후 놓친 예약 시각과 시간대
- 같은 파일의 수동 실행 URL, 마지막 정상 예약 실행 URL
- 예약 실행 조회 결과와 GitHub Status 확인 내용

공유 전에 로그와 YAML에 비밀값이 없는지 확인합니다. 임시 진단용 워크플로는 확인이 끝나면 비활성화하거나 삭제하고, 바꾼 테스트 주기는 원래 의도한 주기로 돌려놓습니다.

예약 문제에서 먼저 가를 것은 **실행이 만들어지지 않은 상태와, 만들어진 실행이 일을 끝내지 못한 상태**입니다. 이 둘을 구분하면 cron을 고쳐야 할지, runner와 작업 로그를 봐야 할지 훨씬 명확해집니다.
