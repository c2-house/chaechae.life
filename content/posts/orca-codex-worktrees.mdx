### 목차

## 작업 폴더를 나누는 이유

Codex로 기능을 하나 만들고 나면 확인할 일이 남습니다. 입력을 비워도 괜찮은지, 새로고침하면 데이터가 유지되는지, 모바일이나 키보드로 쓰기 불편한 부분은 없는지 살펴봐야 하죠. 이런 일을 한 대화에 계속 이어 붙이기보다, 같은 코드를 기준으로 작업을 나눠 맡기고 싶을 때가 있습니다.

**Orca는 Git 저장소의 워크트리와 에이전트 작업 화면을 함께 관리하는 데스크톱 도구**입니다. 워크트리는 하나의 저장소에 연결된 별도 작업 폴더라고 생각하면 됩니다. Git 이력은 공유하면서 파일과 브랜치를 따로 두기 때문에, 한쪽에서 파일을 수정하는 동안 다른 쪽 작업 폴더는 그대로 유지할 수 있습니다.

이번에는 Windows에서 작은 게시판을 만든 뒤 Codex 두 작업을 나눠 실행해봤습니다. 한쪽에는 수동 테스트 계획을, 다른 쪽에는 모바일·키보드 사용성에 대한 코드 검토를 맡겼습니다. 이 예제로 저장소 연결부터 작업 분리, 결과를 가져오는 순서까지 살펴보겠습니다.

## Orca와 Codex 연결

먼저 [Orca 공식 설치 페이지](https://www.onorca.dev/docs/install)에서 Windows 설치 프로그램을 받습니다. 처음 실행하면 저장소 접근과 기존 에이전트 설정 가져오기 안내가 나타납니다.

Codex를 이미 쓰고 있다면 기존 CLI와 로그인 계정을 연결하면 됩니다. 처음 사용하는 경우에는 [Codex CLI 설치 안내](https://developers.openai.com/codex/cli/)에 따라 설치하고 터미널에서 로그인한 다음, Orca의 에이전트 선택 메뉴에서 Codex를 고릅니다. [Orca의 Codex 문서](https://www.onorca.dev/docs/agents/codex)에 따르면 기본 계정은 기존 `~/.codex` 로그인을 사용합니다.

Orca는 작업 화면을 관리하고, 코드 분석과 수정은 연결한 Codex가 수행합니다. 따라서 Orca에 연결한다고 Codex의 사용 한도나 명령 실행 권한이 없어지는 것은 아닙니다. 평소 사용하는 계정과 허용할 작업 범위를 확인한 뒤 시작하면 됩니다.

## 실습용 게시판 준비

기존 Git 프로젝트가 있다면 그대로 따라 해도 됩니다. 가볍게 흐름을 익히려면 HTML, CSS, JavaScript만 사용하는 작은 게시판으로 시작하기 좋습니다. 예를 들어 Codex에 다음처럼 요청할 수 있습니다.

```text
HTML, CSS, JavaScript로 작은 게시판을 만들어줘.
제목과 내용이 있는 글을 등록하고 삭제할 수 있게 해줘.
새로고침 후에도 같은 브라우저에 글이 남도록 localStorage를 사용하고,
빈 입력을 막아줘. index.html을 직접 열어 실행할 수 있게 만들어줘.
```

파일이 만들어지면 게시판을 열어 기본 동작을 확인한 뒤 기준 커밋을 남깁니다. 아래 명령은 **실습용 폴더의 터미널**에서 실행하는 예시입니다. 파일명은 실제 생성된 이름에 맞춰 바꾸면 됩니다.

```powershell
git init
git add index.html styles.css app.js
git commit -m "Create board"
```

이렇게 커밋을 남겨두면 두 작업을 같은 코드에서 출발시킬 수 있습니다. 기존 프로젝트를 사용한다면 진행 중인 변경을 먼저 정리하고, 이번 작업의 출발점으로 삼을 브랜치나 커밋을 고릅니다.

## 테스트 계획과 사용성 검토

Orca의 **프로젝트 추가**에서 게시판 저장소를 등록합니다. 이어 **새 작업 트리 만들기**에서 시작 기준을 지정하고, 작업 이름을 각각 `게시판 테스트 작성`과 `게시판 사용성 검토`로 정합니다. 두 작업 모두 앞서 남긴 같은 커밋에서 시작하고 에이전트로 Codex를 선택합니다.

[생성 화면 원본 크게 보기](/images/blog/orca-codex-worktrees/create-worktree.png)

이름만 다르게 붙인 대화 두 개와는 차이가 있습니다. **각 작업이 별도의 폴더와 브랜치를 사용**하므로 테스트 문서를 작성하는 쪽과 사용성을 검토하는 쪽의 파일 변경이 섞이지 않습니다. 사이드바에서 작업을 선택하면 해당 작업의 대화와 파일을 이어서 볼 수 있습니다.

테스트 쪽에는 확인할 기능과 결과물을 함께 지정했습니다. 같은 범위로 요청하려면 다음처럼 적으면 됩니다.

```text
이 게시판의 글 등록과 삭제, 새로고침 후 저장 유지,
빈 입력 차단을 확인할 수 있는 수동 테스트 계획을 작성해줘.
tests/test-plan.md에 문서만 만들고 다른 파일은 수정하거나 커밋하지 마.
```

사용성 쪽에는 수정 대신 코드 검토를 요청했습니다. 아래는 같은 범위의 요청 예시입니다. 두 작업 모두 문서를 만드는 데 범위를 한정하면, 처음 병렬 작업을 시도할 때 변경 내용을 비교하기 쉽습니다.

```text
현재 코드를 읽고 모바일 화면과 키보드 사용성을 검토해줘.
브라우저 도구는 사용하지 말고 코드로 판단할 수 있는 문제와
실제 화면에서 확인할 항목을 나눠 설명해줘.
docs/mobile-keyboard-review.md에 문서만 만들고
앱 코드를 수정하거나 커밋하지 마.
```

요청을 나누는 기준은 에이전트 수보다 **서로 다른 질문**입니다. 테스트 작업은 `어떤 입력과 순서로 기능을 확인할까`, 사용성 작업은 `쓰는 과정에서 어디가 불편할까`에 답하도록 한 셈입니다.

## 두 작업의 결과 활용

테스트 쪽에서는 `tests/test-plan.md`, 사용성 쪽에서는 `docs/mobile-keyboard-review.md`가 만들어졌습니다. 같은 게시판을 보더라도 결과를 활용하는 방법은 다릅니다.

테스트 계획은 기능을 확인할 순서를 정할 때 유용합니다. 글을 등록하고 새로고침한 뒤 그대로 남는지, 삭제한 글이 다시 나타나지 않는지, 빈 입력을 어떻게 처리하는지 확인할 수 있습니다. **계획 문서가 생겼다고 테스트가 실행된 것은 아니므로**, 실제 확인 결과는 따로 남기면 됩니다. 이번 게시판에서도 등록한 글의 새로고침 후 유지와 삭제 후 저장 상태를 브라우저에서 확인했습니다.

사용성 검토에서는 삭제를 되돌릴 수단, 저장 결과를 알리는 위치 같은 개선 후보가 나왔습니다. 바로 코드를 고치기 전에 무엇을 먼저 개선할지 정하는 데 쓸 수 있는 내용입니다. 다만 코드만 읽은 검토이므로 화면 크기에 따른 배치, 실제 키보드 이동과 스크린 리더 동작은 브라우저나 기기에서 이어서 확인해야 합니다.

`localStorage`의 저장 내용은 다른 기기나 브라우저에 공유되지 않습니다. 특히 `index.html`을 `file://`로 직접 여는 예제는 브라우저에 따라 저장 동작이 다를 수 있으니, 같은 브라우저와 파일 경로에서 먼저 확인하는 편이 좋습니다.

## 변경 검토와 통합

작업이 끝나면 각 워크트리에서 생성되거나 바뀐 파일을 먼저 봅니다. Orca의 변경 비교 화면에서는 시작 기준과 현재 변경을 비교할 수 있습니다. 요청한 문서 외에 앱 코드도 바뀌었는지, 두 결과가 같은 문제를 중복해서 다루고 있지는 않은지 살펴보면 됩니다.

이번 예제는 서로 다른 새 문서 두 개였기 때문에 내용을 읽고 원본 프로젝트로 복사해 모았습니다. 구현 파일을 수정하는 작업이라면 각 브랜치의 변경을 검토한 뒤 Git 병합이나 PR로 통합하는 흐름이 더 적합합니다. 같은 파일을 고쳤다면 충돌을 해결하고, 합쳐진 코드에서 테스트도 다시 실행해야 합니다.

워크트리는 작업 공간을 나누는 기능입니다. **어떤 변경을 최종 코드에 넣을지 결정하고 통합하는 과정은 따로 남습니다.** 결과를 확보한 뒤에 워크트리를 정리하는 순서로 진행하세요. [Orca의 워크트리 문서](https://www.onorca.dev/docs/model/worktrees)는 삭제 시 작업 폴더와 브랜치도 제거하는 흐름을 설명하므로, 남길 변경과 커밋을 먼저 확인하는 것이 좋습니다.

## 병렬 작업에 맞는 조합

Orca에서 편했던 부분은 서로 다른 검토를 한 저장소에 연결해두고, 작업 화면을 오가며 결과를 볼 수 있다는 점입니다. 이번처럼 코드가 준비된 상태에서 테스트 계획과 사용성 검토를 나누거나, 독립적인 기능 후보를 비교하는 작업에 잘 맞습니다.

반대로 한쪽 구현이 끝나야 다른 쪽 검토를 시작할 수 있다면 순서를 두는 편이 낫습니다. 아직 없는 기능을 기준으로 검토를 맡기거나 같은 파일을 여러 작업에서 크게 바꾸면, 나중에 결과를 맞추는 일이 더 늘어날 수 있습니다.

처음에는 `테스트 계획`과 `코드 검토`처럼 서로 겹치지 않는 작은 작업 두 개부터 시작해보면 좋겠습니다. 결과를 읽고 통합하는 흐름에 익숙해진 뒤, 실제 구현이나 더 큰 변경으로 넓혀가는 방식입니다.
