Vercel에서 API 주소를 바꾸고 저장했는데 앱은 여전히 이전 서버로 요청을 보낼 때가 있습니다. 재배포까지 했는데 그대로라면 캐시부터 지워야 할까요? 먼저 **수정한 프로젝트와 환경, 새로 만들어진 배포, 지금 접속한 주소가 서로 맞는지** 확인하는 편이 좋습니다.

[Vercel 공식 문서](https://vercel.com/docs/environment-variables/managing-environment-variables)에 따르면 환경변수 변경은 기존 배포를 수정하는 것이 아니라 **새 배포에 적용**됩니다. 여기에 Next.js의 `NEXT_PUBLIC_` 변수는 빌드할 때 브라우저용 코드에 값이 들어간다는 조건이 더해집니다. 설정 저장과 실행 중인 앱의 값 변경을 같은 일로 생각하면 헷갈리기 쉽습니다.

이 글은 2026년 9월 25일 확인한 Vercel·Next.js 공식 문서를 바탕으로 한 점검 안내입니다. Git 연동으로 Next.js 앱을 배포하는 상황을 중심으로 설명하며, 운영 프로젝트의 설정을 변경해 오류를 해결한 후기는 아닙니다. 실제 수정은 해당 프로젝트의 설정·배포 권한이 있는 계정에서 진행해야 합니다.

## 프로젝트와 배포 환경 확인

환경변수를 고치기 전에, 문제가 발생한 사이트가 어느 Vercel 프로젝트의 배포인지부터 확인합니다. 같은 Git 저장소로 운영용·테스트용 프로젝트를 각각 만들었다면 프로젝트 이름이 비슷해도 설정은 다를 수 있습니다.

1. 문제가 발생한 사이트 주소를 기록합니다.
2. Vercel Dashboard에서 해당 팀과 프로젝트를 선택합니다.
3. **Deployments**에서 문제가 발생한 배포를 열어 환경, Git 브랜치와 커밋을 확인합니다.
4. 같은 프로젝트의 **Environment Variables**를 열고 코드가 읽는 변수 이름을 찾습니다.
5. 그 변수가 어느 환경과 브랜치에 적용되는지 대조합니다.

[Vercel의 환경변수 문서](https://vercel.com/docs/environment-variables)는 기본 적용 대상을 다음처럼 구분합니다.

| 적용 대상 | 사용하는 곳 | 흔히 혼동하는 부분 |
| --- | --- | --- |
| Production | 운영 환경의 새 배포 | Production Branch가 반드시 `main`인 것은 아닙니다. |
| Preview | 미리보기 환경의 새 배포 | Production 값만 바꿔도 Preview 값이 바뀌는 것은 아닙니다. |
| Development | 로컬 개발 환경 | 로컬 `.env.local` 수정이 운영 설정으로 자동 업로드되지는 않습니다. |

Custom Environment를 사용한다면 그 환경에 적용된 값도 별도로 확인합니다. **브랜치 이름이 `staging`이라고 배포 환경까지 자동으로 같은 의미가 되는 것은 아닙니다.** 이름으로 추측하지 말고 해당 배포에 표시된 환경을 기준으로 보세요.

### Preview 브랜치별 설정

Preview에서는 특정 브랜치에만 적용하는 환경변수를 지정할 수 있습니다. 공식 문서에 따르면 **같은 이름의 브랜치별 변수는 일반 Preview 변수보다 우선**합니다.

예를 들어 전체 Preview의 API 주소를 바꿨는데 `feature/search` 브랜치에만 예전 주소가 따로 등록돼 있다면, 그 브랜치의 배포는 별도 값을 사용합니다. 이때 일반 Preview 설정을 반복해서 수정해도 원하는 결과가 나오지 않습니다.

Environment Variables에서 환경 필터와 브랜치 조건을 확인하고, 필요한 항목만 수정합니다. 문제를 빨리 없애려고 운영 DB 키를 모든 Preview에 똑같이 넣지는 마세요. 테스트 배포가 운영 데이터에 접근하는 문제가 생길 수 있습니다.

## 환경변수 저장과 새 배포

수정할 항목을 찾았다면 변경 전 설정을 비공개로 기록한 뒤 필요한 값과 적용 환경을 저장합니다. 비밀키는 공개 문서나 AI 대화에 복사하지 않고, 팀이 사용하는 안전한 저장소에서 관리해야 합니다.

그다음은 **해당 변경 이후에 만들어진 배포**가 필요합니다. **Production 재배포는 완료 시 운영 도메인에 바로 반영될 수 있습니다.** 운영 반영 전에 검증해야 한다면 프로젝트에서 사용하는 사전 검증·승인 절차를 먼저 따르세요. 아래에서 새 배포 URL을 먼저 확인하는 것은 확인 순서이며, 운영 반영을 보류하는 절차는 아닙니다.

Vercel의 [배포 관리 문서](https://vercel.com/docs/deployments/managing-deployments#redeploy-a-project)가 안내하는 Dashboard 경로는 다음과 같습니다.

1. 같은 프로젝트의 **Deployments**를 엽니다.
2. 다시 배포할 코드의 커밋과 환경이 맞는 배포를 고릅니다.
3. 점 세 개 메뉴에서 **Redeploy**를 선택합니다.
4. 확인창에서 대상 환경과 Build Cache 사용 여부를 확인하고 재배포합니다.
5. 새 배포의 상태와 빌드 로그를 확인합니다. 실패했다면 기존 사이트를 새 설정이 적용된 결과로 판단하지 않습니다.

Git 연동으로 새 커밋을 배포하는 방법도 있지만, 값을 바꿨다는 이유만으로 빈 커밋을 만들 필요는 없습니다. 반대로 **예전 코드의 배포를 골라 Redeploy한 뒤 최신 코드가 반영됐다고 생각해서도 안 됩니다.** 확인할 것은 환경변수뿐 아니라 그 배포의 소스 커밋입니다.

캐시를 사용하지 않는 재배포는 원인을 좁힐 때 선택할 수 있습니다. 다만 프로젝트나 적용 환경이 틀렸다면 캐시를 지워도 해결되지 않습니다. 무작정 여러 번 재배포하기보다 설정과 배포의 대응부터 맞추는 편이 낫습니다. 빌드 반복에는 프로젝트의 사용량과 시간이 들기 때문입니다.

## Next.js 공개 변수의 빌드 시점

Vercel의 배포 설정과 Next.js가 값을 읽는 방식은 구분해야 합니다. [Next.js 환경변수 가이드](https://nextjs.org/docs/app/guides/environment-variables#bundling-environment-variables-for-the-browser)는 `NEXT_PUBLIC_`로 시작하는 변수를 브라우저용 JavaScript에 빌드 시점의 값으로 넣는다고 설명합니다.

예를 들어 앱이 `process.env.NEXT_PUBLIC_API_URL`을 직접 참조한다면, `next build`를 실행할 때의 값이 코드에 들어갑니다. **이미 빌드한 결과물에 나중에 환경변수만 다르게 전달해도 그 공개 값이 다시 바뀌지는 않습니다.** 브라우저 새로고침도 오래된 번들 안의 값을 새 설정으로 치환해주지는 않습니다.

따라서 Vercel에서 새 값으로 다시 빌드·배포하고, 그 결과물을 여는지 확인해야 합니다. GitHub Actions 등에서 미리 빌드한 산출물을 배포하는 구조라면 Vercel Dashboard뿐 아니라 **실제로 빌드가 실행된 CI 환경**도 조사 대상입니다.

### 변수 이름과 참조 방식

코드가 `NEXT_PUBLIC_API_URL`을 읽는데 Dashboard에는 `API_URL`만 등록했다면 같은 변수가 아닙니다. 이름과 대소문자를 정확히 대조합니다. 값이 없을 때 예전 주소를 기본값으로 사용하는 코드도 찾아보세요. 정상처럼 보이는 이전 주소가 사실은 환경변수 누락 때 사용하는 대체 값일 수 있습니다.

또한 공식 문서는 `process.env[varName]`처럼 이름을 변수로 전달하거나, `process.env`를 다른 변수에 담아 조회하는 방식은 공개 변수의 빌드 인라인 대상이 아니라고 설명합니다. 브라우저 코드에서 읽히지 않는다면 접두사만 볼 것이 아니라 **변수에 접근하는 코드 형태**도 확인해야 합니다.

### 공개 값과 서버 비밀값

`NEXT_PUBLIC_`는 문제를 해결하는 만능 접두사가 아닙니다. 브라우저에서 읽히지 않는다고 서버 API 키에 이 접두사를 붙이면 비밀값을 클라이언트에 노출할 수 있습니다.

공개돼도 되는 API의 기본 주소와, 서버만 보관해야 하는 인증키는 다릅니다. 서버 비밀값은 서버 코드에서 사용하고, 확인을 위해 응답이나 화면에 출력하지 않습니다. 서버 변수를 쓰더라도 정적 페이지 생성 중 읽은 값이라면 결과물에 그때의 정보가 반영될 수 있으므로, 실제 코드가 빌드 중 실행되는지 요청 시 실행되는지도 확인해야 합니다.

그리고 서버가 요청 시점에 환경변수를 읽는 구조라고 해서 **Vercel의 기존 배포가 Dashboard 변경을 자동으로 따라가는 것은 아닙니다.** 환경변수 변경에는 새 배포가 필요하다는 Vercel의 규칙은 별개로 적용됩니다.

## 새 배포 URL과 운영 도메인

새 배포가 정상이어도 지금 보고 있는 사이트가 그 배포가 아닐 수 있습니다. Vercel Dashboard에서 **방금 완료된 배포의 URL을 직접 열어 먼저 확인**하고, 그다음 평소 사용하는 운영 도메인에서도 같은 동작을 확인합니다.

예를 들어 새 배포 URL에서는 새 API로 요청을 보내는데 `example.com`에서는 예전 API로 보낸다면, 환경변수 값을 다시 바꾸기 전에 운영 도메인이 가리키는 배포부터 확인해야 합니다. 공유받은 과거 배포 URL을 계속 열고 있는 경우도 구분할 수 있습니다.

특히 최근 Instant Rollback을 사용했다면 추가 확인이 필요합니다. [Vercel의 Rollback 문서](https://vercel.com/docs/instant-rollback)는 이전 빌드로 되돌릴 때 현재 프로젝트 설정의 환경변수로 업데이트하지 않는다고 설명합니다. 또한 롤백 이후에는 운영 도메인의 자동 할당이 꺼져 새 Production 배포가 생겨도 바로 운영 도메인에 연결되지 않을 수 있습니다.

이 경우 배포를 계속 만드는 것보다 현재 롤백 상태와 도메인 연결을 먼저 확인합니다. 정상 검증한 배포를 운영에 반영할 때는 프로젝트의 배포 권한·승인 흐름에 따라 **Undo Rollback**을 진행합니다. 프로젝트 개요의 Production Deployment에서 해당 버튼을 누르고 검증한 배포를 선택해 확인하는 절차입니다. **선택한 배포의 운영 반영과 함께 이후 Production Branch push의 운영 도메인 자동 할당도 다시 활성화**된다는 점에 주의해야 합니다.

DB 비밀번호나 외부 API 키를 이미 폐기했다면 이전 앱으로 돌아가는 것만으로 그 자격증명이 복구되지는 않습니다.

## 관찰 결과별 다음 행동

다음 표는 하나의 원인을 확정하는 목록이 아닙니다. 이미 확인한 단계를 반복하지 않고 다음 조사 위치를 고르기 위한 기준입니다.

| 관찰한 상황 | 먼저 확인할 곳 | 다음 행동 |
| --- | --- | --- |
| 값을 저장했지만 새 배포가 없음 | 변경 시각과 배포 목록 | 의도한 코드·환경으로 새 배포 생성 |
| Production은 정상, Preview만 이전 값 | Preview 환경과 브랜치별 변수 | 해당 브랜치에 우선 적용되는 값 대조 |
| 새 배포 URL은 정상, 운영 도메인만 이전 동작 | 도메인 연결과 롤백 상태 | 운영 도메인이 가리키는 배포 확인 |
| 서버 동작은 바뀌었지만 브라우저 요청 주소는 이전 값 | 공개 변수와 브라우저 번들 | 빌드 시점의 값·참조 방식·접속 배포 확인 |
| 새 배포도 변수가 없다고 판단 | 변수 이름·실행 위치·기본값 코드 | 이름 일치와 빌드·서버·브라우저 구분 |
| 배포는 정상인데 로컬만 이전 값 | 로컬 환경 파일과 실행 중인 프로세스 | 로컬 값을 대조하고 개발 서버 재시작 |

로컬 Next.js에서 같은 변수를 여러 곳에 넣었다면 [공식 로드 순서](https://nextjs.org/docs/app/guides/environment-variables#environment-variable-load-order)도 확인합니다. 이미 프로세스에 설정된 값이 `.env` 파일보다 우선이고, `.env.local` 등 더 높은 우선순위의 파일도 영향을 줄 수 있습니다. `.env` 하나만 수정한 뒤 모든 실행 환경이 바뀌었다고 판단하면 안 됩니다.

프로젝트·환경·새 배포가 모두 맞는데도 이전 동작이 남는다면 앱의 데이터 캐시, Service Worker, 별도 설정 저장소나 요청을 중계하는 서버도 확인할 차례입니다. **이전 결과가 보인다는 사실만으로 환경변수가 이전 값이라고 단정하지는 마세요.** 앱이 새 설정을 읽어도 이미 저장된 데이터를 보여주는 상황은 별도의 문제입니다.

## 비밀값 없는 완료 확인

가장 좋은 확인은 설정 화면을 한 번 더 보는 것이 아니라 **해당 변수를 쓰는 기능을 새 배포에서 확인하는 것**입니다. 다만 비밀키를 출력하는 디버그 API를 공개해서 확인할 필요는 없습니다.

공개 API 주소를 바꾼 경우에는 Chrome·Edge 개발자 도구의 **Network** 탭을 열고, 관련 기능을 실행해 요청의 목적지 호스트와 경로를 확인할 수 있습니다. 앱이 자체 서버를 경유한다면 브라우저에는 자체 서버 주소만 보일 수 있으므로 서버 쪽 로그와 기능 결과를 함께 봅니다.

서버 키는 값 자체가 아니라 **설정 존재 여부, 필요한 권한의 정상 동작, 오류 종류**로 확인합니다. 예를 들어 승인된 테스트 계정으로 필요한 조회를 수행하고 성공 여부를 확인하는 방식입니다. 존재 여부만 `true`라고 올바른 키인 것은 아니며, 확인 과정에서 과금이나 데이터 쓰기가 발생하는 기능은 사전 승인된 안전한 테스트 범위로 제한해야 합니다.

완료 기록에는 다음 정도를 남기면 원인을 다시 추적하기 쉽습니다.

- **설정 대상:** 프로젝트, 환경, 브랜치와 변수 이름. 비밀값 원문은 제외합니다.
- **적용 대상:** 변경 뒤 생성된 배포 식별자와 소스 커밋, 배포 완료 상태.
- **확인 위치:** 새 배포 URL과 운영 도메인 각각에서 확인했는지 여부.
- **기능 결과:** 의도한 목적지나 동작, 남은 오류와 확인 시각.

Network 요청 전체나 HAR 파일에는 쿠키·토큰이 담길 수 있습니다. 공개 이슈나 AI에게 질문할 때는 민감한 쿼리·헤더·연결 문자열을 제거하세요. 점검을 위해 추가한 임시 로그도 확인 뒤 정리합니다.

변경 후 문제가 생겼다면 값을 계속 덮어쓰기 전에 원래 설정과 정상 배포로 복구 가능한지 확인합니다. 비밀키 교체가 함께 있었다면 제공업체 쪽 키 상태까지 고려해야 합니다. 같은 조건의 새 배포에서도 문제가 지속되면 위 기록과 민감정보를 제거한 로그를 모아 지원팀에 전달하는 편이 무작정 재배포를 반복하는 것보다 도움이 됩니다.

결국 확인할 것은 **어디에 저장했는지, 어떤 값으로 새 배포를 만들었는지, 어느 배포를 보고 있는지**입니다. 이 세 가지를 구분하면 캐시 문제로 단정하기 전에 설정이 어긋난 지점을 훨씬 좁힐 수 있습니다.
