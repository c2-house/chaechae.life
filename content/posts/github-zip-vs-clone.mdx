### 목차

## 파일만 받을 때와 계속 개발할 때

GitHub에서 예제 프로젝트를 받으려고 **Code**를 누르면, 저장소 주소와 **Download ZIP**이 같은 메뉴에 보입니다. ZIP을 풀어도 소스 파일이 나오고 `git clone`을 실행해도 비슷한 폴더가 생깁니다. 그렇다면 그냥 편한 쪽을 고르면 될까요?

**파일을 한 번 받아 읽거나 활용하려면 ZIP, 원본의 변경사항을 받아오고 내 수정 이력을 관리하려면 clone**이 기본 선택입니다. ZIP은 특정 시점의 파일 묶음이고, 일반적인 clone은 파일뿐 아니라 Git 이력과 원격 저장소 연결도 준비합니다.

## ZIP과 clone의 관리 범위

[GitHub의 다운로드 안내](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-files-from-github)는 Download, Clone, Fork를 서로 다른 작업으로 구분합니다. 여기서 저장소는 프로젝트 파일과 변경 이력을 관리하는 공간이고, 커밋은 그 이력의 한 시점이라고 생각하면 됩니다.

| 비교 항목 | Download ZIP | 일반적인 git clone |
| --- | --- | --- |
| 받는 대상 | 선택한 시점의 파일 스냅샷 | 작업 파일과 Git 저장소 데이터 |
| 이전 커밋 이력 | 포함하지 않음 | 기본적으로 가져옴 |
| 원격 주소 설정 | 없음 | 보통 `origin`으로 설정 |
| 로컬 파일 편집 | 가능 | 가능 |
| Git으로 원본 변경 가져오기 | 압축 해제만으로는 불가 | fetch·pull을 사용할 기반 마련 |
| 받기 위한 준비 | 웹 브라우저와 압축 해제 | Git 또는 Git을 지원하는 도구 |

이 표는 `--depth` 같은 제한 옵션이 없는 일반적인 clone 기준입니다. 이력을 일부만 가져오는 shallow clone 등은 범위가 다릅니다. 또 clone한다고 GitHub의 이슈·PR·계정 권한까지 내 컴퓨터에 복제되는 것은 아닙니다.

**Fork는 내 GitHub 계정 쪽에 별도 저장소를 만드는 작업**입니다. 컴퓨터에 폴더를 받는 clone과는 다릅니다. 원본에 수정안을 제안하려고 fork한 뒤, 그 fork를 내 컴퓨터에 clone하는 흐름도 가능합니다.

### ZIP으로 파일 받기

1. 받을 저장소의 파일 목록을 엽니다.
2. 파일 목록 위의 브랜치 선택기에서 필요한 브랜치를 확인합니다. 예제 화면은 `main`입니다.
3. **Code → Download ZIP**을 선택합니다.
4. 내려받은 압축파일을 **기존 작업 폴더와 다른 위치에** 풉니다.
5. 압축 해제된 실제 프로젝트 폴더를 열고 `README.md`와 필요한 파일이 있는지 확인합니다.

브랜치의 ZIP을 나중에 다시 받으면, 그동안 브랜치가 바뀌어 다른 파일을 받을 수 있습니다. [GitHub의 소스 아카이브 문서](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives)도 브랜치·태그가 가리키는 커밋이 달라질 수 있다고 설명합니다. 같은 자료를 다시 확인해야 한다면 **저장소 주소뿐 아니라 받은 커밋이나 버전도 기록**하는 편이 좋습니다.

### clone으로 작업 폴더 만들기

Git이 설치된 환경에서, 프로젝트를 둘 **상위 폴더**를 터미널로 엽니다. 기존 Git 프로젝트 안보다는 별도 실습 폴더에서 시작하세요. Windows에서는 Git Bash 등을 사용할 수 있습니다. 먼저 다음 명령이 버전을 출력하는지 확인합니다.

```bash
git --version
```

이어서 공개 예제 저장소를 새 폴더에 받습니다. 아래 `Spoon-Knife-clone`은 생성할 폴더 이름입니다. 같은 이름의 작업 폴더가 이미 있다면 덮어쓰려 하지 말고 다른 이름을 사용합니다.

```bash
git clone https://github.com/octocat/Spoon-Knife.git Spoon-Knife-clone
cd Spoon-Knife-clone
git status
git remote -v
git log --oneline -3
```

다른 프로젝트라면 Code 메뉴에서 복사한 HTTPS 주소로 바꾸면 됩니다. `git status`에 현재 브랜치와 작업 상태가 나오고, `git remote -v`에 의도한 저장소 주소가 표시되는지 확인하세요. `git log`에서는 가져온 커밋 이력을 볼 수 있습니다.

`origin`은 원격 저장소 주소에 붙인 기본 이름입니다. `git remote -v`에 `(push)` 주소가 보이더라도 **그 저장소에 쓸 권한을 받았다는 뜻은 아닙니다.** 공개 저장소를 읽어오는 것과 다른 사람의 저장소에 변경을 올리는 권한은 별개입니다. 비공개 저장소는 내려받을 때부터 해당 저장소의 접근 권한과 인증이 필요합니다.

## 같은 커밋으로 확인한 결과

Windows 11 빌드 26200과 Git `2.54.0.windows.1`에서 같은 커밋 `d0dd1f61b33d64e29d8bc1372a94ef6a2fee76a9`의 ZIP과 clone을 비교했습니다. 파일 내용은 줄바꿈 자동 변환을 끈 상태에서 대조했습니다.

| 확인 항목 | ZIP 압축 해제 폴더 | clone 폴더 |
| --- | --- | --- |
| README.md·index.html·styles.css | clone 쪽과 세 파일의 바이트 내용 일치 | ZIP 쪽과 세 파일의 바이트 내용 일치 |
| `.git` 디렉터리 | 없음 | 있음 |
| `git status` | Git 저장소가 아니라는 오류 | `main`, 변경사항 없음 |
| 이전 커밋 확인 | 원본 이력 없음 | 최근 커밋 3개 확인 |
| 원격 연결 | 없음 | `origin`에 원본 HTTPS 주소 설정 |

ZIP 쪽에서 `git status`를 실행했을 때 실제로 나온 메시지는 다음과 같습니다.

```text
fatal: not a git repository (or any of the parent directories): .git
```

압축을 푼 폴더에는 Git 이력을 저장하는 `.git` 디렉터리가 없습니다. clone한 폴더에서는 아래 이력을 조회할 수 있었습니다.

```text
d0dd1f6 Pointing to the guide for forking
bb4cc8d Create styles.css and updated README
a30c19e Created index page for future collaborative edits
```

파일 단위로 대조해야 한다면 커밋과 함께 Git 줄바꿈·필터 설정, Git LFS 파일과 submodule 포함 여부를 확인하세요.

## 이미 ZIP에서 수정한 파일의 처리

ZIP을 풀어 작업하다가 Git을 쓰고 싶어졌다면, **기존 폴더를 보관하고 새 폴더에서 시작**하세요.

원본 프로젝트의 이력을 이어가려는 경우에는 다음 순서가 이해하기 쉽습니다.

1. 수정한 ZIP 폴더를 별도로 백업합니다.
2. 원본 저장소를 **다른 새 폴더에 clone**합니다.
3. 처음 받았던 버전과 새 clone의 버전 차이를 확인합니다. 기준 버전을 모르면 비교가 더 어려울 수 있습니다.
4. 자신이 바꾼 파일을 비교하면서 필요한 변경만 옮깁니다. `.git`이나 비밀값이 담긴 환경 파일을 통째로 복사하지 않습니다.
5. 새 clone 폴더에서 `git status`로 변경 파일을 확인하고, 편집기의 비교 화면 등으로 의도한 수정만 남았는지 검토합니다.

원본도 그동안 같은 파일을 고쳤다면, 내 파일 전체를 복사하는 순간 원본의 새 수정을 덮어쓸 수 있습니다. 이 경우에는 파일별 차이를 확인하고 필요한 부분을 합쳐야 합니다. 원본 버전이나 변경 내용을 알 수 없다면 백업을 유지한 채 비교부터 하는 편이 안전합니다.

ZIP 폴더에서 `git init`만 실행하면 해결되는지도 별도 사본으로 확인했습니다. 새 Git 저장소는 만들어졌지만 `git remote -v`는 비어 있었고, `git log`에는 아직 커밋이 없다는 오류가 나왔습니다. **git init은 새 이력을 시작하는 명령이지 원본 GitHub 이력을 복원하는 명령이 아닙니다.**

원본과의 연결이 필요 없는 독립 프로젝트를 만들려는 목적이라면 새 저장소로 시작할 수 있습니다. 다만 코드의 이용·수정·배포는 해당 프로젝트의 라이선스를 확인해야 합니다. ZIP 다운로드나 clone은 이용 허락의 범위를 넓혀주지 않습니다.

## 업데이트와 프로그램 설치의 구분

clone한 폴더도 원본과 저절로 실시간 동기화되지는 않습니다. Git에서는 **fetch로 원격의 변경 정보를 가져오고, pull로 가져온 변경을 현재 브랜치에 통합**할 수 있습니다. 통합 방식과 충돌 여부는 설정과 로컬 작업 상태에 따라 달라집니다.

pull을 실행하기 전에 현재 브랜치와 변경 파일을 확인하세요. 원격 변경을 먼저 살펴보려면 [Git 실전 팁의 fetch 설명](/blog/git-advanced-tips)을 참고하세요.

한편 목적이 개발이 아니라 **프로그램을 설치해서 사용하는 것**이라면, ZIP과 clone 둘 다 원하는 답이 아닐 수 있습니다. 저장소의 `README`에 있는 설치 안내나 **Releases**의 배포 파일을 먼저 확인합니다.

- `Code → Download ZIP`은 선택한 소스 파일을 받는 경로입니다.
- Releases의 `Source code (zip)`은 해당 버전의 소스 코드 아카이브입니다.
- 개발자가 별도로 올린 설치 파일·실행 파일이 있다면, 해당 릴리스의 설명과 지원 OS·CPU 종류를 확인해 선택합니다.

GitHub의 [Releases 안내](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)는 릴리스에 소프트웨어와 바이너리 파일을 함께 제공할 수 있다고 설명합니다. 모든 프로젝트가 실행 파일을 올리는 것은 아니며, 예제로 쓴 Spoon-Knife에는 확인 당시 공개 릴리스가 없었습니다. 소스만 제공하는 프로젝트라면 별도의 개발 환경과 빌드가 필요할 수 있습니다.

설치 스크립트를 실행하기 전에는 공식 프로젝트 주소와 README의 실행 절차·필요 권한을 확인하세요.
