AI에게 문서를 찾아달라고 했을 때 링크만 받는 것과, 실제 페이지를 열어 검색하고 필요한 항목까지 가져오는 것은 다릅니다. **ego(lite)는 내가 사용하는 에이전트가 웹페이지를 읽고 조작할 수 있게 해주는 Chromium 브라우저**입니다. 브라우저에 질문만 던지는 방식이 아니라, 로컬 명령을 실행할 수 있는 에이전트와 연결해 씁니다.

이번에는 Windows에서 ego(lite)를 실행하고 **Python 공식 문서 검색 → 결과 링크 열기 → 메서드 세 개의 설명과 출처 수집**을 해봤습니다. 검색창에 값을 넣고 버튼을 누르는 조작부터 원문 확인까지 실제로 수행했습니다. 로그인이나 결제 없이 시작할 수 있는 공개 자료 조사입니다.

확인일은 2026년 10월 21일이며, 설치된 브라우저 실행 파일 버전은 **0.6.0.16**, `ego-browser skill`이 출력한 사용 가이드 버전은 **2.1.0**이었습니다. 가이드 버전과 브라우저 버전은 다릅니다. 실행에는 Hermes에서 ego의 공식 CLI를 사용했고, 개인 계정 페이지나 가져온 로그인 정보를 이용하는 작업은 하지 않았습니다.

## 설치 후 에이전트 연결

[Windows 빠른 시작](https://lite.ego.app/document/en/docs/windows/quick-start)의 흐름은 브라우저 설치, 초기 설정, 에이전트 연결 순서입니다. 현재 Windows 다운로드에는 beta 표시가 있습니다. 설치 과정에서 다른 브라우저의 데이터를 가져오는 옵션이 나오더라도, **공개 문서 검색을 위해 기존 비밀번호나 쿠키를 가져올 필요는 없습니다.**

여기서 한 번 막혔습니다. 설치된 CLI가 있어도 초기 설정을 끝내기 전에는 `Please complete the onboarding process first`라는 안내만 반환했습니다. 명령의 종료 코드는 0이었지만 페이지를 연 결과는 없었습니다. 설치 성공과 사용 준비 완료를 따로 확인해야 하는 이유입니다.

초기 설정을 마친 뒤에는 실제 앱에서 아래의 환영 화면이 보였고, CLI로 만든 작업 공간에 공개 페이지를 열어 내용을 읽을 수 있었습니다. **환영 화면만 보는 것보다, 에이전트가 URL과 페이지 내용을 반환하는지까지 확인하는 편이 확실합니다.**

<Image src="/ego-lite-public-research/01-ready.png" alt="Windows ego(lite)의 초기 설정 완료 후 환영 화면과 에이전트 연결 안내" caption="출처: ego(lite) 0.6.0.16 Windows 앱, 2026년 10월 21일 직접 캡처. 초기 설정 뒤 에이전트 연결 안내가 표시된 상태입니다." />

연결된 에이전트는 먼저 `ego-browser skill`로 설치 버전에 맞는 사용법을 읽습니다. 공식 저장소는 설치 과정에서 에이전트의 skills 디렉터리에 `ego-browser`가 추가된다고 안내합니다. 에이전트가 이를 찾지 못한다면 초기 설정 완료 여부와 에이전트 재시작부터 확인하세요. 회사에서 관리하는 PC라면 PATH 등록과 스킬 추가도 설치 검토 범위에 포함하는 것이 좋습니다.

작업용 탭은 **Space**에 모입니다. 이번 실행에서는 `ego-lite-public-web-review`라는 작업 공간이 생성됐고 ID는 1이었습니다. 이후 명령에서도 같은 ID와 `p1` 탭을 다시 사용해 검색과 본문 열기를 이어갔습니다. 매 단계마다 새 브라우저를 시작하지 않아도 페이지 상태가 이어졌습니다.

다만 Space를 보안 격리 공간으로 이해하면 안 됩니다. [공식 설명](https://lite.ego.app/document/en/docs/windows/product-introduce)은 작업 탭을 나누는 기능이며, ego에 로그인된 사이트를 활용할 수 있다고 안내합니다. **작업 화면의 분리와 계정 접근 권한의 분리는 다른 문제**입니다.

공식 Codex 예시에는 Full access 설정이 등장하지만, 이를 모든 에이전트에서 무조건 켜야 하는 일반 절차로 옮기지는 않겠습니다. 이번 실행에서는 에이전트의 접근 모드를 확대하지 않았습니다. 사용하는 에이전트에서 필요한 로컬 명령 실행 권한을 검토하고, 허용할 사이트와 중단할 행동을 먼저 정하는 편이 낫습니다.

## 공개 문서 검색과 링크 이동

첫 작업은 “웹에서 알아서 조사해줘”보다 **사이트와 결과 항목을 좁혀서** 맡기는 것이 확인하기 쉽습니다. 이번에 실행한 작업을 요청문으로 표현하면 다음과 같습니다. 그대로 제출했던 대화 로그가 아니라, 같은 범위의 작업을 맡길 때 쓸 수 있는 예시입니다.

```text
ego-browser를 사용해 Python 공식 문서에서 pathlib를 검색해줘.
검색 결과에서 pathlib 문서를 열고 iterdir, glob, read_text의
용도와 주의점, 해당 절의 원문 링크를 표로 정리해줘.
공개 문서만 읽고 로그인, 파일 업로드, 계정 설정 변경은 하지 마.
읽지 못한 항목은 추측하지 말고 알려줘.
```

실제 실행에서는 공식 문서의 **Quick search** 입력란에 `pathlib`를 넣고 **Go** 버튼을 눌렀습니다. 검색 결과 페이지가 열린 뒤, `pathlib — Object-oriented filesystem paths` 링크를 선택했습니다. 주소를 추측해서 결과를 만든 것이 아니라 페이지의 입력란과 링크를 사용했습니다.

<Image src="/ego-lite-public-research/02-search.png" alt="ego-browser가 pathlib를 입력해 실행한 Python 공식 문서 검색 결과" caption="ego(lite)에서 검색창 입력과 버튼 클릭을 실행한 결과입니다. 출처: docs.python.org, 2026년 10월 21일 직접 캡처. 당시 문서 버전 표시는 3.15.0이었습니다." />

에이전트가 조작 대상을 찾는 데 사용한 것은 **Snapshot**입니다. 여기서 Snapshot은 화면 이미지가 아니라 페이지를 간결한 텍스트로 표현한 결과입니다. 입력란, 버튼, 링크와 참조 번호가 포함되므로 에이전트가 다음에 무엇을 누를지 판단할 수 있습니다. 글에 넣은 이미지는 이와 별도로 저장한 실제 페이지 캡처입니다.

한 가지 주의할 점도 있었습니다. 검색 버튼을 누른 직후에는 URL과 제목이 검색 페이지로 바뀌었는데도 Snapshot에 `root`만 보였습니다. 검색 결과가 아직 준비되지 않은 순간이었습니다. 결과 목록이 생기는 조건을 기다린 뒤 다시 읽자 검색어와 결과 링크들이 나타났습니다.

따라서 에이전트가 빈 내용을 받았다고 바로 “검색 결과 없음”으로 결론 내리면 안 됩니다. **페이지 이동 완료와 필요한 내용의 준비 완료는 구분해서 확인**해야 합니다. 이번에는 기다린 뒤 같은 탭에서 계속 진행했고, 결과 링크를 열어 원문까지 도달했습니다.

공식 사이트는 속도와 토큰 절감을 장점으로 내세웁니다. 이번 작업에서 확인한 것은 검색·탐색·본문 수집의 동작이며, 다른 브라우저와 같은 조건으로 시간이나 비용을 비교한 성능 측정은 아닙니다.

## 원문 대조와 결과 확인

검색 결과의 짧은 설명만으로 표를 완성하지 않았습니다. `pathlib` 문서를 연 뒤 `Path.iterdir`, `Path.glob`, `Path.read_text`의 본문을 읽고, 각 절로 바로 이동하는 링크를 함께 남겼습니다. 아래는 수집한 원문을 바탕으로 정리한 결과입니다.

| 항목 | 확인한 용도 | 함께 확인할 내용 |
|---|---|---|
| [Path.iterdir()](https://docs.python.org/3/library/pathlib.html#pathlib.Path.iterdir) | 디렉터리의 자식 경로 순회 | 나열 순서는 보장되지 않음 |
| [Path.glob()](https://docs.python.org/3/library/pathlib.html#pathlib.Path.glob) | 패턴과 일치하는 경로 수집 | 정해진 순서가 필요하면 결과 정렬 |
| [Path.read_text()](https://docs.python.org/3/library/pathlib.html#pathlib.Path.read_text) | 파일 내용을 문자열로 읽기 | 파일을 열어 읽은 뒤 닫음 |

이 표는 Python 코드를 실행한 결과가 아니라 **브라우저로 읽은 문서의 정리**입니다. 문서 제목과 메서드별 원문, 링크는 로컬 JSON에도 저장했습니다. 수집된 항목이 세 개이고 비어 있는 설명이 없는지 검사한 뒤, `iterdir()`의 원문 위치를 다시 열어 표의 설명과 대조했습니다.

[Python 문서 화면의 라이선스 및 저작권 고지](/images/blog/ego-lite-public-research/LICENSE-PYTHON.txt)를 함께 남겼습니다.

이런 작업의 완료 기준은 “AI가 표를 만들었다”보다 구체적이어야 합니다. **요청한 항목이 빠지지 않았는지, 링크가 해당 설명으로 연결되는지, 원문과 요약이 맞는지**를 확인하면 됩니다. 특히 버전별 동작이 달라지는 기술 문서는 페이지에 표시된 버전도 결과와 함께 남기는 것이 좋습니다.

브라우저가 로컬에서 실행된다고 읽은 내용이 모두 기기 안에만 머무는 것은 아닙니다. [개인정보 처리방침](https://lite.ego.app/privacy)은 브라우저 기록·쿠키 등의 로컬 저장과 별개로, 연결한 외부 AI 도구에 페이지 내용이나 실행 결과가 전달된다고 설명합니다. 그 도구와 모델 제공자의 데이터 정책도 적용됩니다. 사용 분석 정보의 서버 전송과 초기 설정에서 기본 활성화되는 충돌 보고 전송도 안내되어 있습니다. 민감한 자료를 맡기기 전에는 이 부분을 따로 검토해야 합니다.

비용도 나누어 봐야 합니다. 현재 [Windows 제품 설명](https://lite.ego.app/document/en/docs/windows/product-introduce)은 브라우저 다운로드와 사용, 작업별·브라우저 시간 과금이 없다고 안내합니다. **연결한 에이전트나 모델의 비용까지 무료라는 뜻은 아닙니다.**

공개 문서 조사 용도로는 입력부터 출처가 있는 정리까지 이어지는 흐름을 확인할 수 있었습니다. 반면 이미 검색 도구만으로 충분한 작업이라면 로컬 브라우저를 추가 설치하고 연결하는 수고가 더 클 수도 있습니다. 로그인된 사이트의 업무나 민감한 자료 접근까지 한꺼번에 맡기기보다, 이번처럼 공개 페이지 하나에서 **검색, 링크 이동, 원문 대조가 끝나는 작은 작업**으로 판단해보는 것을 권합니다.
