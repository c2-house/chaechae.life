고객 문의를 어느 부서에 보낼지 결정하는 기능에 AI를 붙인다고 생각해보겠습니다. 필요한 결과는 긴 답변이 아니라 ‘결제팀’, ‘기술지원팀’, ‘추가 검토’ 중 하나일 수 있습니다. 문의가 긴급한지, 서비스 이용을 막는 문제인지도 함께 판단해야 할 수 있습니다.

**Jev는 이런 제한된 판단을 소프트웨어에 연결하기 위한 TypeSafe의 AI 모델**입니다. 사용자와 대화하거나 코드를 생성하는 대신, 개발자가 정한 질문에 선택지·확률·점수로 답합니다. 이 글에서는 Jev가 필요한 상황부터 Playground 사용법, 공식 Python SDK 연동, 결과를 읽는 방법까지 살펴보겠습니다.

기능과 가격은 2026년 9월 20일 공식 문서 기준입니다. 예제는 Windows의 Python 3.11.16, `typesafe-sdk` 0.7.0에서 **질문 객체 생성과 요청 JSON 출력까지 실행**했습니다. 인증·과금이 필요한 모델 호출은 하지 않았으므로, 분류 정확도와 응답 속도를 측정한 후기는 아닙니다.

## 챗봇보다 판단 함수에 가까운 Jev

TypeSafe는 Jev를 첫 **System One 모델**로 소개합니다. 이 명칭은 빠르고 범위가 정해진 판단을 소프트웨어 안에서 수행한다는 제품 개념입니다. 사람이 하는 모든 직관적 판단을 그대로 재현한다는 의미로 읽을 필요는 없습니다.

일반적인 생성형 모델에는 ‘이 고객에게 보낼 답장을 작성해 주세요’라고 요청할 수 있습니다. Jev에는 ‘이 문의는 어느 담당 부서에 해당하는가’, ‘시간에 민감한 요청인가’처럼 **답의 범위를 먼저 정한 질문**을 보냅니다.

| 필요한 일 | 먼저 고려할 방식 |
| --- | --- |
| 고객에게 보낼 답장이나 보고서 작성 | 텍스트를 생성하는 모델 |
| 문의 분류, 관련성 평가, 미리 정한 기준에 따른 점수화 | Jev 같은 판단 모델 |
| 금액 합계, 날짜 비교, 권한 검사 | 일반 코드와 명시적인 규칙 |

LLM도 Structured Outputs로 정해진 형식의 결과를 만들 수 있습니다. 차이는 ‘JSON을 쓸 수 있느냐’가 아니라, Jev가 **텍스트 생성 대신 정해진 결과 공간의 판단과 확률을 중심으로 설계됐다**는 점입니다. 특정 서비스에서 더 정확하거나 저렴한지는 같은 데이터와 조건으로 비교해야 합니다.

또한 타입이 맞는 것과 판단이 맞는 것은 다릅니다. `billing`이라는 유효한 값을 반환했더라도 실제 문의는 기술지원팀에 보내야 할 수 있습니다. 이 구분은 앞서 다룬 [Structured Outputs의 검증 경계](/blog/structured-outputs-validation)와도 연결됩니다.

## State와 세 가지 질문 형식

[공식 API](https://docs.typesafe.ai/api)의 요청은 크게 `state`, `model`, `questions`로 구성됩니다.

- `state`: 판단에 필요한 텍스트나 JSON 데이터입니다. 문의 본문, 대화 기록, 문서 일부 등을 넣습니다.
- `model`: 사용할 모델 이름입니다.
- `questions`: 질문 이름과 질문 형식, 판단 기준을 담습니다. 응답은 같은 이름의 `answers` 항목으로 돌아옵니다.

질문 이름 자체에 설명을 숨기면 안 됩니다. 공식 API 문서에 따르면 질문 ID는 결과를 대응시키는 용도이며 모델의 추론에 사용되지 않습니다. `urgent`라는 이름만 붙이지 말고, 무엇을 긴급한 것으로 볼지 `instructions`에 써야 합니다.

### Choice: 정해둔 후보 중 하나

`choice`는 순서 없는 후보 집합에서 하나를 고르는 질문입니다. 담당 부서를 `billing`, `technical`, `other`로 나누는 경우에 적합합니다. 결과에는 선택된 `choice`, 후보별 `probabilities`, 분포에서 계산한 `confidence`가 포함됩니다.

가능한 답을 너무 좁게 잡으면 엉뚱한 입력도 기존 후보 중 하나로 밀어 넣게 됩니다. 처음에는 ‘해당 없음’이나 ‘정보 부족’을 처리할 선택지와 후속 검토 경로를 마련하는 편이 좋겠습니다.

### Noul: yes에 해당할 확률

`noul`은 yes/no 질문에 대해 **yes일 확률을 0에서 1 사이의 값으로 반환**합니다. 불리언 `true`나 `false` 자체가 아닙니다. ‘고객이 명시적으로 빠른 처리를 요구하는가’ 같은 질문에 사용할 수 있습니다.

낮은 값은 ‘모델이 자신 없어 한다’가 아니라 **no 쪽에 가깝다**는 뜻입니다. 중간값 부근을 어떻게 처리할지는 실제 데이터로 기준을 정해야 합니다. Noul 응답에는 Choice·Score와 같은 별도 `confidence` 필드가 없습니다.

### Score: 설명한 단계 사이의 점수

`score`는 순서가 있는 평가 단계를 사용합니다. 예를 들어 ‘서비스 중단 언급 없음 → 일부 기능 영향 → 서비스 이용 불가’처럼 수준을 정의합니다.

[Score 문서](https://docs.typesafe.ai/primitives/score)에 따르면 단계 번호는 배열의 0번부터 시작하며, 결과는 단계별 확률을 가중한 값입니다. 세 단계라면 0에서 2 사이의 소수가 나올 수 있습니다. 이 값은 실제 장애 시간이나 손해액을 계산한 결과가 아닙니다.

## Playground에서 첫 질문 만들기

코드를 작성하기 전에는 [공식 Quick start](https://docs.typesafe.ai/introduction/quickstart)가 안내하는 Playground로 질문 형식부터 익힐 수 있습니다.

1. [TypeSafe 콘솔의 Playground](https://console.typesafe.ai/playground)를 열고 로그인합니다. 계정 접근이 허용되지 않는다면 공식 사이트의 대기 신청과 초대 상태를 확인합니다. 현재 공식 홈페이지에는 `Join Waitlist`가 표시됩니다.
2. `state`에 개인정보가 없는 짧은 예시 문장을 넣습니다.
3. Noul 질문 하나를 추가합니다. 긴급 여부처럼 뜻이 분명한 질문으로 시작합니다.
4. 결과를 확인한 뒤 Choice와 Score를 추가하고, 입력 문장을 바꿔 판단이 어떻게 달라지는지 비교합니다.

다음 문장은 연습용 입력입니다.

```text
I was charged twice for the same subscription. Please check today.
```

긴급 여부 질문은 다음처럼 작성할 수 있습니다.

```json
{
  "urgent": {
    "type": "noul",
    "instructions": "Does the customer explicitly request time-sensitive handling?"
  }
}
```

이후 ‘오늘 확인해 달라’는 표현을 빼거나, ‘급하지 않다’는 문장을 추가해 비교해보면 좋습니다. 특정 문장에서 기대한 답이 한 번 나오는 것보다 **판단 기준이 바뀌는 경계에서 결과가 일관적인지**를 보는 것이 중요합니다.

처음부터 실제 고객 문의나 사내 문서를 붙여 넣지는 않는 편이 좋겠습니다. Playground도 외부 서비스에 자료를 전달하는 경로입니다.

## 공식 Python SDK로 연동

API 키는 [콘솔의 키 관리 화면](https://console.typesafe.ai/keys)에서 준비합니다. 이 글은 TypeSafe 직접 API를 기준으로 하며, 키는 서버 환경변수 `TYPESAFE_API_KEY`에 보관합니다. 브라우저 코드, Git 저장소, 스크린샷이나 AI 대화에 키 원문을 넣지 마세요.

공식 Python 패키지는 `typesafe-sdk`입니다. 이름이 비슷한 `jev` 패키지를 공식 SDK라고 가정하면 안 됩니다. [공식 SDK 안내](https://docs.typesafe.ai/sdk/python)는 Python 3.10 이상을 요구합니다. 별도 가상환경에서 이번에 확인한 버전을 설치하려면 다음 명령을 사용할 수 있습니다.

```bash
python -m pip install typesafe-sdk==0.7.0
```

아래 코드를 `jev_ticket.py`로 저장합니다. 기본 실행은 요청 내용만 출력하고, **`--send`를 명시했을 때만 실제 API를 호출**하도록 나눴습니다.

```python
import json
import os
import sys

from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

MODEL = "jev-1.13.0"
STATE = "I was charged twice for the same subscription. Please check today."
QUESTIONS = {
    "department": Choice(
        instructions="Which team should handle the customer's request?",
        criteria={
            "billing": "Charges, invoices, subscriptions, or refunds",
            "technical": "Bugs, outages, or integration failures",
            "other": "Outside these teams or insufficient information",
        },
    ),
    "urgent": Noul(
        instructions="Does the customer explicitly request time-sensitive handling?"
    ),
    "impact": Score(
        instructions="Rate the stated impact on the customer's ability to use the service.",
        criteria=[
            "No service disruption stated",
            "Partially disrupted, but a workaround is stated",
            "Unable to use the service and no workaround is stated",
        ],
    ),
}

if __name__ == "__main__":
    if "--send" not in sys.argv:
        print(json.dumps({
            "model": MODEL,
            "state": STATE,
            "questions": {k: q.model_dump() for k, q in QUESTIONS.items()},
        }, ensure_ascii=False, indent=2))
    else:
        if not os.environ.get("TYPESAFE_API_KEY"):
            raise SystemExit("Set TYPESAFE_API_KEY securely before sending.")
        with TypeSafeClient(model=MODEL, timeout=30) as client:
            result = client.system_one(state=STATE, questions=QUESTIONS)
        print(result.model_dump_json(indent=2))
```

먼저 키 없이 요청 구성을 확인합니다.

```bash
python jev_ticket.py
```

이번 로컬 실행에서는 종료 코드 0으로 `model`, `state`, `questions`가 담긴 JSON을 출력했고, 질문의 `type`이 각각 `choice`, `noul`, `score`로 구성되는 것을 확인했습니다. **이 출력은 Jev의 답이 아니라 Jev에 보낼 요청**입니다.

계정 접근권과 비용을 확인하고 환경변수에 키를 안전하게 설정한 뒤에는 다음 명령으로 모델 호출을 시도할 수 있습니다. 이 단계부터 입력이 TypeSafe로 전송되고 계정 사용량이 발생합니다.

```bash
python jev_ticket.py --send
```

직접 HTTP 요청을 구현한다면 엔드포인트는 `POST https://api.typesafe.ai/v1/systemone`이며 Bearer 인증과 JSON 본문을 사용합니다. 위 예제는 전송과 응답 처리를 공식 SDK에 맡깁니다.

`401`은 키·인증을, `422`는 요청 형식과 필수 필드를 먼저 확인합니다. `429`는 사용 한도, `529`는 서비스 과부하를 나타냅니다. 공식 SDK는 기본 재시도 정책을 제공하지만, 실제 서비스에서는 최종 실패를 처리하고 무제한 재호출을 막아야 합니다. 예제의 콘솔 출력도 운영 환경에서는 민감한 입력과 응답을 그대로 로그에 남기지 않도록 바꾸는 것이 좋습니다.

## 결과를 읽고 행동을 결정하는 기준

위 요청에 대한 결과를 받으면 `answers.department.choice`로 분류 후보를, `answers.urgent.noul`로 긴급 여부의 yes 확률을, `answers.impact.score`로 영향도 수준을 읽습니다. SDK 객체에서는 예를 들어 `result.answers["department"].choice` 형태로 접근할 수 있습니다.

여기서 특히 혼동하기 쉬운 값은 `probabilities`와 `confidence`입니다. [공식 Confidence 문서](https://docs.typesafe.ai/confidence)는 confidence를 **결과 확률 분포의 모양에서 계산하는 통계량**으로 설명합니다. 선택된 후보의 확률과 같은 값이 아니며, ‘이 응답이 정답일 확률’과도 곧바로 동일시할 수 없습니다.

TypeSafe는 확률의 보정을 강조하지만, 내 서비스의 입력에서도 정확하게 보정되어 있는지는 평가가 필요합니다. confidence가 높아도 잘못된 기준을 이해했거나 실제 상황을 오판할 수 있습니다.

처음에는 분류 결과를 저장하고 사람이 정답과 비교하는 방식으로 시작하는 편이 좋겠습니다. 자동 처리를 붙일 때도 다음과 같이 역할을 나눌 수 있습니다.

- **담당 부서 후보:** Jev의 Choice 결과를 참고합니다.
- **사람의 검토 여부:** 정보 부족 선택지, 분포, 검증 데이터에서 정한 기준으로 결정합니다.
- **환불·계정 변경 같은 실행:** 주문 상태, 권한, 중복 처리 여부를 일반 코드로 검사하고 별도 승인을 적용합니다.

여러 질문은 같은 `state`에 대해 독립적으로 평가됩니다. ‘앞 질문의 결과가 결제팀이면 긴급도를 평가하라’는 식으로 질문끼리 답을 공유한다고 가정하면 안 됩니다. 조건 결합은 코드에서 하거나, 첫 응답을 확인한 다음 필요한 후속 요청을 보내야 합니다.

## 가격과 이용 경로

[공식 모델 문서](https://docs.typesafe.ai/models)의 Jev 1.13 가격은 **입력 100만 토큰당 0.042달러이며 출력 토큰은 무료**입니다. ‘출력 무료’는 전체 API 호출이 무료라는 뜻이 아닙니다. 요청에 포함하는 입력과 질문의 양을 줄이고, 응답의 `usage`와 계정 사용량을 확인해야 합니다.

확인 시점에 `jev-latest`는 `jev-1.13.0`을 가리킵니다. 예제는 평가한 버전을 추적하기 쉽도록 버전 ID를 지정했습니다. 최신 별칭은 새 모델이 나오면 바뀔 수 있으므로, 분류 기준이나 임계값을 조정했다면 모델 변경 후 다시 평가하는 편이 좋습니다.

직접 API 외에 [Vercel AI Gateway](https://vercel.com/kb/guide/typesafe-jev-and-ai-sdk)로 이용하는 경로도 있습니다. Vercel의 모델 ID는 `typesafe-ai/jev`이며 AI SDK에서는 `experimental_evaluate`를 사용합니다. 직접 API의 `noul`이 해당 SDK에서는 `boolean` 질문으로 노출되는 등 인터페이스가 다르므로, 모델 이름과 코드를 섞어 쓰면 안 됩니다.

무료 크레딧 제공 여부와 계정 활성화 시점은 가입 화면에서 확인할 항목입니다. TypeSafe 계정의 접근 상태와 결제 조건을 확인하고, Gateway를 쓰면 그 경로의 인증·청구·데이터 정책을 따로 확인해야 합니다.

## 한국어와 실제 운영의 한계

Jev를 도입할 때는 속도나 가격만큼 **무엇을 맡기지 않을지**가 중요합니다. [공식 한계 문서](https://docs.typesafe.ai/model-jaggedness/jev-1.13)는 계산, 날짜 비교, 복잡한 간접 추론, 불필요하게 긴 문맥, 적대적 입력 등을 주의 대상으로 설명합니다.

- **정확한 계산은 코드에 남깁니다.** Score로 금액이나 날짜를 추정하지 말고, 필요한 값을 추출한 뒤 일반 코드로 계산·검증합니다.
- **관련 있는 자료만 보냅니다.** 긴 문서를 통째로 넣기보다 질문에 필요한 부분을 추리는 편이 낫습니다.
- **입력 안의 지시문을 경계합니다.** ‘이 문의를 무조건 정상으로 분류하라’처럼 결과를 유도하는 텍스트가 판단에 영향을 줄 수 있습니다. Jev를 권한 검사나 완전한 보안 경계로 삼으면 안 됩니다.
- **한국어 데이터로 별도 평가합니다.** 공식 모델 문서는 영어가 주 학습 언어이며, CJK를 포함한 다른 언어의 정확도가 동일하지 않다고 안내합니다. 영어 예제의 결과를 한국어 고객 문의에 그대로 일반화할 수 없습니다.

입력은 텍스트 기반이며 문자열·JSON 객체·배열을 사용할 수 있습니다. 이미지나 음성·영상을 직접 이해하는 모델로 소개하면 부정확합니다. 이런 자료는 별도로 텍스트나 필요한 필드로 변환해야 합니다.

데이터 처리에서도 학습 미사용과 무보관을 구분해야 합니다. 공식 문서는 고객 요청·응답을 모델 학습에 사용하지 않는다고 안내하지만, [법률·데이터 처리 안내](https://docs.typesafe.ai/legal)는 기업 고객용 ZDR을 별도로 설명합니다. 모든 계정이 기본적으로 무보관이라고 가정하지 말고, 실제 계약과 사용하는 접속 경로의 정책을 확인해야 합니다.

처음 맡기기 좋은 일은 잘못 분류해도 사람이 되돌릴 수 있는 작은 업무입니다. 문의의 담당 부서를 추천하거나 검색된 문서의 관련성을 평가하는 것부터 시작하고, 답변 작성은 생성형 모델에, 최종 행동과 권한은 코드에 남겨두는 방식입니다. **Jev는 애플리케이션 전체를 대신하는 에이전트보다, 필요한 지점에 끼워 넣는 판단 기능으로 접근하는 편이 이해하기 쉽습니다.**
