### 목차

## 브라우저 자동화에 MCP만 선택할 필요가 있을까?

AI Agent에게 웹 페이지를 열고 버튼을 누르게 하려면 어떤 도구를 연결해야 할까요? Playwright MCP가 먼저 떠오를 수 있습니다. 그런데 Playwright는 코딩 Agent를 위한 **CLI와 Skills 조합**도 제공합니다. 공식 문서에서는 오히려 코딩 Agent에 CLI가 더 잘 맞는 경우를 설명하고 있습니다.

그러면 이미 연결한 MCP를 CLI로 바꿔야 할까요? 명령이 짧으면 비용도 줄고, 작업도 더 잘 끝낼까요? 문서의 추천 문구만으로 결정하기에는 빠진 조건이 많습니다. 브라우저 상태가 어디에 남는지, Agent가 실제로 어떤 응답을 받는지도 확인해야 합니다.

이번에는 **같은 TodoMVC 작업을 CLI와 MCP로 실행하고, 사용 흐름과 상태 관리 방식을 비교**했습니다. 설치법을 길게 따라가기보다 어떤 환경에서 무엇을 선택할지에 초점을 맞춰보겠습니다.

<Callout emoji="🔎">
  이 글의 실험은 2026년 9월 11일 Hermes가 별도 Windows 테스트 환경에서 수행했습니다. 작성자의 장기 사용 후기가 아니라 원본 실행 기록을 바탕으로 정리한 검증입니다. 공식 문서도 같은 날 집필 직전에 다시 확인했습니다.
</Callout>

## 공식 문서는 CLI와 MCP를 어떻게 구분할까?

[Playwright CLI 가이드](https://playwright.dev/docs/getting-started-cli)는 CLI를 코딩 Agent용 브라우저 자동화 인터페이스로 소개합니다. 간결한 명령과 설치 가능한 Skills를 통해 코드베이스, 테스트, 추론이 함께 들어가는 컨텍스트를 효율적으로 사용한다는 설명입니다.

반면 [Playwright MCP 공식 저장소](https://github.com/microsoft/playwright-mcp)는 MCP 클라이언트에 브라우저 도구를 제공하고, **구조화된 accessibility snapshot**으로 페이지를 다루는 방식을 설명합니다. 화면의 픽셀을 해석하는 대신 `textbox`, `button`, `link` 같은 역할과 이름을 읽기 때문에 비전 모델이 필수는 아닙니다.

공식 문서의 권장 방향은 다음과 같습니다.

| 구분 | 공식 문서가 강조하는 사용 환경 |
| --- | --- |
| CLI + Skills | 큰 코드베이스와 브라우저 작업을 함께 다루는 코딩 Agent, 간결한 명령 중심의 흐름 |
| MCP | 페이지 구조를 반복 탐색하는 자동화, 풍부한 상태 확인이 필요한 Agent 루프, 장시간 작업 |

여기서 **CLI는 상태가 없고 MCP만 상태를 가진다는 뜻으로 읽으면 안 됩니다.** 뒤에서 확인하겠지만 CLI도 명령 사이에 브라우저를 유지합니다.

### 설치보다 중요한 것은 Agent가 도구를 읽는 방식

CLI는 `@playwright/cli` 패키지를 전역 또는 프로젝트 로컬에 설치하는 방식입니다. 공식 문서는 `npm install -D @playwright/cli@latest`로 로컬 설치한 뒤 `npx playwright-cli --help`를 사용하는 방법도 안내합니다. `playwright-cli install --skills`를 실행하면 지원하는 Agent가 읽을 Skills를 준비할 수 있습니다.

이번 검증에서는 블로그 저장소 밖에 로컬 설치했고, Skills 파일이 테스트 작업 공간의 `.claude/skills/playwright-cli`에 생성되는 것까지 확인했습니다. Skills 없이 `--help`를 읽으며 사용하는 방식도 공식적으로 안내됩니다. 다만 Skills를 읽은 모델의 행동이 얼마나 개선되는지는 이번 실험 대상이 아닙니다.

MCP는 보통 클라이언트 설정에 실행 명령 `npx`와 인자 `@playwright/mcp@latest`를 등록합니다. 연결되면 클라이언트는 `tools/list`로 도구 이름, 설명, 입력 schema를 받습니다. 실제 테스트 서버에서는 기본 도구 **24개**가 반환됐습니다. 예를 들어 `browser_type`에는 요소를 지정하는 `target`과 입력할 `text`가 필요했습니다.

CLI가 명령 사용법을 읽고 실행하는 흐름이라면, MCP는 구조화된 도구 목록과 인자를 통해 호출하는 흐름입니다. 어느 쪽이 편한지는 Agent가 터미널과 파일 읽기를 잘 지원하는지, MCP를 기본 도구로 사용하는지에 따라 달라집니다.

### Node 버전 안내도 한 번 더 확인해야 합니다

확인 당시 CLI·MCP README는 Node.js 18 이상을, 공식 CLI 가이드는 20 이상을 안내했습니다. 설치된 패키지도 최상위 `engines`는 18 이상이었지만, 함께 설치된 `playwright` 의존성은 20 이상을 요구했습니다. 그래서 **README의 최소 숫자 하나만 보고 환경을 정하는 것은 피하는 편이 좋겠습니다.** 이번에는 Node 22에서 검증했습니다.

[Playwright 설치 문서](https://playwright.dev/docs/intro)는 Windows·macOS·Linux에서 Chromium·Firefox·WebKit 지원을 설명합니다. CLI/MCP 도움말에는 Chrome·Edge 채널 선택지도 있습니다. 아래 결과는 그중 Windows의 Chrome에서만 확인한 내용입니다.

## 이번에는 Agent 성능 벤치마크를 하지 않았다

원래 궁금한 것은 같은 Agent에게 도구만 바꿔주면 무슨 차이가 생기느냐는 것입니다. 하지만 현재 환경에서는 동일 모델이 CLI와 MCP를 번갈아 보며 다음 행동을 결정하는 조건을 구성하지 않았습니다.

대신 **고정된 Node.js 테스트 드라이버**를 만들었습니다. 드라이버는 CLI 쪽에서는 명령별 프로세스를 실행하고, MCP 쪽에서는 공식 MCP SDK로 실제 서버에 stdio 연결을 맺어 도구를 호출했습니다. MCP 응답을 흉내 낸 테스트가 아닙니다.

| 환경 | 실험 당시 값 |
| --- | --- |
| OS | Windows x64, 빌드 26200 |
| Node.js / npm | 22.23.2 / 10.9.8 |
| Playwright CLI | `@playwright/cli` 0.1.19 |
| Playwright MCP | `@playwright/mcp` 0.0.80 |
| MCP SDK | `@modelcontextprotocol/sdk` 1.30.0 |
| 공통 Playwright 의존성 | 1.63.0-alpha-2026-08-31 |
| 브라우저 | Chrome 152.0.7977.83, headless |
| Viewport | 1280 × 720 |

두 패키지는 같은 Playwright 의존성을 사용했습니다. **그 의존성이 prerelease라는 점도 결과의 범위에 포함**됩니다. 모든 안정 버전에서 똑같이 동작한다고 일반화하지는 않습니다.

페이지, 입력 데이터, 작업 순서, 브라우저와 검증 기준을 맞췄습니다. 프로필은 CLI의 기본 메모리 프로필과 MCP의 `--isolated`를 사용했습니다. 즉, 각 제품의 기본 설정을 그대로 비교한 것이 아니라 저장 조건을 맞춘 비교입니다. 별도 모델 API 호출이나 실제 로그인 계정은 사용하지 않았습니다.

## TodoMVC에서 같은 작업을 세 번씩 실행하기

대상은 [Playwright 공식 TodoMVC 데모](https://demo.playwright.dev/todomvc/)입니다. 할 일 추가와 필터 선택 정도면 너무 쉬운 것 아닌가 싶지만, 입력·클릭·요소 탐색·상태 검증을 작게 묶어 확인하기에는 좋습니다.

작업은 다음 순서로 진행했습니다.

1. TodoMVC에 접속합니다.
2. `OJT alpha`, `OJT beta`, `OJT gamma`를 차례로 생성합니다.
3. 두 번째 항목인 `OJT beta`를 완료 처리합니다.
4. Active를 선택하고 alpha와 gamma만 표시되는지 확인합니다.
5. Completed를 선택하고 beta만 표시되는지 확인합니다.
6. Clear completed로 완료 항목을 삭제합니다.
7. All로 돌아와 최종 상태를 검증합니다.

각 방식에서 세 번씩 실행했고, 순서는 CLI→MCP, MCP→CLI, CLI→MCP로 번갈아 진행했습니다. 입력과 Enter는 양쪽 모두 별도 호출로 나눴습니다. 호출 수를 최대한 줄이는 최적화 실험은 아닙니다.

중요한 것은 마지막 확인입니다. **화면에서 beta가 안 보인다고 삭제 성공으로 판정하지 않았습니다.** Active 필터 때문에 숨겨졌을 수도 있으니까요. All 화면의 DOM과 TodoMVC가 localStorage에 저장한 데이터를 함께 읽어 alpha·gamma만 남고, 두 항목 모두 미완료인지 검사했습니다. 브라우저의 입력과 클릭은 도구로 수행했고, JavaScript 평가는 검증에 사용했습니다.

## 호출 수와 응답을 비교하니 생각보다 비슷했다

정식 측정에서는 두 방식 모두 작업을 끝냈습니다.

| 측정 항목 | CLI | MCP |
| --- | --- | --- |
| 핵심 Task 성공 | 3/3 | 3/3 |
| 실행당 명령 / Tool Call | 16회 | 16회 |
| 실행당 snapshot 파일 읽기 | 9회 | 9회 |
| 정식 측정 중 도구 실패 / 재시도 | 0회 / 0회 | 0회 / 0회 |
| 정식 실행 중 사용자 개입 | 0회 | 0회 |
| 실제 모델 token 사용량 | 미측정 | 미측정 |

16회에는 접속 1회, 입력 3회, Enter 3회, 클릭 5회, 결과 검증 4회가 포함됩니다. snapshot 파일 읽기는 그 밖에 드라이버가 수행한 파일 접근입니다. **도구 호출 수만 세면 Agent가 결과를 읽는 작업을 빠뜨리기 쉽습니다.**

사용자 개입이 없었다는 것도 고정 드라이버 실행 중의 이야기입니다. 준비 단계에서는 Hermes가 작성한 체크박스 탐색 로직이 접근성 이름을 잘못 가정해 예비 실행이 한 번 중단됐습니다. 실제 snapshot의 `checkbox "Toggle Todo"`를 기준으로 고친 뒤 정식 측정을 진행했습니다. 이 예비 실패는 기록에 남겼으며, 제품의 도구 실패와 구분했습니다.

### 시간은 기록했지만 순위를 매기지는 않았습니다

| 실행 | CLI | MCP |
| --- | --- | --- |
| 1회 | 11.852초 | 6.976초 |
| 2회 | 11.805초 | 6.943초 |
| 3회 | 11.827초 | 7.151초 |
| 중앙값 | 약 11.827초 | 약 6.976초 |

이 숫자는 첫 브라우저 접속부터 최종 검증까지의 드라이버 실행 시간입니다. 설치, Skills 준비, MCP 초기 연결과 정리는 제외했습니다. **CLI에는 명령별 프로세스 실행 비용이 포함됐고, MCP는 이미 연결된 서버를 호출했습니다.** 파일 읽기와 로컬 검증도 작업 흐름에 들어갑니다.

따라서 이 차이를 MCP Agent의 일반적인 속도 우위로 해석할 수는 없습니다. 모델이 다음 행동을 생각하는 시간도 없고, 초기 연결 조건도 다르니까요. 여기서는 독자가 실험 규모와 측정 경계를 파악할 수 있도록 원래 값을 남겼습니다.

### MCP도 snapshot 파일 링크를 반환했습니다

이번에 더 눈여겨볼 부분은 응답의 모양이었습니다. CLI의 자동 응답이 snapshot 파일 링크를 반환하는 것은 공식 문서의 예시와 비슷했습니다. 그런데 **설치된 MCP도 자동 응답에서는 snapshot 파일 링크를 반환**했습니다.

반대로 `browser_snapshot`을 명시적으로 호출했을 때에는 YAML tree가 응답 본문에 들어왔습니다. CLI에서 명시적으로 `snapshot`을 요청했을 때도 인라인 YAML 응답을 확인했습니다.

즉, **CLI는 파일, MCP는 항상 전체 tree라는 이분법은 이번 버전에 맞지 않습니다.** 설치된 공통 구현에서도 자동 snapshot과 명시적 요청을 다르게 처리하는 분기를 확인했습니다.

이번 드라이버는 반환된 파일을 양쪽 모두 읽었습니다. 읽은 snapshot은 실행당 9개, 내용은 합계 14,090문자였습니다. 별도로 반환 텍스트는 CLI가 실행당 6,556~6,734문자, MCP가 6,494~6,671문자였습니다. 이것은 schema나 요청까지 포함한 전체 통신량이 아니라 **응답 텍스트와 읽은 파일의 크기를 따로 센 기록**입니다.

또 하나의 조건이 있습니다. MCP 서버와 드라이버가 같은 로컬 파일시스템을 사용했기 때문에 파일 링크를 읽을 수 있었습니다. 원격 서버의 파일 경로가 내 Agent에서도 열릴지는 별도 문제입니다. 파일 접근이 없다면 명시적 snapshot 요청 등 클라이언트가 실제로 지원하는 읽기 경로부터 확인해야 합니다.

## CLI에도 상태가 있다: session과 profile 구분하기

CLI라는 이름 때문에 명령 한 번 실행하면 모든 상태가 사라질 것처럼 느낄 수 있습니다. 그런데 이번 테스트의 CLI 호출은 매번 별도 프로세스였어도 같은 이름의 브라우저 세션을 사용했습니다. 그래서 앞에서 만든 할 일과 선택한 상태를 다음 명령에서 이어서 다룰 수 있었습니다.

여기서는 세 가지를 구분하면 이해가 편합니다.

- **Session**: 여러 명령이나 도구 호출이 어떤 브라우저 작업 흐름을 이어갈지 정하는 단위입니다. CLI는 `-s=<session>`으로 대상을 지정할 수 있습니다. MCP에서는 연결된 서버와 브라우저 컨텍스트의 수명주기를 함께 봐야 합니다.
- **Profile**: cookie와 저장 데이터 등을 어디에 보관할지에 관한 설정입니다. 메모리에만 둘지, 전용 디스크 경로에 남길지에 따라 브라우저 재시작 후 결과가 달라집니다.
- **Browser connection reuse**: 이미 실행 중인 브라우저에 연결을 다시 붙이는 것입니다. 브라우저를 새로 시작하면서 디스크 데이터를 읽는 것과 다릅니다.

[CLI README](https://github.com/microsoft/playwright-cli)는 기본 프로필을 메모리에 유지하고, `--persistent` 또는 `--profile`로 디스크에 보존할 수 있다고 설명합니다. [MCP README](https://github.com/microsoft/playwright-mcp)는 기본 persistent profile과 별도의 `--isolated` 모드를 구분합니다. 전용 디스크 경로는 `--user-data-dir`로 지정할 수 있습니다.

### 브라우저를 닫았다가 열면 어떻게 될까?

핵심 Task와 별도로, 테스트용 localStorage 값과 만료 시간을 지정한 가짜 cookie를 넣고 확인했습니다. CLI는 `--profile`, MCP는 `--user-data-dir`로 별도 디스크 프로필도 만들었습니다.

| 확인한 조건 | CLI | MCP |
| --- | --- | --- |
| 같은 브라우저 실행 중 별도 호출 | 유지 | 유지 |
| 같은 브라우저에서 reload 또는 같은 URL 재접속 | 유지 | 유지 |
| 메모리 프로필로 종료 후 재실행 | 소멸 | 소멸 |
| 디스크 프로필로 종료 후 재실행 | 유지 | 유지 |
| 디스크 프로필로 클라이언트까지 다시 시작 | 유지 | 유지 |
| 실행 중인 외부 브라우저에 CDP 재연결 | 유지 | 유지 |

외부 브라우저 연결은 테스트 전용 Chrome을 따로 띄워 확인했습니다. CLI는 attach→detach→attach, MCP는 CDP 연결 클라이언트를 종료한 뒤 새 클라이언트로 연결했습니다. **브라우저 자체를 살려둔 상태였기 때문에** 저장 데이터를 이어서 읽을 수 있었습니다.

상태 실험은 각 조건의 동작 확인이지 반복 통계가 아닙니다. 실제 로그인 복원이나 모든 종류의 cookie를 검증한 것도 아닙니다. 특히 운영 계정의 프로필을 편하다는 이유로 바로 연결하는 것은 피하는 편이 좋겠습니다. 자동화 전용 프로필을 분리하고, 언제 버릴지를 먼저 정하는 쪽이 낫습니다.

## ref가 잘못됐을 때 어떻게 복구할까?

snapshot의 ref는 페이지 요소를 가리키는 참조입니다. 오래된 참조나 잘못된 값을 사용했을 때 어떤 응답이 오는지도 별도로 확인했습니다. 이번에는 존재하지 않는 `e999999`를 의도적으로 전달했습니다.

양쪽에서 아래 오류가 반환됐습니다.

```text
Error: Ref e999999 not found in the current page snapshot. Try capturing new snapshot.
```

이후 드라이버가 새 snapshot을 요청하고, 그 안에서 입력창의 유효한 ref를 찾아 다시 클릭했습니다. 양쪽 모두 **의도적 오류 1회 → snapshot 갱신 1회 → 대체 클릭 1회**로 진행됐습니다.

이것은 복구할 수 있는 인터페이스를 확인한 것입니다. **모델이 오류를 이해하고 스스로 고친 실험은 아닙니다.** 다만 자동화를 설계할 때 같은 명령을 무작정 반복하는 대신, 페이지를 다시 관찰하고 참조를 갱신하는 경로가 필요하다는 점은 확인할 수 있습니다.

CLI에서는 오류가 있어도 종료 코드만으로 충분히 판정되지 않는 경우가 있어 응답의 `### Error`도 확인했습니다. MCP는 `isError`와 반환 내용을 확인했습니다. 데모의 favicon 404 콘솔 로그도 관찰됐지만, 할 일 조작과 최종 상태 검증은 통과했으므로 Task 실패로 세지 않았습니다.

## 이 결과를 토큰 비용 비교라고 부를 수 없는 이유

공식 문서는 CLI를 **token-efficient**라고 표현합니다. 큰 도구 schema와 장황한 페이지 정보를 모델 컨텍스트에 넣는 부담을 줄이는 방향을 설명하는 문구입니다. 이 공식 설명과 이번 실험의 문자 수는 서로 다른 근거입니다.

이번에는 모델 호출 자체를 비교하지 않았습니다. 실제 입력·출력 token, 캐시 적용, 클라이언트의 schema 지연 로딩, Agent가 읽은 파일의 범위도 모델 사용량으로 측정하지 않았습니다. snapshot 파일을 만들었다고 그 전체가 자동으로 모델에 들어가는 것도 아니고, 반대로 파일을 모두 읽으면 그만큼의 내용이 필요해질 수 있습니다.

그래서 **응답이 짧았다는 관찰을 비용이 싸다는 결론으로 바꾸지 않습니다.** 실제 비용을 비교하려면 같은 모델과 Agent 설정에서 작업을 반복하고, 도구 목록을 포함해 모델에 무엇이 전달됐는지와 실제 사용량을 함께 확인해야 합니다.

이번 결과로 말할 수 있는 것은 응답을 전달하고 읽는 경로, 상태 보관 방식, 고정 작업의 성공 여부까지입니다. 복잡한 로그인·iframe·캔버스 UI나 장시간 탐색의 신뢰성은 남은 검증 대상입니다.

## 내 Agent에는 어느 쪽이 더 맞을까?

터미널과 파일 읽기를 자연스럽게 사용하는 코딩 Agent라면 **CLI부터 작게 붙여보는 선택**이 괜찮겠습니다. 브라우저 작업을 코드 탐색과 테스트 사이에 넣기 쉽고, session 이름과 읽을 snapshot을 작업 흐름에 맞춰 관리할 수 있습니다. 다만 셸 실행과 파일 접근이 제한된 환경이라면 이 장점이 그대로 적용되지는 않습니다.

반대로 이미 MCP 중심으로 도구를 연결하고 있다면 **브라우저 도구만을 위해 CLI로 옮길 이유는 약합니다.** 구조화된 인자로 호출하고 기존 클라이언트의 연결 관리 방식을 쓰는 편이 자연스러울 수 있습니다. 대신 서버가 반환하는 파일에 접근 가능한지, 명시적 snapshot을 어떻게 읽는지, 연결 종료 때 브라우저가 어떻게 되는지는 확인해야 합니다.

어느 쪽이든 세션을 이어가는 것과 데이터를 디스크에 남기는 것을 같은 설정으로 생각하지 않는 게 중요합니다. 반복 테스트는 깨끗한 메모리 프로필이 편하고, 작업을 재개해야 한다면 전용 디스크 프로필이나 실행 중 브라우저 재연결이 필요할 수 있습니다. 같은 프로필을 여러 실행에서 무작정 공유하는 방식도 피해야 합니다. MCP 공식 문서 역시 동일 persistent profile의 동시 사용 충돌을 주의하라고 안내합니다.

새로 구성하는 터미널 중심 자동화라면 CLI를, 이미 MCP 도구 체계가 자리 잡았다면 MCP를 먼저 검토하겠습니다. 이번 작은 실험만으로 기존 도구를 교체할 이유는 찾지 못했습니다. **지금 불편한 것이 도구 연결인지, snapshot 읽기인지, 상태 관리인지**부터 나눠보면 전환할 필요가 있는지도 더 분명해집니다.

MCP의 구성 요소 자체가 낯설다면 [MCP 개념 정리](/blog/mcp-study)를 먼저 읽어보셔도 좋습니다. 사람이 코드를 작성하는 웹 자동화 흐름은 [Helium 실습 글](/blog/python-web-automation-helium)과 비교해볼 수 있습니다.
