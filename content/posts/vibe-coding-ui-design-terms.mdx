AI에게 화면을 만들어달라고 할 때 “깔끔하게”, “요즘 서비스처럼”, “조금 더 고급스럽게”라는 말부터 떠오를 수 있습니다. 그런데 결과가 마음에 들지 않으면 다음 요청도 “뭔가 답답한데 더 예쁘게”가 되기 쉽습니다. 카드 안이 좁은 것인지, 카드끼리 붙은 것인지, 모든 글자가 비슷한 크기인 것인지부터 구분하면 수정할 위치가 달라집니다.

**원하는 화면을 설명하려면 용어 이름에 대상과 조건을 붙이는 편이 좋습니다.** “여백을 늘려주세요”보다 “카드 안쪽 패딩은 24px, 카드 사이 간격은 16px로 맞춰주세요”라고 요청하는 식입니다. 디자인을 전공하지 않아도 이 정도 구분은 바로 써먹을 수 있습니다.

이번 글에서는 웹·앱 UI를 만들 때 자주 쓰는 용어를 화면 구조, 여백, 스타일, 동작 상태로 나눠 정리했습니다. Carbon·MDN·W3C 등의 설명을 참고했고, 비교 이미지는 직접 제작했습니다. 아래 요청문은 자신의 프로젝트에 맞게 바꿔 쓰는 예시이며, 특정 AI 도구의 결과 품질을 비교한 실험은 아닙니다.

## 화면 구조와 배치

먼저 화면에 무엇이 어디에 있는지부터 정합니다. 색이나 그림자보다 이 단계가 먼저입니다. 목록을 빠르게 훑어야 하는 서비스와 제품을 소개하는 랜딩 페이지는 필요한 구성이 다르기 때문입니다.

<Image src="/vibe-coding-ui-design-terms/00.png" alt="북마크 서비스 예시 화면에 내비게이션, 사이드바, 시각적 위계, 핵심 CTA, 3열 그리드와 카드 위치를 표시한 그림" />

각 용어가 가리키는 위치를 보여주려고 직접 만든 북마크 서비스 예시입니다.

- **레이아웃**(Layout): 화면 요소의 배치입니다. “왼쪽에 메뉴, 오른쪽에 콘텐츠”처럼 큰 구조를 설명할 때 씁니다.
- **와이어프레임**(Wireframe): 색과 장식을 덜어내고 구조·내용·기능의 위치를 보여주는 설계입니다. 첫 요청에서 완성 화면 대신 와이어프레임부터 확인하면 구조 수정에 집중하기 좋습니다.
- **내비게이션**(Navigation): 사용자가 다른 페이지나 주요 영역으로 이동하는 메뉴입니다. 상단 메뉴 바뿐 아니라 여러 형태가 있습니다. **사이드바**(Sidebar)는 화면 옆쪽 영역이며, 이동 메뉴나 필터 등을 담을 수 있습니다.
- **히어로 섹션**(Hero section): 랜딩 페이지 상단에서 핵심 메시지와 주요 행동을 강조하는 영역입니다. 모든 앱 화면에 큰 히어로가 필요한 것은 아닙니다. 작업용 대시보드라면 목록을 밀어내는 큰 배너가 오히려 불편할 수 있습니다.
- **그리드**(Grid): 콘텐츠를 행과 열에 맞춰 배치하는 방식입니다. **카드**(Card)는 제목·설명·이미지처럼 관련 정보를 묶은 단위입니다. “카드로 만들어주세요”와 “카드를 3열 그리드에 놓아주세요”는 서로 다른 요청입니다.
- **벤토 그리드**(Bento grid): 도시락 칸처럼 크기가 다른 블록을 조합한 배치를 가리키는 표현입니다. 특정 CSS 기능명이 아닙니다. 큰 기능 하나와 작은 보조 기능 여러 개를 소개할 때 고려할 수 있지만, 비슷한 항목을 비교하는 목록에서는 같은 크기의 카드가 더 적합할 수 있습니다.

북마크 관리 화면이라면 이렇게 요청할 수 있습니다.

> 데스크톱은 왼쪽 사이드바와 오른쪽 콘텐츠 영역의 2단 레이아웃으로 구성해주세요. 콘텐츠 상단에는 제목과 ‘새 북마크 추가’ 버튼을 두고, 아래에는 같은 구조의 카드를 3열 그리드로 배치해주세요. 작업 화면이므로 큰 히어로 배너는 넣지 말아주세요. 우선 와이어프레임을 보여주세요.

결과에서는 메뉴가 장식으로만 남아 있지 않은지, 제목이 긴 카드도 읽을 수 있는지, 주요 목록이 불필요하게 아래로 밀리지 않는지 봅니다. 벤토처럼 비대칭 배치를 요청했다면, 큰 블록에 들어간 정보가 실제로 더 중요한지도 확인해야 합니다.

## 패딩, 마진, 갭

**패딩**(Padding)은 요소의 테두리 안쪽 여백이고, **마진**(Margin)은 테두리 바깥 여백입니다. **갭**(Gap)은 그리드나 플렉스 배치에서 항목 사이에 두는 간격입니다. [MDN의 박스 모델 설명](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Box_model)을 보면 내용, 패딩, 테두리, 마진이 서로 다른 영역임을 확인할 수 있습니다.

<Image src="/vibe-coding-ui-design-terms/01-spacing.png" alt="카드 테두리 안쪽의 padding, 바깥쪽의 margin, 그리드 카드 사이의 gap을 구분한 도식" />

글이 카드 테두리에 붙어 있으면 패딩을, 카드끼리 붙어 있으면 갭을 먼저 확인합니다. 이미지의 색 영역은 위치 설명용이며, 실제 픽셀 값의 비율을 나타낸 것은 아닙니다.

**화이트스페이스**(Whitespace)는 글이나 이미지가 차지하지 않는 여유 공간을 뜻합니다. 흰색 배경만을 말하는 것은 아닙니다. 중요한 정보 주변을 비워 묶음을 구분하고 읽는 순서를 만드는 데 씁니다.

> 카드 안쪽 패딩은 24px, 카드 사이의 gap은 16px로 맞춰주세요. 페이지 바깥 좌우 여백과 카드 내부 여백은 따로 조정할 수 있게 해주세요. 제목과 설명 사이 간격은 카드 사이 간격보다 작게 유지해주세요.

이 수치는 시작점의 예시이지 정답은 아닙니다. 결과에서는 카드 안의 여유와 카드 사이의 여유가 각각 바뀌었는지 봅니다. 화면 전체를 넓히거나 글자를 줄여서만 문제를 해결했다면, 요청한 부분을 다시 짚어주는 편이 좋습니다.

## 타이포그래피와 시각적 위계

**타이포그래피**(Typography)는 글꼴만 고르는 일이 아닙니다. 크기, 굵기, 줄 간격, 글자 간격 등 글을 읽게 만드는 표현을 함께 다룹니다. **행간**(Line height)은 줄 사이의 간격에 영향을 주고, **자간**(Letter spacing)은 글자 사이 간격을 조절합니다.

**시각적 위계**(Visual hierarchy)는 무엇을 먼저 보고 다음에 무엇을 읽게 할지 정하는 관계입니다. [NN/g의 설명](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/)처럼 크기·색·대비·묶음 등으로 중요도를 드러냅니다. 모든 제목과 버튼을 크게 만든다고 위계가 선명해지는 것은 아닙니다.

**CTA**(Call to action)는 사용자가 하도록 유도하는 행동이나 그 행동을 제안하는 요소입니다. 북마크 화면의 ‘새 북마크 추가’, 가입 화면의 ‘계정 만들기’가 예입니다. 그중 현재 화면에서 가장 중요한 행동을 Primary CTA라고 부를 수 있습니다.

> 페이지 제목, 카드 제목, 본문, 보조 설명의 크기와 굵기를 구분해주세요. ‘새 북마크 추가’를 주된 CTA로 강조하고, ‘정렬’과 ‘필터’는 보조 버튼으로 표현해주세요. 설명은 작게 만들더라도 지나치게 연한 회색으로 처리하지 말아주세요.

여기서 확인할 것은 글꼴 이름보다 읽는 순서입니다. 제목보다 보조 버튼이 더 눈에 띄지는 않는지, 긴 한글 문장에서 행간이 답답하지 않은지, 실제 설명 문구를 넣어도 카드 높이가 버틸 수 있는지 살펴봅니다.

**대비**(Contrast)는 글자나 UI 요소가 주변과 구분되는 정도입니다. WCAG 2.2의 [텍스트 최소 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)은 일반 텍스트에 4.5:1 이상, 큰 텍스트에 3:1 이상을 요구합니다. 여기서 큰 텍스트는 18pt(24 CSS px) 이상 또는 굵은 글씨 14pt(약 18.7 CSS px) 이상을 말합니다. 비활성 요소·로고 등 예외도 있어, 모든 색 조합에 같은 숫자를 적용하는 규칙은 아닙니다. 특히 **보조 설명을 연하게 만든다는 이유로 읽을 수 없게 해서는 안 됩니다.**

## 플랫, 글래스모피즘, 뉴모피즘

구조가 정해졌다면 이제 표면의 느낌을 정할 수 있습니다. 이때 “미니멀하게”와 “글래스모피즘으로”는 같은 뜻이 아닙니다.

- **미니멀리즘**(Minimalism): 불필요한 요소를 줄이고 필요한 내용과 행동에 집중하는 방향입니다. 버튼 이름이나 입력 설명까지 지우라는 뜻은 아닙니다.
- **플랫 디자인**(Flat design): 입체적인 질감과 효과를 덜어내고 면·색·선 중심으로 표현하는 스타일입니다. [NN/g의 플랫 디자인 설명](https://www.nngroup.com/articles/flat-design/)은 클릭 가능한 요소의 단서를 지나치게 없애면 사용성이 나빠질 수 있다고 지적합니다.
- **글래스모피즘**(Glassmorphism): 반투명한 면과 배경 흐림 등을 이용해 유리 너머로 뒤쪽 레이어가 보이는 듯한 깊이를 표현합니다. [NN/g의 가이드](https://www.nngroup.com/articles/glassmorphism/)에서도 배경 변화에 따른 글자 대비를 주의점으로 다룹니다.
- **뉴모피즘**(Neumorphism): 배경과 비슷한 색의 면에 밝고 어두운 그림자를 더해 표면이 솟거나 눌린 듯 표현하는 스타일입니다. [IxDF의 설명](https://ixdf.org/literature/topics/neumorphism)처럼 낮은 대비 때문에 요소를 구분하기 어려울 수 있습니다.

<Image src="/vibe-coding-ui-design-terms/02-styles.png" alt="동일한 북마크 카드에 플랫, 반투명 유리 효과, 부드러운 양쪽 그림자를 적용한 스타일 비교" />

같은 제목·설명·버튼을 유지하고 HTML/CSS로 표면 표현만 바꾼 예시입니다.

자주 함께 쓰는 **보더 래디우스**(Border radius)는 모서리 둥글기, **섀도**(Shadow)는 그림자, **그레이디언트**(Gradient)는 색이 점진적으로 바뀌는 표현입니다. 스타일 이름이 막연하게 느껴지면 이 속성을 직접 지정해도 됩니다.

> 전체 화면은 플랫 스타일로 만들고, 카드 모서리는 12px로 통일해주세요. 유리 효과는 상단의 작은 안내 패널에만 적용해주세요. 입력창과 주요 버튼은 불투명하게 유지하고, 밝은 배경과 어두운 배경 모두에서 글자가 읽히는지 확인해주세요.

“글래스모피즘으로 전체를 바꿔주세요”보다 적용 범위를 제한한 요청입니다. 스타일이 마음에 들어도 폼·표·설정 화면까지 같은 효과를 확장할 필요는 없습니다. **효과가 아니라 읽기와 조작이 기준**이어야 합니다.

## 모달, 토스트, 탭과 입력 요소

버튼을 누른 뒤 어떤 형태로 내용을 보여줄지도 이름으로 구분할 수 있습니다. 디자인 시스템마다 세부 명칭과 변형은 다르므로, 이름과 함께 기대하는 동작을 적어주는 편이 안전합니다.

### 모달과 토스트

**모달**(Modal)은 현재 작업 위에 열려 사용자가 그 안의 작업에 집중하도록 하고, 뒤쪽 화면과의 상호작용을 제한하는 방식입니다. 삭제 확인이나 짧은 입력에 쓸 수 있습니다. 작은 창처럼 보인다고 모두 모달인 것은 아닙니다. 뒤쪽 화면을 계속 조작할 수 있는 창은 비모달일 수 있습니다.

<Image src="/vibe-coding-ui-design-terms/03-carbon-modal.png" alt="Carbon 공식 모달 구조도. 1 헤더, 2 본문, 3 버튼 영역, 4 닫기 버튼, 5 배경 오버레이가 표시돼 있다" />

출처: [Carbon Design System의 Modal anatomy](https://carbondesignsystem.com/components/modal/usage/). 공식 저장소의 이미지를 수정 없이 사용했습니다. [Apache 2.0 라이선스 및 출처 정보](/images/blog/vibe-coding-ui-design-terms/CARBON-LICENSE.txt), 2026년 9월 22일 확인.

이 그림에서 1은 헤더, 2는 본문, 3은 하단 버튼 영역, 4는 닫기 버튼, 5는 배경 오버레이입니다. **오버레이**(Overlay)는 기존 화면 위에 겹쳐지는 레이어를 뜻하며, 여기서는 모달 뒤쪽을 덮는 배경입니다. 어두운 배경만 추가했다고 키보드 동작까지 갖춘 모달이 완성되는 것은 아닙니다.

[W3C의 모달 대화상자 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)에서는 열릴 때 초점을 안으로 옮기고, Tab 이동을 내부에서 유지하며, 닫은 뒤에는 일반적으로 실행 버튼으로 초점을 돌려주는 동작 등을 설명합니다.

**토스트**(Toast)는 작업 흐름을 크게 끊지 않고 결과를 알려주는 알림 형태입니다. “저장했습니다”처럼 짧은 확인에 고려할 수 있습니다. [Carbon의 알림 가이드](https://carbondesignsystem.com/components/notification/usage/)처럼 알림의 긴급도와 사용자의 조치 필요성을 함께 판단해야 합니다. 고쳐야 할 입력 오류나 반드시 읽어야 하는 실패 안내를 금방 사라지는 토스트에만 담는 것은 피하는 편이 좋습니다.

> 북마크 삭제는 제목과 취소·삭제 버튼이 있는 확인 모달을 사용해주세요. 열릴 때 모달 내부로 포커스를 옮기고, Esc나 취소로 닫으면 원래 삭제 버튼으로 돌려주세요. 저장 성공은 작업을 막지 않는 토스트로, 저장 실패는 원인을 읽고 재시도할 수 있는 지속적인 안내로 보여주세요.

### 탭, 아코디언, 드롭다운

**탭**(Tabs)은 관련 콘텐츠 패널을 전환하는 요소입니다. ‘프로필 / 알림 설정’처럼 같은 맥락의 내용을 나눌 때 고려할 수 있습니다. 다른 주소로 이동하는 사이트 메뉴는 모양이 비슷해도 내비게이션일 수 있습니다.

**아코디언**(Accordion)은 제목을 눌러 해당 영역의 내용을 펼치거나 접는 구성입니다. 자주 묻는 질문이나 고급 설정처럼 처음부터 모두 펼칠 필요가 없는 내용에 쓸 수 있습니다. 반드시 입력해야 하는 항목을 접힌 곳에 숨기는 것은 주의해야 합니다.

**드롭다운**(Dropdown)은 눌렀을 때 아래로 펼쳐지는 형태를 넓게 부르는 표현입니다. 값을 고르는 셀렉트인지, ‘이름 변경 / 삭제’ 같은 명령 메뉴인지 지정해야 합니다. **콤보박스**(Combobox)는 입력과 선택 팝업을 결합하는 패턴으로, 구현에 따라 검색·입력 가능한 형태 등이 있습니다. 검색이 필요하다면 그 조건을 따로 적습니다.

> 정렬은 ‘최근 저장순 / 제목순’ 중 하나를 고르는 셀렉트로 만들어주세요. 카테고리는 검색 가능한 콤보박스로 만들고, 선택지가 없을 때의 안내도 넣어주세요. 추가 설정은 아코디언에 두되 필수 입력 항목은 접지 말아주세요.

**툴팁**(Tooltip)은 요소의 짧은 부가 설명입니다. hover 때만 보여주면 터치 기기나 키보드 사용자에게 전달되지 않을 수 있습니다. 필수 입력 조건·오류 해결 방법은 툴팁에만 숨기지 말고 화면에 읽을 수 있는 텍스트로 두는 편이 낫습니다.

## 호버, 포커스와 화면 상태

AI에게 기본 화면만 요청하면 정상 데이터가 있는 모습만 만들어질 수 있습니다. 실제 서비스에는 마우스를 올린 상태, 저장 중인 상태, 데이터가 없는 상태도 필요합니다.

- **호버**(Hover): 포인터를 요소 위에 올린 상태입니다. 터치 화면에는 같은 방식이 없을 수 있으므로 중요한 기능을 호버에만 숨기지 않습니다.
- **포커스**(Focus): 키보드 입력 등을 받을 대상이 된 상태입니다. Tab으로 이동했을 때 현재 위치가 보여야 합니다. [W3C의 Focus Visible 설명](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)은 키보드로 조작할 수 있는 요소의 초점 표시를 다룹니다.
- **선택됨과 비활성**(Selected / Disabled): 현재 선택된 값과 지금 조작할 수 없는 상태입니다. 둘은 다른 의미이므로 같은 표현으로 처리하지 않습니다. 비활성의 이유도 사용자가 알 수 있어야 합니다.
- **로딩**(Loading): 요청을 처리하거나 데이터를 가져오는 중입니다. **스켈레톤**(Skeleton)은 들어올 콘텐츠의 대략적인 모양을 먼저 보여주는 로딩 표현입니다. 진짜 데이터처럼 보이는 임의 숫자를 채우는 것과는 다릅니다.
- **빈 상태**(Empty state): 아직 데이터가 없거나 검색 결과가 없는 화면입니다. 처음 방문한 경우에는 시작할 행동을, 검색 결과가 없는 경우에는 검색어 변경이나 필터 해제를 안내할 수 있습니다.
- **오류 상태**(Error state): 실패한 작업과 해결 방법을 알려주는 상태입니다. 빨간 테두리뿐 아니라 무엇을 고쳐야 하는지 텍스트로 전달합니다.

> 북마크 목록에 로딩, 첫 저장 전, 검색 결과 없음, 불러오기 실패 상태를 각각 만들어주세요. 저장 버튼은 요청 중에 중복 클릭을 막고 ‘저장 중’이라고 표시해주세요. 실패하면 입력값을 유지하고 재시도할 수 있게 해주세요. 키보드로 이동할 때는 포커스 표시가 보이게 해주세요.

이 부분은 완성 스크린샷 한 장으로 확인할 수 없습니다. 느린 응답, 빈 검색 결과, 실패 응답을 각각 재현해봐야 합니다. 모달도 직접 열고 닫으며 Tab·Shift+Tab·Esc 동작을 확인해야 합니다.

## 반응형과 브레이크포인트

**반응형 디자인**(Responsive design)은 화면 공간과 환경에 맞게 콘텐츠 배치를 조정하는 방식입니다. **브레이크포인트**(Breakpoint)는 열 수나 메뉴 형태 같은 배치 규칙을 바꾸는 기준점입니다. [MDN의 반응형 디자인 설명](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design)처럼 화면이 깨지는 지점을 기준으로 조정하는 것이 중요합니다.

“모바일 대응해주세요”라고만 적으면 모든 요소를 작게 축소한 화면이 나올 수 있습니다. 남길 정보와 바꿀 배치를 정해주는 편이 좋습니다.

> 넓은 화면에서는 카드 3열, 중간 폭에서는 2열, 좁은 화면에서는 1열로 배치해주세요. 사이드바는 좁은 화면에서 메뉴 버튼으로 접고, 검색과 ‘새 북마크 추가’는 계속 사용할 수 있게 해주세요. 본문 글자 크기를 줄여 억지로 맞추지 말고, 카드가 답답해지는 지점을 기준으로 브레이크포인트를 제안해주세요.

결과는 예쁜 모바일 캡처 한 장보다 폭을 연속으로 줄여보는 방식으로 확인합니다. 긴 제목이나 오류 문구를 넣었을 때 가로 스크롤이 생기는지, 화면을 확대해도 버튼과 입력칸을 사용할 수 있는지도 봅니다. 메뉴를 접었다면 열기·닫기와 키보드 접근도 함께 확인합니다.

## 컴포넌트와 디자인 토큰

**컴포넌트**(Component)는 버튼·입력창·카드처럼 반복해서 사용하는 UI 단위입니다. 화면마다 버튼을 따로 만들면 조금씩 높이·색·모서리가 달라질 수 있습니다. 기존 프로젝트에 공통 버튼이 있다면 그 규칙을 재사용하도록 요청하는 편이 좋습니다.

**디자인 토큰**(Design token)은 색, 간격, 글자 크기 같은 디자인 값에 이름을 붙여 공유하는 방식입니다. [Design Tokens Community Group의 설명](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/)도 사람이 읽을 수 있는 이름과 값을 기본으로 다룹니다. 예를 들어 화면마다 초록색 값을 직접 넣기보다 `color.action.primary`처럼 역할을 나타내는 이름으로 관리할 수 있습니다.

> 기존 버튼·입력창 컴포넌트를 먼저 확인하고 재사용해주세요. 기본 간격과 모서리 둥글기, 주요 색은 공통 토큰으로 관리해주세요. 화면마다 새로운 값을 추가하기 전에 기존 값으로 표현할 수 있는지 확인해주세요. 기존 디자인 시스템이 있다면 다른 라이브러리로 교체하지 말아주세요.

여기서 중요한 것은 파일 이름이 아니라 수정 범위입니다. 주요 버튼 색을 바꿨을 때 다른 페이지의 같은 역할 버튼도 함께 바뀌는지, 오류 색과 브랜드 색을 구분해서 관리할 수 있는지 확인합니다.

## AI에게 전달할 화면 제작 요청문

용어를 모두 외운 뒤 요청할 필요는 없습니다. **어떤 화면인지, 바꿀 부분은 어디인지, 어떤 상태까지 필요한지**를 순서대로 적으면 됩니다. 아래는 북마크 관리 화면에 맞춘 예시입니다. 새 화면이라면 전체를, 이미 만든 화면을 고치는 경우라면 필요한 부분만 가져가면 됩니다.

```text
북마크 관리 화면의 UI를 만들어주세요.
목표는 저장한 자료를 빨리 찾고 새 북마크를 추가하는 것입니다.

1. 기존 프로젝트 확인
- 현재 UI 컴포넌트와 디자인 토큰을 먼저 확인해 재사용해주세요.
- 로그인, API, 데이터 저장 로직은 임의로 바꾸지 말아주세요.
- 실제 사용자 데이터 대신 샘플 데이터로 화면을 확인해주세요.

2. 구조
- 먼저 내비게이션, 사이드바, 콘텐츠 영역의 와이어프레임을 보여주세요.
- 콘텐츠 상단에는 제목, 검색, ‘새 북마크 추가’를 배치해주세요.
- 카드 그리드는 넓은 화면 3열, 중간 폭 2열, 좁은 화면 1열로 구성해주세요.
- 큰 히어로 배너는 필요하지 않습니다.

3. 시각 규칙
- 플랫 스타일을 기본으로 하고 주요 CTA만 강조해주세요.
- 카드 padding은 24px, gap은 16px, 모서리는 12px를 시작점으로 제안합니다.
- 기존 토큰과 충돌하면 기존 값과 차이를 설명한 뒤 조정해주세요.
- 제목, 본문, 보조 설명의 위계와 읽을 수 있는 대비를 유지해주세요.

4. 상태와 조작
- 로딩, 첫 저장 전, 검색 결과 없음, 실패 상태를 분리해주세요.
- 저장 중 중복 클릭 방지, 실패 시 입력값 유지와 재시도를 지원해주세요.
- 삭제 확인 모달은 포커스 이동, Tab 순환, Esc 닫기를 지원해주세요.
- 저장 성공은 토스트로, 수정이 필요한 오류는 지속적인 안내로 표시해주세요.
- 버튼과 입력창에 키보드 포커스가 보이게 해주세요.

5. 검수 결과
- 데스크톱과 모바일 화면을 각각 보여주세요.
- 긴 제목, 좁은 화면, 확대, 키보드 조작, 실패 상태를 확인해주세요.
- 확인한 항목과 아직 확인하지 못한 항목을 구분해서 알려주세요.
```

참고 이미지를 함께 전달한다면 “이것과 똑같이” 대신 가져올 특징을 지정해보세요. “왼쪽 이미지에서는 메뉴 구조만, 오른쪽 이미지에서는 카드 간격만 참고하고 색과 문구는 우리 서비스에 맞춰주세요”처럼 적을 수 있습니다. 직접 캡처한 화면이라도 사용자 이름·이메일·운영 데이터·비밀키가 들어 있지 않은지 먼저 확인해야 합니다.

첫 결과를 보고 수정할 때도 범위를 좁힙니다.

> 레이아웃과 색은 유지해주세요. 카드 안쪽 패딩만 늘리고, 주요 CTA와 보조 버튼의 강조 차이를 더 분명하게 해주세요. 모바일에서 제목이 길어질 때 버튼을 밀어내는 문제도 함께 수정해주세요. API와 데이터 구조는 변경하지 말아주세요.

저라면 스타일 이름을 많이 넣는 것보다, **구조를 먼저 맞추고 간격과 상태를 하나씩 확인하는 순서**로 요청하겠습니다. “고급스럽게”는 서로 다른 화면을 떠올리게 하지만, “카드 안쪽 여백”과 “저장 실패 뒤 입력값 유지”는 함께 확인할 수 있는 조건이 됩니다.

게임 화면을 만드는 경우에는 [바이브코딩 게임 개발에 필요한 디자인 용어](/blog/vibe-coding-game-design-terms)에서 HUD·스프라이트·판정 영역을 이어서 볼 수 있습니다. UI가 정리된 뒤 실제 공개를 준비한다면 [바이브코딩 서비스 배포 전 보안 체크리스트](/blog/vibe-coding-security-checklist)도 별도로 확인해주세요. 화면이 잘 보이고 잘 눌리는 것과 사용자 데이터가 안전한 것은 다른 검증입니다.
