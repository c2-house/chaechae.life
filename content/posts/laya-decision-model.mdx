고객 문의를 결제팀과 기술지원팀 중 어디로 보낼지 고르는 데 꼭 긴 답변을 생성하는 AI가 필요할까요? 원하는 결과가 정해진 후보 하나라면, 문장을 생성하고 다시 JSON으로 읽어 들이는 과정을 줄일 수 있습니다.

**Laya는 이런 제한된 판단을 내 컴퓨터나 서버에서 실행하는 결정 모델**입니다. 질문에 답장을 써주는 챗봇이 아니라, 개발자가 정한 선택지·점수·확률을 반환하는 부품에 가깝습니다. 문의 분류나 처리 경로 추천에 붙일 수 있지만, 모델이 내놓은 판단을 곧바로 환불·계정 해지 권한으로 연결하는 것은 다른 문제입니다.

이번 글은 2026년 10월 7일의 공식 저장소, 모델 카드와 문서를 바탕으로 활용 범위를 살펴봅니다. 확인한 Python 패키지는 `laya` 0.3.28입니다. **모델 가중치를 내려받아 추론하거나 속도를 측정하지는 않았으며**, 아래 성능 수치는 프로젝트가 공개한 조건과 함께 읽어야 합니다.

## 챗봇과 다른 결정 모델

Laya의 공식 연결 경로는 [NandhaKishorM/laya 저장소](https://github.com/NandhaKishorM/laya), 그 저장소가 안내하는 [공식 문서](https://nandhakishorm.github.io/laya/), [convaiinnovations/laya 모델 카드](https://huggingface.co/convaiinnovations/laya)입니다. 저장소와 문서는 개발 주체를 **Convai Innovations**로 표시합니다. 검색에 나오는 `laya-ai.com`은 스스로 독립 커뮤니티 자료라고 밝히고 있으므로 공식 개발사 사이트와 구분해야 합니다.

공식 설명의 **System 1**은 빠르고 범위가 정해진 판단을 가리킵니다. 사람의 직관 전체를 구현했다는 의미는 아닙니다. Laya는 문장을 토큰 하나씩 이어 쓰는 대신 입력과 질문을 받아 한 번의 순전파로 판단을 계산하는 비자기회귀 모델입니다. 순전파는 입력을 신경망에 통과시켜 출력을 계산하는 과정이라고 이해하면 됩니다.

예를 들어 ‘배송 지연을 사과하는 답장을 써줘’는 생성형 모델의 일입니다. 반면 ‘이 문의를 배송·결제·기타 중 어디로 보낼까’는 Laya에 맞는 질문 형태입니다. 문장을 생성하지 않으니 자유 형식 답변을 파싱하는 문제는 줄지만, **유효한 선택지를 반환한다고 내용까지 맞는 것은 아닙니다.**

[Jev를 소개한 이전 글](/blog/jev-typed-decisions)과 질문 형식은 비슷합니다. 이번에 살펴볼 차이는 그 판단 기능을 로컬에 두고, 공개된 가중치와 코드로 업무에 맞게 조정할 수 있다는 점입니다. Jev보다 무조건 정확하거나 빠르다는 결론과는 구분해야 합니다.

## 문의 분류에 적용하는 세 가지 질문

Laya에 보내는 `state`는 판단할 텍스트나 JSON이고, `questions`는 질문 형식과 기준입니다. 같은 문의에 대해 담당 부서, 긴급도, 환불 요청 여부를 각각 물을 수 있습니다.

| 질문 형식 | 문의 처리에 넣을 질문 | 결과의 의미 |
| --- | --- | --- |
| `choice` | 결제·기술지원·기타 중 어느 부서에 보낼지 | 선택한 후보와 후보별 확률 |
| `score` | 낮음·보통·긴급 중 어느 수준인지 | 순서가 있는 단계의 확률 가중 점수 |
| `noul` | 고객이 환불을 요청했는지 | yes에 해당하는 확률인 P(true) |

세 형식을 모두 써야 하는 것은 아닙니다. 부서 분류가 목적이라면 `choice` 하나로 시작하는 편이 오답의 원인을 찾기 쉽습니다. 선택지 이름만 `A`, `B`로 두지 말고 각각 어떤 문의를 뜻하는지 설명도 넣어야 합니다.

<Image src="/laya-decision-model/01-questions.png" alt="Laya 공식 문서에 표시된 choice, noul, score 질문과 반환값 예제" caption="공식 Questions and answers 문서를 직접 캡처했습니다. 화면의 숫자는 문서 예제이며 이번 로컬 실행 결과가 아닙니다. 2026년 10월 7일 확인." />

[질문과 응답 문서](https://nandhakishorm.github.io/laya/questions-and-answers/)에서 `score`는 가장 유력한 단계 번호가 아니라 **단계별 확률을 가중한 값**입니다. 따라서 소수 점수가 나올 수 있고, 이를 반올림한 단계가 항상 가장 확률 높은 단계인 것도 아닙니다. `noul`의 낮은 값은 ‘자신이 없다’가 아니라 ‘아니오 쪽으로 판단했다’에 가깝습니다.

실제 적용을 상상해보면 역할이 더 분명해집니다. 아래는 실행 결과가 아니라 문의 처리 설계 예입니다.

1. 주문번호와 중복 청구 여부는 기존 서비스 코드가 확인합니다.
2. Laya는 문의를 어느 부서에 보낼지 추천합니다.
3. 모호한 문의나 검증 기준을 통과하지 못한 결과는 사람이 검토합니다.
4. 환불은 별도의 권한 검사와 승인 절차를 거쳐 실행합니다.

이때 모델이 ‘환불 요청이 있다’고 판단하는 것과 ‘환불해도 된다’는 것은 다릅니다. 문의 분류 모델에 결제 정책이나 사용자의 권한까지 맡기지 않는 것이 중요합니다.

## 로컬 실행 조건과 체크포인트

공식 설치 안내는 Python 3.10 이상을 요구하며 Windows, macOS, Linux용 환경 구성을 설명합니다. PyTorch 기반으로 CPU에서도 실행할 수 있고, 지원 환경에 맞춰 CUDA나 MPS 같은 가속 경로를 사용할 수 있습니다. 다만 ‘로컬에서 실행 가능’은 모든 노트북에서 같은 속도가 나온다는 뜻이 아닙니다.

Laya에는 용도가 다른 체크포인트가 있습니다. 체크포인트는 학습된 모델 가중치와 설정의 묶음입니다.

| 체크포인트 | 기반 모델·파라미터 수 | 먼저 검토할 입력 |
| --- | --- | --- |
| `laya` | ModernBERT-large·421M | 영어 분류 작업 |
| `laya-multilingual` | mmBERT-base·322M | 한국어를 포함한 다국어 입력 |
| `laya-typed-decisions` | ModernBERT-large·421M | 해당 미세조정 업무와 비슷한 판단 작업 |

**기본 `laya` 체크포인트는 영어용**입니다. 프로젝트 전체가 다국어를 지원한다는 설명을 영어용 가중치에도 그대로 적용하면 안 됩니다. `Router`는 입력 언어를 판단해 영어용과 다국어용 모델 사이에서 경로를 고릅니다. 어떤 체크포인트가 선택됐는지는 결과의 `routing.model`로 확인할 수 있습니다.

<Image src="/laya-decision-model/02-model-card.png" alt="Hugging Face의 convaiinnovations/laya 모델 카드와 Apache 2.0 라이선스 표시" caption="공식 저장소가 연결하는 Hugging Face 모델 카드의 실제 화면입니다. 프로젝트 전체 소개와 개별 체크포인트의 용도를 구분해서 읽어야 합니다. 2026년 10월 7일 확인." />

[공식 설치·Quickstart](https://github.com/NandhaKishorM/laya#installation-details)를 따라 시작할 때는 새 가상환경에 `laya`를 설치하고, `Router()`를 만든 뒤 짧은 입력과 `choice` 질문 하나를 보내는 순서입니다. 첫 사용에는 체크포인트 다운로드와 로딩이 필요합니다. 처음부터 `Router(preload=True)`로 세 모델을 모두 올리면 메모리 부담도 커지므로, 메모리 부족을 해결하는 옵션으로 사용하면 안 됩니다.

이번 환경에는 PyTorch와 Transformers가 설치돼 있지 않았고, 기본 모델의 `model.safetensors` 파일 하나만 약 843MB였습니다. 추가 라이브러리와 모델 다운로드가 필요해 이번에는 설치·추론까지 진행하지 않았습니다. **이 파일 크기는 실행에 필요한 RAM 수치가 아닙니다.** 실제 메모리는 로딩할 모델 수, 자료형, 입력 길이, 배치 크기와 런타임에 따라 달라집니다.

문서 길이도 고려해야 합니다. 영어용의 기본 문맥 길이는 512토큰이고, 다국어용과 typed-decisions는 기본 1,024토큰입니다. 이 안에는 본문뿐 아니라 질문과 선택지 설명도 들어갑니다. 다국어용은 `max_len=8192`로 최대 8,192토큰을 읽도록 설정할 수 있지만, 길이를 늘리는 것만으로 긴 문서의 판단 품질이 유지되지는 않습니다.

로컬 SDK 경로와 외부 데모도 구분해야 합니다. 가중치를 준비해 자체 실행하는 경로는 외부 추론 API로 입력을 보내는 방식과 다르지만, 웹 Playground에 넣은 고객 정보까지 로컬에 머무르는 것은 아닙니다. 처음에는 개인정보 없는 샘플로 확인하는 편이 좋겠습니다.

## 미세조정과 확률 보정

Laya가 유용해 보이는 지점은 공개된 모델을 자기 업무에 맞게 조정할 수 있다는 점입니다. 반대로 **설치 직후 아무 판단이나 잘하는 범용 모델로 기대하면 곤란합니다.**

[공식 벤치마크](https://github.com/NandhaKishorM/laya/blob/main/BENCHMARKS.md)의 typed-decisions 평가에서 기본 영어용 모델은 정확도 0.362, 다국어용은 0.352로 보고돼 있습니다. 해당 평가에서 가장 흔한 답만 고르는 기준선은 0.461입니다. 프로젝트가 강조하는 0.766은 같은 기본 모델을 그대로 사용한 수치가 아니라, 해당 벤치마크의 학습 분할로 미세조정한 `laya-typed-decisions`의 보고값입니다. 문서에는 이 미세조정 행의 원본 결과 파일이 아직 커밋돼 있지 않다는 주석도 있습니다.

따라서 이 숫자를 새 회사의 문의 분류 정확도로 가져오면 안 됩니다. 자기 업무의 정답 데이터를 모아 일부는 학습에 쓰고, 따로 남긴 데이터로 성능을 확인해야 합니다. 학습하지 않은 입력에 바로 적용하는 **제로샷**은 시작점을 보는 용도로 생각하는 편이 낫습니다.

확률도 따로 확인해야 합니다. Laya의 `choice`와 `score`에서 `confidence`는 분포가 얼마나 한쪽으로 몰렸는지를 나타내고, `answer_confidence`는 가장 확률 높은 답의 확률입니다. `noul` 값 자체는 P(true)이므로, 어느 쪽이든 더 유력한 답을 나타내는 `answer_confidence`와 의미가 다를 수 있습니다.

공식 문서는 출고 상태의 기본 체크포인트가 공개 평가에서 과신하는 경향을 설명합니다. **0.9라는 숫자가 나왔다고 실제로 열 번 중 아홉 번 맞는다고 간주할 수는 없습니다.** 확률 보정은 이런 숫자와 실제 정답 비율을 맞추는 과정입니다. 보정에 쓴 자료와 평가 자료를 분리하고, 실제 사용할 선택지 수와 언어에서 기준을 확인해야 합니다.

예를 들어 부서 세 개를 분류하며 정한 자동 처리 기준을 부서 스무 개짜리 질문에 그대로 옮기지 않는 편이 좋습니다. Jev와 Laya의 `confidence` 계산 방식도 같지 않아, 기존 Jev 서비스의 임계값을 복사하는 것으로 전환 검증을 대신할 수 없습니다.

## 속도 수치와 실제 업무의 한계

Laya 소개에서 자주 나오는 약 33ms는 모든 컴퓨터의 응답 시간이 아닙니다. 공식 벤치마크는 Tesla T4에서 질문 하나를 처리한 `laya-multilingual`의 32.8ms를 제시합니다. 같은 표의 영어용 `laya`는 39.5ms입니다. 처음 모델을 내려받고 올리는 시간, CPU 실행, 긴 입력, 여러 질문을 처리하는 상황은 나누어 봐야 합니다.

<Image src="/laya-decision-model/03-benchmarks.png" alt="Laya 공식 벤치마크 안내에서 데이터셋, 체크포인트, 하드웨어 조건을 구분한 표" caption="공식 Benchmarks and known limits 문서의 실제 캡처입니다. Jev 비교가 동일 조건의 직접 대결 실험이 아니라는 설명도 포함돼 있습니다. 2026년 10월 7일 확인." />

[벤치마크 조건 안내](https://nandhakishorm.github.io/laya/benchmarks/)는 Jev 수치를 다른 연구의 공개 결과에서 가져왔으며 질문과 표본 수가 다르다고 명시합니다. 그래서 ‘Laya가 Jev보다 몇 배 빠르고 더 정확하다’는 순위로 단정하기보다, 내 입력을 어느 하드웨어에서 어떤 품질로 처리할지 판단하는 자료로 보는 편이 좋습니다.

활용할 때 특히 확인할 부분은 다음과 같습니다.

- **한국어 품질:** 다국어용은 한국어 입력을 지원하지만 지원 언어 목록이 업무 정확도를 보증하지는 않습니다. 공식 MASSIVE 20선택지 평가의 한국어 행은 다국어용 정확도 0.470으로 보고됩니다. 내 고객 문의와 같은 과제의 점수가 아니므로 실제 한국어 샘플로 따로 평가해야 합니다.
- **많은 선택지:** 기본 설정에서 선택지가 많아지면 짧은 토큰 예산을 나눠 쓰느라 설명이 잘릴 수 있습니다. 후보를 먼저 좁히거나 큰 분류 뒤에 작은 분류를 붙이는 방식을 검토할 수 있습니다. 최신 버전에는 후보를 묶어 단계적으로 비교하는 기능도 있지만, 추가 추론과 후보 축소 뒤의 확률 해석을 함께 고려해야 합니다.
- **부정문과 표현 순서:** 공식 문서에는 ‘계정을 해지하지 말라’는 입력을 해지로 고른 사례, 선택지 순서에 따라 답이 바뀐 사례가 있습니다. 높은 확률만으로 이런 오류를 걸러낼 수 있다고 가정하면 안 됩니다.
- **점수와 안전 판정:** 다국어용의 `score`는 첫 단계에 대한 편향이 보고돼 있고, 공개 평가의 유해성 분류도 약점으로 명시돼 있습니다. 보안 검사나 콘텐츠 차단의 유일한 판단 근거로 두기에는 별도 검증이 필요합니다.

Laya가 문장을 생성하지 않는다는 특징은 틀린 판단까지 없앤다는 뜻이 아닙니다. 자동화를 붙인다면 성공 사례만 모으기보다 부정문, 복합 요청, 정보 부족, 범위 밖 문의에서 멈추거나 사람에게 넘길 수 있는지 확인하는 것이 더 중요합니다.

## 공개 가중치를 활용할 범위

Laya는 가중치만 공개된 모델에 그치지 않고, 추론 코드와 미세조정 코드도 공개합니다. 공식 저장소의 코드와 기본 모델 카드는 Apache 2.0을 명시합니다. 따라서 ‘오픈 가중치’와 ‘공개 소스 코드’를 모두 확인할 수 있습니다. 다만 이것이 모든 학습 데이터의 재배포 권리나 제3자 서비스의 이용 조건까지 같다는 뜻은 아닙니다.

Apache 2.0은 상업적 사용을 허용하는 라이선스지만, 재배포 때의 라이선스·고지 의무를 지켜야 하고 상표 사용권이나 무상 보증을 제공하지는 않습니다. 외부에서 변환한 모델이나 별도 런타임을 사용한다면 해당 저장소의 조건도 확인해야 합니다. 로컬 실행에는 외부 모델 API의 호출 요금이 없더라도 장비, 전력, 운영과 학습 비용은 남습니다.

저라면 처음부터 결제 승인이나 계정 해지를 맡기기보다, **사람이 쉽게 되돌릴 수 있는 분류 추천**부터 검토하겠습니다. 기존 처리 흐름을 바꾸지 않고 Laya의 추천과 담당자의 실제 선택을 비교한 뒤, 어느 입력까지 자동 처리할 수 있는지 정하는 방식입니다. 답장 작성은 생성형 모델에, 계산과 권한 검사는 코드에 남겨두면 Laya를 쓸 자리도 더 분명해집니다.
