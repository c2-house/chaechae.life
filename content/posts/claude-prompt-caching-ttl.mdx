긴 문서와 시스템 지침을 매번 Claude API에 보내는 작업이라면 프롬프트 캐싱이 눈에 들어옵니다. 그런데 5분 캐시보다 1시간 캐시가 더 오래 유지되니, 처음부터 1시간으로 설정하는 편이 좋을까요?

**같은 앞부분을 짧은 간격으로 계속 재사용한다면, 이 글에서 비교한 Sonnet 4.6에서는 5분 캐시가 더 저렴합니다.** 반대로 사람이 답변을 읽거나 다른 Agent의 작업을 기다리느라 5분 캐시를 놓치는 경우에는 1시간 캐시가 유리해질 수 있습니다. 중요한 것은 전체 작업 시간보다 **동일한 내용을 다시 쓰는 간격과 횟수**입니다.

2026년 9월 19일 공식 문서와 요금표를 확인하고, Claude Sonnet 4.6의 요청 패턴별 비용을 Python으로 계산해봤습니다. 아래 숫자는 가정한 토큰 수에 요금을 적용한 계산 결과입니다. 유료 API 호출이나 실제 캐시 적중률·응답 속도를 측정한 실험은 아니며, Claude 구독료가 아닌 직접 API의 표준 요금을 다룹니다.

## 답변이 아닌 프롬프트 앞부분의 재사용

프롬프트 캐싱은 이전 답변을 저장해 그대로 돌려주는 응답 캐시와 다릅니다. 이미 처리한 입력의 앞부분, 즉 **prefix**를 다시 활용하는 기능입니다. 캐시 대상으로 지정한 지점까지 `tools`, `system`, `messages` 순서의 내용이 포함되며, 뒤에 새로운 질문을 붙여도 앞부분이 일치하면 재사용할 수 있습니다.[1]

예를 들어 같은 제품 설명서로 여러 질문에 답하는 서비스를 생각해보겠습니다. 도구 정의와 시스템 지침, 제품 설명서는 유지하고 사용자의 질문만 바꿉니다. 이때 캐시 경계인 **breakpoint**를 고정된 설명서의 끝에 두면, 반복되는 자료와 매번 바뀌는 질문을 나눌 수 있습니다.[1]

다만 내용이 대략 비슷하다고 캐시에 적중하는 것은 아닙니다. 해당 경계까지의 텍스트와 이미지가 정확히 일치해야 하며, 도구 정의 변경도 뒤에 이어지는 캐시에 영향을 줍니다.[1] 따라서 요청마다 달라지는 시각이나 요청 ID를 맨 앞에 넣는 구조라면, TTL을 늘리기 전에 입력 구성부터 살펴보는 편이 좋습니다.

## 5분과 1시간의 쓰기·읽기 비용

Sonnet 4.6의 직접 API 요금은 다음과 같습니다. 단위는 **백만 토큰당 미국 달러**입니다.[2][3] 아래 계산에는 Batch 할인, 데이터 지역 지정에 따른 할증, 별도 도구 비용과 세금을 넣지 않았습니다.

| 처리 방식 | 백만 토큰당 요금 |
| --- | ---: |
| 일반 입력 | $3.00 |
| 5분 캐시 쓰기 | $3.75 |
| 1시간 캐시 쓰기 | $6.00 |
| 캐시 읽기 | $0.30 |
| 출력 | $15.00 |

캐시를 처음 만들 때는 일반 입력보다 비쌉니다. 대신 같은 prefix를 다시 읽을 때 비용이 낮아집니다. 이 모델에서 읽기는 일반 입력 단가의 10%지만, **첫 쓰기와 비캐시 입력, 출력까지 모두 90% 할인되는 것은 아닙니다.** 다른 Claude 모델에 이 배율을 그대로 적용하지 말고 모델별 요금표를 확인해야 합니다.[2]

### 캐시 적중과 수명 갱신

5분 캐시는 처음 만들어진 뒤 무조건 5분 후 끊기는 고정 구간이 아닙니다. 캐시에 적중할 때마다 수명이 갱신되며, 갱신을 위한 별도 쓰기 비용은 없습니다. 물론 캐시 읽기 요금은 부과됩니다.[1][2]

따라서 전체 작업이 오래 걸려도 같은 prefix에 대한 요청이 계속 5분보다 짧은 간격으로 이어진다면, 단지 작업 시간이 길다는 이유로 1시간 캐시를 선택할 필요는 없습니다.

또 하나 중요한 조건은 **TTL이 응답 완료 시점이 아니라 캐시를 쓰거나 읽는 요청의 시작 시점부터 계산된다는 것**입니다. 응답을 생성하는 동안에도 시간이 흐릅니다.[1] 긴 답변 생성 후 사용자의 검토까지 기다리는 작업이라면, 답변을 받은 뒤의 대기 시간만 재서는 안 됩니다.

## 요청 간격별 6회 합산 비용

비교를 위해 다음 조건을 고정했습니다.

- 매번 재사용할 prefix: 20,000토큰
- prefix 뒤에 붙는 비캐시 입력: 요청마다 1,000토큰
- 출력: 요청마다 500토큰
- 요청 횟수: 6회, 첫 요청에는 캐시가 없는 상태
- 고정 prefix 끝에 명시적 breakpoint 하나를 두고, 그 밖의 캐시 관련 설정은 유지

토큰 수는 계산을 위한 가정입니다. 특정 문서를 토큰화한 결과가 아니고, 응답이 매번 정확히 500토큰 나온다는 보장도 아닙니다. 두 번째 요청 전에 첫 캐시를 사용할 수 있게 된 상황을 전제로 했습니다.

아래의 10분·70분 간격 사례는 **다음 요청 전에 해당 TTL의 캐시가 만료·삭제되어 미스가 난 경우**를 가정합니다. 공식 문서는 TTL을 최소 수명으로 설명하고, 그 이후 즉시 삭제되는 것은 아니라고 안내합니다.[1] 따라서 “10분 뒤 요청하면 반드시 미스”라는 실측 결과로 읽으면 안 됩니다.

| 요청 패턴 | 5분 캐시 쓰기 / 읽기 | 5분 캐시 총액 | 1시간 캐시 쓰기 / 읽기 | 1시간 캐시 총액 |
| --- | --- | ---: | --- | ---: |
| 동일 prefix, 1분 간격 | 1회 / 5회 | $0.168 | 1회 / 5회 | $0.213 |
| 동일 prefix, 10분 간격 | 6회 / 0회 | $0.513 | 1회 / 5회 | $0.213 |
| 동일 prefix, 70분 간격 | 6회 / 0회 | $0.513 | 6회 / 0회 | $0.783 |
| 매번 다른 prefix, 부분 적중 없음 | 6회 / 0회 | $0.513 | 6회 / 0회 | $0.783 |

표의 총액에는 캐시 부분뿐 아니라 일반 입력과 출력도 포함했습니다. **캐시를 사용하지 않는 기준 비용은 6회 합계 $0.423**입니다.

1분 간격에서는 두 설정 모두 한 번 쓰고 다섯 번 읽습니다. 읽기 비용은 같으므로 처음 쓸 때 저렴한 5분 캐시가 유리합니다. 10분 간격의 가정에서는 반대로 5분 캐시가 계속 재생성되어, 캐시를 쓰지 않을 때보다도 비싸집니다.

마지막 행도 놓치기 쉽습니다. 같은 문서를 보낸다고 생각해도 매번 앞부분이 바뀌고, 재사용할 짧은 prefix도 저장되어 있지 않다면 긴 TTL이 해결책이 되지 않습니다. 읽기가 없는 상태에서 쓰기 비용만 더 내는 셈입니다.

### 캐시 없는 요청과 TTL 간 비교

Sonnet 4.6에서 같은 prefix를 한 번 저장한 뒤 만료 없이 재사용한다면, 캐시를 사용하지 않는 경우보다 5분 캐시는 **총 2회 요청**, 1시간 캐시는 **총 3회 요청**부터 저렴해집니다. 최초 쓰기를 포함한 횟수이며, 새 내용을 계속 캐시에 추가하는 상황은 제외한 비교입니다.

하지만 “캐시를 쓸까?”와 “5분 대신 1시간을 쓸까?”는 다른 질문입니다. 위의 20,000토큰 prefix에서 1시간 캐시의 최초 쓰기 추가 비용은 $0.045입니다. 5분 캐시 재쓰기 한 번을 1시간 캐시 읽기로 바꾸면 $0.069를 줄일 수 있습니다. 그래서 이 조건에서는 **5분 캐시의 재생성 한 번만 피하더라도** 더 비싼 최초 쓰기 비용을 회수합니다.

이 계산을 실제 서비스에 적용하려면 전체 요청 수보다 같은 prefix가 얼마나 자주 재생성되는지 봐야 합니다.

## 캐시 경계와 설정 위치

Claude API에는 요청 최상위에 `cache_control`을 넣는 자동 캐싱과, 개별 콘텐츠 블록에 넣는 명시적 breakpoint 방식이 있습니다. 자동 캐싱은 대화가 자라며 과거 메시지를 그대로 이어 붙이는 작업에 편리합니다.[1]

반면 이 글처럼 **고정 문서 뒤에 독립적인 질문을 매번 바꾸는 구조**에서는 고정 문서 끝에 경계를 두는 편이 계산 가정과 맞습니다. 바뀌는 질문까지 포함해 캐시를 쓰면, 앞에 같은 문서가 있다는 이유만으로 그 부분의 캐시가 알아서 생기지는 않습니다. 공식 문서도 캐시 쓰기는 지정된 경계에서 발생하고, 재사용 탐색은 이전에 실제로 저장한 경계를 찾는다고 설명합니다.[1]

1시간 TTL은 해당 `cache_control` 객체에 `"ttl": "1h"`를 지정합니다.[1] 다음은 고정 텍스트 블록의 **구조 설명용 예시**입니다. 완전한 API 요청이나 이번에 실행한 요청은 아니며, 짧은 예시 문장 자체는 캐시 길이 조건을 충족하지 않습니다.

```json
{
  "type": "text",
  "text": "반복해서 사용할 긴 지침과 참고 문서",
  "cache_control": {
    "type": "ephemeral",
    "ttl": "1h"
  }
}
```

캐시 경계 뒤에는 이번 요청의 질문을 별도 블록으로 둡니다. TTL을 지정하지 않은 기본 캐시는 5분입니다.[1]

### 최소 길이와 동시 요청

Sonnet 4.6의 최소 캐시 길이는 1,024토큰입니다. 이보다 짧으면 `cache_control`을 넣어도 오류 없이 비캐시로 처리될 수 있습니다. 또한 캐시는 첫 응답이 시작된 뒤부터 사용할 수 있으므로, 캐시가 없는 상태에서 여러 요청을 동시에 보내면 첫 요청을 제외한 나머지가 모두 읽기로 처리된다고 가정하면 안 됩니다.[1]

캐시 할인을 받으려고 불필요한 문장을 억지로 늘리기보다는, 실제로 반복되는 긴 자료가 있는 작업부터 적용하는 편이 낫겠습니다.

## usage의 읽기·쓰기 구분

설정값에 `1h`가 들어갔다는 것만으로 비용이 줄었다고 판단할 수는 없습니다. 실제 응답의 `usage`에서 읽기와 쓰기를 나눠 확인해야 합니다. 공식 문서가 안내하는 입력 토큰 구분은 다음과 같습니다.[1]

- `input_tokens`: 캐시에서 읽거나 캐시에 쓴 부분을 제외한 일반 입력
- `cache_creation_input_tokens`: 새로 캐시에 쓴 입력
- `cache_read_input_tokens`: 기존 캐시에서 읽은 입력

따라서 전체 입력은 세 항목의 합입니다. `input_tokens`만 보고 전체 입력이 줄었다고 판단하거나, 캐시에 쓴 토큰에 일반 입력 비용을 다시 더하면 계산이 틀어집니다.[1]

쓰기의 세부 항목인 `cache_creation.ephemeral_5m_input_tokens`와 `cache_creation.ephemeral_1h_input_tokens`도 확인할 수 있습니다. 둘의 합이 `cache_creation_input_tokens`이므로, 총계와 세부 항목을 다시 합산하지 않습니다.[1]

### 로컬 비용 계산

앞의 표는 Windows의 Python 3.11.16에서 `Decimal`로 계산했습니다. 아래 코드는 같은 계산을 요청별 로그 없이 쓰기·읽기 횟수로 재현하는 짧은 버전입니다. 네트워크 호출 없이 실행할 수 있습니다.

```python
from decimal import Decimal as D

prefix, tail, output, calls = 20_000, 1_000, 500, 6
million = D(1_000_000)

def total(writes, reads, write_rate):
    assert writes + reads == calls
    cached = D(prefix) * (D(writes) * D(write_rate) + D(reads) * D("0.30"))
    other = D(calls) * (D(tail) * D("3") + D(output) * D("15"))
    return (cached + other) / million

print("5m, 1 write + 5 reads:", f"${total(1, 5, '3.75'):.3f}")
print("5m, 6 writes:", f"${total(6, 0, '3.75'):.3f}")
print("1h, 1 write + 5 reads:", f"${total(1, 5, '6'):.3f}")
print("1h, 6 writes:", f"${total(6, 0, '6'):.3f}")
```

실행 결과는 다음과 같습니다.

```text
5m, 1 write + 5 reads: $0.168
5m, 6 writes: $0.513
1h, 1 write + 5 reads: $0.213
1h, 6 writes: $0.783
```

운영에서는 이 고정 토큰 수 대신 실제 `usage` 값을 넣고, 요청 시작 간격과 prefix 변경 여부를 함께 기록하면 됩니다. 민감한 프롬프트 원문을 비용 로그에 복사할 필요는 없습니다. 캐시 설정별 비교에도 출력량이 달라진 영향을 포함해야, 입력 할인과 전체 청구액 절감을 혼동하지 않을 수 있습니다.

## 작업 패턴에 맞는 TTL 선택

제가 먼저 볼 지표는 요청 수 자체보다 **동일한 prefix의 재사용 간격**입니다. 짧게 이어지는 대화와 도구 호출에서는 5분 캐시로 시작하고, 사람의 검토나 다른 작업을 기다리는 동안 캐시 쓰기가 반복되는지 확인하겠습니다. 그 반복을 1시간 캐시가 읽기로 바꿀 수 있을 때 전환을 검토하는 방식입니다.

반대로 단발성 요청이 많거나 참고 자료가 계속 바뀌는 작업이라면, 1시간으로 늘리기 전에 재사용할 공통 부분이 실제로 있는지부터 봐야 합니다. 캐시가 있다고 필요 없는 문서를 더 보내는 것도 좋은 출발점은 아닙니다. **불필요한 입력을 줄이는 일과, 필요한 입력을 저렴하게 재사용하는 일은 함께 할 수 있습니다.**

데이터 처리 조건도 별도입니다. 이 기능은 로컬 저장소가 아니라 제공사 측 캐시이며, 공식 문서는 캐시 표현과 해시를 메모리에 보관한다고 설명합니다. Claude 직접 API의 캐시는 workspace 단위로 분리되지만, 이를 애플리케이션의 사용자별 접근 제어 대신 사용해서는 안 됩니다.[1] 비용을 줄이더라도 외부 전송이 허용된 자료만 보내는 기준은 그대로 유지해야 합니다.

1시간 캐시는 5분 캐시의 상위 등급이라기보다, **다시 쓰기까지 오래 기다리는 작업을 위한 다른 비용 선택지**로 보는 편이 정확합니다.
