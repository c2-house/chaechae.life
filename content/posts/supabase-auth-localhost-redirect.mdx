배포한 웹사이트에서 Google 로그인까지 진행했는데 마지막에 `localhost:3000`으로 이동한다면, 로그인 버튼이나 DB 연결부터 다시 만들 필요는 없습니다. 먼저 **어느 단계에서 localhost 주소가 선택됐는지** 확인하는 편이 빠릅니다. Supabase의 기본 복귀 주소, 앱이 요청하는 복귀 주소, 로그인 처리 뒤 앱이 보내는 주소가 서로 다를 수 있기 때문입니다.

우선 Supabase의 **Site URL과 Redirect URLs**, 그리고 앱의 `redirectTo`를 함께 확인해야 합니다. Site URL만 운영 주소로 바꿔도 끝나는 경우가 있지만, 앱 코드가 계속 localhost를 요청하거나 콜백 처리 뒤 다시 localhost로 보내면 문제가 남습니다. Google에 등록하는 OAuth 콜백 주소도 앱의 복귀 주소와는 별개입니다.

2026년 9월 23일 확인한 공식 문서를 바탕으로, **Supabase 호스팅 프로젝트를 사용하는 웹앱**의 점검 순서를 정리했습니다. 실제 운영 프로젝트의 설정을 변경하거나 로그인 오류를 재현한 후기는 아닙니다. 아래 주소는 설명용 예시이며, 모바일 딥링크·자체 호스팅·Google One Tap 같은 별도 인증 방식은 범위에서 제외합니다.

## 로그인 과정의 두 콜백 주소

콜백(callback)은 다른 서비스에서 처리를 마친 뒤 돌아오는 주소입니다. Supabase를 거쳐 Google에 로그인하는 방식에는 돌아오는 구간이 두 번 있어서 헷갈리기 쉽습니다.

1. **Google → Supabase Auth:** Google의 인증 결과를 Supabase가 받습니다.
2. **Supabase Auth → 내 웹앱:** Supabase가 사용자를 앱으로 돌려보냅니다.
3. **내 웹앱 → 로그인 후 화면:** 앱이 필요한 세션 처리를 마친 뒤 홈이나 대시보드로 이동시킵니다.

[Supabase의 Google 로그인 문서](https://supabase.com/docs/guides/auth/social-login/auth-google)는 Google의 **Authorized redirect URIs에 Supabase 프로젝트의 콜백 URL**을 등록하도록 안내합니다. 실제 값은 Supabase Dashboard의 Google 제공업체 설정 화면에서 확인합니다. 커스텀 Auth 도메인을 쓰는 경우도 있으므로 주소를 추측해 입력하지 않는 편이 좋습니다.

반면 앱에서 지정하는 `redirectTo`는 **Supabase에서 내 웹앱으로 돌아올 주소**입니다. 아래는 앱에 `/auth/callback` 경로가 구현된 경우의 예시입니다.

```text
Google에 등록하는 제공업체 콜백
https://PROJECT_REF.supabase.co/auth/v1/callback

앱의 redirectTo와 Supabase 허용 목록에 넣는 앱 콜백
https://example.com/auth/callback

앱 콜백 코드에서 세션 처리 뒤 이동할 화면
https://example.com/dashboard
```

`PROJECT_REF`와 `example.com`은 실제 프로젝트 값으로 바꿔야 합니다. **`/auth/callback`이라는 이름이 모든 앱의 필수 경로인 것은 아닙니다.** 사용 중인 인증 흐름에서 실제로 처리하는 경로를 지정해야 합니다.

Google 화면에서 `redirect_uri_mismatch`로 멈춘다면 첫 번째 구간부터 확인합니다. [Google 공식 문서](https://developers.google.com/identity/protocols/oauth2/web-server#redirect-uri-mismatch)도 요청의 복귀 주소가 등록된 값과 정확히 일치해야 한다고 안내합니다. Google 인증 이후 내 앱 대신 localhost가 열리는 상황과는 확인할 설정이 다릅니다. 두 주소를 모두 운영 홈페이지 하나로 통일하면 오히려 정상적인 인증 흐름을 깨뜨릴 수 있습니다.

## Site URL과 Redirect URLs 설정

Supabase Dashboard에서 **실제로 앱이 연결하는 프로젝트**를 선택하고 **Authentication → URL Configuration**을 엽니다. 개발용 프로젝트를 고쳐놓고 운영 앱을 확인하는 일이 없도록, 앱에 설정된 Supabase 프로젝트 URL과 먼저 대조합니다.

[Redirect URLs 문서](https://supabase.com/docs/guides/auth/redirect-urls)는 두 설정을 다음처럼 구분합니다.

- **Site URL:** 코드에서 `redirectTo`를 지정하지 않았을 때 사용하는 기본 복귀 주소입니다. 기본값인 `http://localhost:3000`이 남아 있다면 운영 사이트 주소로 변경합니다.
- **Redirect URLs:** 앱에서 요청할 수 있는 복귀 주소의 허용 목록입니다. 여기에 주소를 추가하는 것만으로 앱의 목적지가 그 주소로 바뀌지는 않습니다.

예를 들어 운영 사이트가 `https://example.com`이고 OAuth 콜백이 `/auth/callback`이라면 다음과 같이 맞춰볼 수 있습니다.

```text
Site URL
https://example.com

Redirect URLs에 추가할 운영 콜백
https://example.com/auth/callback

앱의 redirectTo
https://example.com/auth/callback
```

이는 설정값의 대응 예시이지 전체 로그인 구현은 아닙니다. 비밀번호 재설정처럼 다른 경로로 돌아오는 기능이 있다면 그 기능이 실제 요청하는 주소도 따로 확인합니다.

### 정확한 주소와 허용 범위

Supabase의 [localhost 이동 관련 지원 문서](https://supabase.com/docs/guides/troubleshooting/why-am-i-being-redirected-to-the-wrong-url-when-using-auth-redirectto-option-_vqIeO)도 `redirectTo`가 동작하려면 해당 주소가 Redirect URLs 설정과 맞아야 한다고 설명합니다.

도메인만 비슷한지 보지 말고 `https` 여부, `www` 유무, 포트, 경로, 마지막 `/`까지 비교합니다. 앱은 `https://example.com/auth/callback`을 요청하는데 허용 목록에는 `https://www.example.com/auth/callback/`만 있다면 같은 문자열이 아닙니다.

와일드카드도 구분해야 합니다. 공식 문서에 따르면 `http://localhost:3000/*`는 `/foo`에는 맞지만 `/foo/bar`에는 맞지 않습니다. `**`는 더 깊은 경로에도 맞습니다. 다만 오류를 없애려고 허용 범위를 무작정 넓히기보다 **운영 환경에는 필요한 정확한 콜백 경로**를 등록하는 편이 좋습니다.

미리보기 배포를 지원해야 한다면 실제 사용하는 Preview 주소 또는 필요한 범위의 패턴을 별도로 추가합니다. 운영 Site URL을 그때그때의 Preview 주소로 바꾸는 방식은 기본 복귀 주소까지 흔들리게 만듭니다.

## 앱의 복귀 주소와 배포 설정

설정 화면이 맞다면 다음은 앱입니다. 저장소에서 `signInWithOAuth`, `redirectTo`, `localhost`를 찾아 로그인 버튼이 실행하는 코드를 확인합니다. URL을 만드는 공통 함수가 있다면 그 함수가 사용하는 환경변수와 기본값까지 따라가야 합니다.

예를 들어 운영 주소 환경변수가 없을 때 `http://localhost:3000`을 기본값으로 쓰는 코드라면, Supabase 설정을 바꿔도 앱이 만드는 요청은 그대로일 수 있습니다. 특히 **Supabase Dashboard의 Site URL과 앱의 환경변수는 서로 자동으로 동기화되는 설정이 아닙니다.**

### 브라우저에서 요청 확인

소스에 적힌 값보다 배포된 앱이 보내는 값이 중요합니다. Chrome·Edge 개발자 도구의 **Network** 탭에서 다음처럼 확인할 수 있습니다.

1. 문제를 확인할 운영 주소를 열고 Network의 **Preserve log**를 켭니다. 페이지가 바뀌어도 요청 기록을 남기기 위한 옵션입니다.
2. 허가된 테스트 계정으로 로그인 흐름을 새로 시작합니다.
3. Supabase Auth의 `/auth/v1/authorize` 요청을 찾습니다. 브라우저에서 직접 OAuth를 시작하는 방식이라면 요청의 Query String Parameters에서 `redirect_to` 값을 확인합니다.
4. 그 값이 localhost인지, 의도한 운영 콜백인지, 아예 없는지 나눠 봅니다. 서버에서 로그인 시작 URL을 만드는 구조라면 해당 서버 코드와 반환되는 이동 주소도 확인합니다.

SDK 코드의 옵션 이름은 `redirectTo`, 실제 인증 요청의 쿼리 이름은 `redirect_to`입니다. 요청한 주소가 운영 주소라면 다음에는 Supabase의 허용 목록을 대조합니다. localhost라면 먼저 URL을 만드는 앱 코드와 배포 설정으로 돌아갑니다.

**인증 요청 전체를 복사해 AI 대화나 공개 이슈에 붙이지 마세요.** URL에는 `code`, `state`, 토큰 등 민감한 값이 들어갈 수 있습니다. 확인 기록에는 단계, 호스트와 경로, 비밀값을 지운 오류만 남겨도 됩니다. Network의 HAR 내보내기에도 쿠키와 인증 정보가 포함될 수 있습니다.

### Next.js와 Vercel의 재배포

Next.js에서 `NEXT_PUBLIC_SITE_URL` 같은 공개 환경변수로 주소를 만든다면, [빌드 시점에 값이 브라우저 JavaScript에 들어간다](https://nextjs.org/docs/app/guides/environment-variables)는 점을 확인해야 합니다. 변수 이름 자체가 특별한 Supabase 설정은 아니고, 앱 코드가 그 이름을 읽을 때 의미가 있습니다.

Vercel을 사용한다면 프로젝트의 **Environment Variables**에서 해당 변수가 Production·Preview 중 어느 환경에 적용되는지 확인합니다. 로컬 `.env.local`을 바꾼 것만으로 운영 설정이 바뀌지는 않습니다. [Vercel 공식 문서](https://vercel.com/docs/environment-variables/managing-environment-variables)에 따르면 환경변수 변경은 기존 배포가 아니라 **새 배포에 적용**됩니다.

필요한 값을 수정한 뒤 새로 빌드·배포하고, 새 배포가 연결된 주소에서 로그인 요청을 다시 확인합니다. Supabase Dashboard의 URL 설정만 바꾼 경우와 앱 환경변수·코드를 바꾼 경우를 구분하세요. 모든 변경에 앱 재배포가 필요한 것은 아니지만, 이전 브라우저 번들에 들어간 localhost는 Dashboard 수정만으로 교체되지 않습니다.

## localhost가 나타나는 단계별 진단

최종 주소창만 보면 중간에 어디까지 정상적으로 도착했는지 놓치기 쉽습니다. Network 기록에서 문서 이동 요청과 응답의 `Location`을 확인하고, **처음으로 localhost가 목적지가 된 구간**을 찾습니다. JavaScript가 이동시키는 경우에는 해당 요청의 Initiator와 앱의 이동 코드도 살펴봅니다.

| 관찰한 상황 | 먼저 확인할 곳 | 다음 행동 |
| --- | --- | --- |
| Google에서 `redirect_uri_mismatch`로 중단 | 제공업체의 콜백 등록 | Supabase Google 설정에 표시된 콜백과 Google 등록값 대조 |
| 로그인 시작 요청의 `redirect_to`가 localhost | 앱의 로그인 코드·URL 생성 함수 | 하드코딩, 환경변수 누락, localhost 기본값 확인 후 필요한 재배포 |
| `redirect_to`가 없고 localhost로 복귀 | 연결된 Supabase 프로젝트의 Site URL | 운영 기본 주소로 설정됐는지 확인 |
| `redirect_to`는 운영 주소인데 다른 곳으로 복귀 | 같은 프로젝트의 Redirect URLs | 실제 요청 주소와 허용 목록 대조, 새 로그인으로 재확인 |
| 운영 `/auth/callback`에 도착한 뒤 localhost로 이동 | 앱 콜백의 후속 이동 코드 | 세션 처리 뒤 생성하는 URL, 배포 설정, 프록시 환경 확인 |
| 운영 주소로 돌아왔지만 다시 로그인 화면 표시 | 세션 교환·쿠키·보호 경로 처리 | URL 설정만 바꾸지 말고 서버 측 인증 흐름 점검 |

이 표는 원인을 확정하는 목록이 아니라 **다음에 조사할 위치를 좁히는 순서**입니다. 같은 증상이라도 설정한 프로젝트가 다르거나 오래된 배포를 보고 있을 수 있습니다.

### 앱 콜백과 세션 처리

Next.js 등의 서버 측 인증에서 PKCE 흐름을 사용한다면, 앱 콜백은 주소만 존재한다고 끝나지 않습니다. PKCE는 인증 코드와 로그인 시작 시 준비한 검증값을 함께 사용하는 흐름입니다. [공식 Google 로그인 가이드](https://supabase.com/docs/guides/auth/social-login/auth-google#signing-users-in)는 콜백에서 `exchangeCodeForSession`으로 코드를 교환하고 세션을 저장하는 단계를 설명합니다.

**운영 도메인으로 돌아오는 것과 로그인 상태가 만들어지는 것은 별개**입니다. 콜백에서 404가 나면 해당 경로 구현과 배포를, 세션 교환이 실패하면 인증 흐름과 쿠키 처리를 확인해야 합니다. 기존 SSR 구성을 없애고 일반 브라우저 클라이언트로 통째로 교체하는 식으로 해결하지 않는 편이 좋습니다.

콜백 처리 뒤 localhost로 이동한다면 앱이 마지막 주소를 만드는 부분이 조사 대상입니다. 리버스 프록시 뒤의 서버 주소를 외부 서비스 주소처럼 쓰는지, 운영 주소 환경변수가 남아 있는지 확인합니다. 이때 요청의 `next`나 `Host` 값을 검증 없이 목적지로 사용하면 외부 사이트로 사용자를 보내는 문제가 생길 수 있으므로, 신뢰하는 운영 origin과 허용된 경로를 기준으로 처리해야 합니다.

## 이메일 템플릿의 복귀 주소

Google 로그인은 정상인데 가입 확인이나 비밀번호 재설정 메일만 localhost로 간다면, 이메일 템플릿을 별도로 확인합니다. **메일에 이미 들어간 링크는 설정을 바꿔도 자동으로 다시 작성되지 않습니다.** 수정 뒤에는 새 메일을 요청해 비교해야 합니다.

[Supabase 이메일 템플릿 문서](https://supabase.com/docs/guides/auth/auth-email-templates)는 다음 값을 구분합니다.

- `{{ .ConfirmationURL }}`: 인증 확인에 사용하는 URL입니다.
- `{{ .SiteURL }}`: 프로젝트에 설정된 기본 사이트 URL입니다.
- `{{ .RedirectTo }}`: 인증 요청에서 전달한 복귀 URL입니다.

템플릿에 `http://localhost:3000`이 직접 들어가 있는지, 기본 사이트로 보내도록 작성됐는지, 요청별 복귀 주소를 쓰도록 작성됐는지 확인합니다. Redirect URLs 문서도 요청별 주소를 쓰려면 템플릿의 `SiteURL` 대신 `RedirectTo`가 필요한 경우가 있다고 안내합니다.

다만 **템플릿의 모든 `SiteURL`을 일괄 치환하면 안 됩니다.** 예를 들어 복귀 주소에 이미 `/auth/confirm`이 있는데 템플릿에서도 같은 경로를 붙이면 주소가 중복됩니다. 해당 템플릿이 기대하는 주소 형식과 앱의 확인 경로를 함께 봐야 합니다.

인증 버튼의 링크를 운영 홈페이지 주소 하나로 바꾸는 것도 해결책이 아닙니다. 토큰 확인이나 코드 교환을 거쳐야 하는 링크에서 그 단계를 없애면 홈페이지는 열려도 인증은 완료되지 않을 수 있습니다.

## 수정 후 완료 확인

설정을 저장했다는 사실보다 **새로 시작한 인증 흐름이 끝까지 맞는지** 확인해야 합니다. 기존 로그인 상태 때문에 성공으로 오판하지 않도록, 앱에 로그인되지 않은 별도 브라우저 프로필이나 새 시크릿 세션에서 시작합니다. 로그인 전 보호된 화면 접근이 차단되는지 확인한 뒤 허가된 테스트 계정으로 로그인합니다. 로그인 시작부터 콜백까지 같은 브라우저 세션을 유지하고, 운영 주소와 Preview 주소를 섞지 않습니다.

- **복귀 주소:** 의도한 도메인과 콜백 경로로 돌아오며 중간에 localhost로 빠지지 않는지 확인합니다.
- **세션 유지:** 의도한 테스트 계정으로 보호된 화면이 열리고, 새로고침해도 그 로그인 상태가 유지되는지 봅니다. 실패하면 세션·쿠키 처리 쪽을 확인합니다.
- **이메일 기능:** 사용하는 가입 확인·비밀번호 재설정 흐름에서 새로 발급한 링크를 확인합니다. 소셜 로그인 성공만으로 이메일도 정상이라고 판단하지 않습니다.
- **환경 구분:** Preview를 지원한다면 그 환경에서도 시작한 인증이 의도한 주소로 돌아오는지 별도로 확인합니다.

수정 전 설정을 비공개 기록에 남기고 한 번에 한 항목씩 바꾸면 영향을 비교하기 쉽습니다. 문제가 생겼다고 허용 목록을 전체 도메인으로 넓히거나 인증 검사를 꺼서는 안 됩니다. 앱을 이전 배포로 되돌리더라도 Supabase Dashboard 설정까지 자동으로 돌아가는 것은 아니라는 점도 기억해야 합니다.

실제 요청 주소와 허용 목록이 일치하는데도 계속 잘못 이동한다면, 요청 시각·배포 식별자·인증 방식·민감값을 제거한 이동 경로를 정리해 지원팀에 문의할 수 있습니다. 공개 질문에 비슷한 증상이 있다는 이유만으로 플랫폼 버그나 특정 해결책을 확정하지 않는 편이 맞습니다.

이 문제에서 먼저 구분할 것은 **Google이 돌아갈 주소, Supabase가 돌려보낼 주소, 앱이 마지막으로 보낼 주소**입니다. 세 구간을 나눠 보면 바꿔야 할 설정이 좁혀집니다. DB 키 교체나 RLS 해제처럼 로그인 복귀 주소와 관계없는 변경부터 시작할 필요는 없습니다.
