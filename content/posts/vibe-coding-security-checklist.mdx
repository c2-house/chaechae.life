AI에게 기능을 맡겨 만들고 로그인과 저장까지 잘 되는 것을 확인하면, 이제 주소를 공개해도 될 것처럼 느껴질 수 있습니다. 그런데 기능 테스트는 보통 ‘내 계정으로 내 데이터를 잘 다루는지’를 확인합니다. 배포 전 보안 점검에서는 반대로 **다른 사람의 데이터에 접근하거나 변경하려고 해도 막히는지**를 확인해야 합니다.

바이브코딩만의 별도 보안 규칙이 있는 것은 아닙니다. 다만 AI가 만든 코드를 빠르게 연결할 때도 인증을 생략한 테스트 API, 과도한 DB 권한, 무제한 유료 호출이 남아 있지 않은지 확인해야 합니다. **화면이 정상이고 빌드가 통과했다는 사실만으로 서비스 공개 준비가 끝난 것은 아닙니다.**

이 글은 2026년 9월 21일 확인한 OWASP와 Next.js·Supabase·Stripe의 공식 자료를 바탕으로 정리한 배포 전 점검 절차입니다. 특정 서비스에 침투 테스트를 수행한 결과는 아닙니다. 아래 확인은 소유하거나 명시적으로 허가받은 테스트 환경에서, 실제 개인정보가 없는 계정과 데이터로 진행하는 것을 전제로 합니다.

## 배포를 멈춰야 하는 신호

모든 항목을 같은 무게로 다루기보다, 먼저 공개를 막아야 하는 문제부터 찾는 편이 좋습니다.

| 발견한 상태 | 우선 조치 |
| --- | --- |
| 서버 비밀키가 브라우저 번들·공개 저장소에 포함됨 | 공개 중단, 노출 원인 제거와 키 폐기·재발급 |
| 사용자 A가 B의 비공개 데이터를 읽거나 변경함 | 해당 기능 차단, 서버·DB의 권한 검사 수정 |
| 비로그인·일반 사용자가 관리자 작업을 수행함 | 관리자 경로 차단, 서버에서 권한 재검증 |
| 누구나 유료 API를 제한 없이 호출함 | 호출 제한과 비용 통제 마련 전 기능 비활성화 |
| 결제되지 않았는데 유료 권한을 얻을 수 있음 | 결제 확인·권한 부여 경로 수정 |

문제가 있는 기능만 확실하게 비활성화할 수 있다면 나머지 기능의 공개 여부를 따로 판단할 수 있습니다. 버튼만 숨기는 것은 비활성화가 아닙니다. 요청을 받는 서버나 데이터 접근 경로에서도 막혀야 합니다.

점검에는 **비로그인 상태, 일반 사용자 A, 일반 사용자 B**를 준비합니다. 관리자 기능이 있다면 관리자 계정도 별도로 준비하고, 각 계정이 소유한 테스트 데이터의 식별자를 기록합니다. 기대 결과와 실제 결과를 나란히 남겨야 나중에 같은 검사를 반복할 수 있습니다.

## 1. 공개 설정과 비밀키

- [ ] **점검 항목:** 서버용 키·DB 비밀번호·웹훅 서명 비밀값이 공개 코드나 응답에 포함되지 않는지 확인합니다.
- **확인 방법:** 브라우저의 Sources·Network, 저장소와 커밋 이력, CI 로그를 점검합니다. 키 원문을 복사해 AI 대화나 이슈에 올리지 말고 변수 이름·파일 위치·노출 경로만 기록합니다. 자동 비밀 탐지 도구를 쓰더라도 탐지되지 않은 노출이 없다고 단정하지 않습니다.
- **중단 기준:** 실제 비밀값이 공개된 상태라면 파일에서 지우는 것만으로 끝내지 않습니다. 사용처와 영향을 확인하고 노출 원인을 수정한 뒤, 유출된 키를 폐기·교체해야 합니다.

환경변수에 넣었다고 항상 비공개가 되는 것은 아닙니다. [Next.js 데이터 보안 문서](https://nextjs.org/docs/app/guides/data-security)는 `NEXT_PUBLIC_` 변수가 클라이언트에 노출된다고 설명합니다. 서버에서 읽은 값도 클라이언트 props나 API 응답에 넣으면 밖으로 나갑니다.

반대로 **공개 가능하도록 설계된 키를 무조건 유출 사고로 취급할 필요는 없습니다.** Supabase의 publishable key는 클라이언트에서 사용하지만, secret·`service_role` 키는 서버의 관리 권한용입니다. 이 차이는 [Supabase publishable key 전환 글](/blog/supabase-publishable-key-migration)에서 따로 정리했습니다. 공개 키 뒤의 접근 권한은 RLS 등으로 제한해야 합니다.

## 2. 로그인과 객체별 접근 권한

- [ ] **점검 항목:** 로그인 여부뿐 아니라 요청한 데이터의 소유자·조직·역할을 서버에서 확인하는지 살펴봅니다.
- **확인 방법:** A와 B가 각각 테스트 데이터를 만든 뒤, A의 세션으로 B의 비공개 데이터 식별자를 사용하는 요청을 테스트 환경에서 확인합니다. 조회뿐 아니라 수정·삭제·내보내기도 포함합니다. 비로그인·일반 사용자의 관리자 API 접근도 확인합니다.
- **중단 기준:** 다른 사용자의 비공개 데이터가 응답에 포함되거나, 권한 없는 변경이 저장되면 배포를 멈춥니다. 화면의 오류 메시지와 별개로 실제 데이터가 바뀌지 않았는지도 확인합니다.

성공 기준은 항상 `403` 하나로 고정할 필요는 없습니다. 존재 여부를 숨기기 위해 `404`를 반환하거나 RLS 때문에 조회 결과가 비어 있을 수도 있습니다. 중요한 것은 **보면 안 되는 데이터가 전달되지 않고, 허용되지 않은 변경이 발생하지 않는 것**입니다. 동시에 A의 정상적인 자기 데이터 접근도 계속 동작해야 합니다.

[OWASP 권한 검사 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)은 기본 차단과 모든 요청의 권한 검사를 강조합니다. `user_id`, `owner_id`, `role`을 요청 본문에서 받는다고 그 값을 신뢰하면 안 됩니다. 검증된 세션의 사용자와 서버가 가진 권한 정보를 기준으로 결정해야 합니다.

Next.js의 Server Action도 이름이 ‘서버’라고 내부 전용 함수가 되는 것은 아닙니다. 호출 가능한 액션에서는 인증·인가를 검사해야 하며, 관리자 메뉴를 숨겼다는 이유로 처리를 생략하면 안 됩니다.

## 3. DB와 파일 저장소의 접근 범위

- [ ] **점검 항목:** DB의 테이블 권한과 RLS 정책, 파일 저장소의 공개 범위가 서비스 의도와 일치하는지 확인합니다.
- **확인 방법:** 실제 클라이언트와 같은 낮은 권한으로 A·B의 조회·쓰기·파일 다운로드를 나눠 시험합니다. 관리자 콘솔이나 RLS를 우회하는 서버 키로 성공한 조회는 이 검사의 근거가 될 수 없습니다.
- **중단 기준:** 비공개 정보가 공개 테이블·버킷에서 보이거나, 오류를 없애려고 RLS를 꺼둔 상태라면 공개 전에 수정합니다.

[Supabase 운영 체크리스트](https://supabase.com/docs/guides/deployment/going-into-prod)는 RLS와 Security Advisor 확인을 안내합니다. 다만 RLS가 켜져 있다는 표시만으로 끝내지 말고, 조회·추가·수정·삭제 각각에 의도한 정책이 적용되는지 확인해야 합니다. DB 권한과 RLS 정책은 함께 살펴봐야 합니다.

파일 저장소도 별개입니다. [Supabase 버킷 문서](https://supabase.com/docs/guides/storage/buckets/fundamentals)에 따르면 public 버킷의 파일은 URL을 아는 사람이 가져갈 수 있습니다. 파일 이름이 복잡하다는 것은 접근 통제가 아닙니다. 비공개 파일에는 private 버킷과 적절한 정책을 사용하고, 서명 URL을 발급한다면 발급 대상과 만료 시간을 확인합니다.

다른 사용자의 파일 URL을 넣었을 때 접근이 막히는지도 별도로 확인해야 합니다. DB 행을 숨겼다고 파일 원본까지 자동으로 숨겨지는 것은 아닙니다.

## 4. 서버 입력 검증과 화면 출력

- [ ] **점검 항목:** 입력 길이·자료형·허용 값·변경 가능 필드를 서버에서 검사하고, 사용자 입력을 화면의 실행 코드로 해석하지 않는지 확인합니다.
- **확인 방법:** 테스트 데이터로 필수 값 누락, 허용 범위를 벗어난 값, 변경하면 안 되는 필드 추가를 확인합니다. 프런트엔드 폼 검사를 거치지 않는 API 요청에도 같은 제한이 적용돼야 합니다. HTML·Markdown을 표시하는 위치와 DB 쿼리 생성 방식도 검토합니다.
- **중단 기준:** 클라이언트가 보낸 관리자 역할·상품 가격·소유자 값을 그대로 저장하거나, 신뢰하지 않는 HTML을 정제 없이 삽입하는 경로가 있다면 수정합니다.

‘입력 검증’ 한 가지로 모든 문제가 해결되는 것은 아닙니다. SQL은 값 바인딩을 지원하는 쿼리 방식을 사용하고, 브라우저 출력에는 출력 위치에 맞는 이스케이프와 필요한 경우 HTML 정제가 적용돼야 합니다.

[OWASP XSS 방어 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)은 React의 `dangerouslySetInnerHTML` 같은 우회 지점을 주의 대상으로 설명합니다. 기본 텍스트 렌더링은 안전하게 처리하면서도, AI가 만든 미리보기 기능에서 HTML을 직접 삽입하면 별도의 위험이 생길 수 있습니다. AI 모델이 생성한 HTML도 신뢰된 코드로 간주하지 않습니다.

## 5. 파일 업로드와 외부 URL 가져오기

- [ ] **점검 항목:** 업로드 형식·크기·저장 위치를 제한하고, 서버가 사용자 제공 URL에 무제한으로 요청하지 않는지 확인합니다.
- **확인 방법:** 작은 무해한 테스트 파일로 금지 형식과 설정한 크기 제한을 확인합니다. 파일 이름·확장자·전송된 `Content-Type`만 믿는 코드가 없는지 검토합니다. URL 가져오기는 허용된 테스트 주소로 제한 동작을 확인하고, 리다이렉트와 DNS 처리까지 설계를 검토합니다.
- **중단 기준:** 임의 파일을 실행 가능한 위치에 저장하거나, 임의 URL로 내부 네트워크에 접근할 수 있는 구조라면 해당 기능을 공개하지 않습니다.

[OWASP 파일 업로드 지침](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)은 허용 목록, 실제 파일 형식 확인, 크기 제한, 애플리케이션이 생성한 파일 이름 등을 함께 권고합니다. 압축 해제나 이미지 변환을 한다면 업로드 크기뿐 아니라 처리 시간·메모리·해제 후 크기도 제한해야 합니다.

URL 요약·미리보기·이미지 가져오기는 서버가 대신 네트워크 요청을 보내는 기능입니다. [SSRF 방어 지침](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)에 따라 가능한 경우 대상 허용 목록을 사용하고, 사설·로컬 주소 접근과 리다이렉트 우회를 막는 네트워크 제한도 검토합니다. 주소 문자열에 특정 단어가 없는지만 검사하는 방식으로 충분하다고 보면 안 됩니다.

운영 서버에서 내부 주소나 클라우드 메타데이터 주소를 직접 호출하며 시험하지는 마세요. 이런 검증은 별도의 격리 환경과 승인된 범위에서 진행할 항목입니다.

## 6. 유료 API와 호출 제한

- [ ] **점검 항목:** AI 생성·메일·SMS·이미지 처리처럼 비용이 드는 기능에 호출량·동시 실행·입력 크기·시간 제한이 있는지 확인합니다.
- **확인 방법:** 테스트 환경에서 제한을 낮게 설정하고 소수의 요청으로 제한 이후 작업이 시작되지 않는지 확인합니다. 사용자별 제한과 서비스 전체 예산을 함께 보고, 재시도·실패도 비용에 포함될 수 있는지 점검합니다.
- **중단 기준:** 외부인이 무제한으로 유료 작업을 시작할 수 있거나, 이상 사용을 멈출 수단이 없다면 비용 발생 기능을 끕니다.

버튼을 잠시 비활성화하는 것은 서버의 호출 제한이 아닙니다. 계정·IP 등 적절한 기준으로 제한하되, 하나의 계정을 여러 요청이 동시에 사용하는 경우도 고려해야 합니다. 여러 서버 인스턴스로 동작한다면 프로세스 메모리의 카운터만으로 전체 한도를 지키기 어렵습니다.

[OWASP API 자원 소비 항목](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/)은 서비스 장애뿐 아니라 외부 API 청구 증가도 위험으로 다룹니다. **예산 알림과 실제 사용 차단은 다릅니다.** 제공업체의 설정이 알림만 보내는지, 어느 범위를 실제로 차단하는지 확인하고 필요하면 애플리케이션에도 한도를 둡니다.

AI를 쓴다면 출력 토큰·도구 호출·재시도 횟수도 제한 대상입니다. 모델의 출력만으로 환불·관리자 권한 변경·파일 삭제 같은 작업을 실행하지 말고, 서버의 권한 검사와 승인 조건을 별도로 둡니다.

## 7. 세션과 요청 출처

- [ ] **점검 항목:** 세션 만료·로그아웃·재인증이 설계대로 동작하고, 쿠키 기반 인증의 상태 변경 요청에 CSRF 방어가 적용되는지 확인합니다.
- **확인 방법:** 만료된 세션과 비로그인 상태로 보호된 작업을 요청합니다. 쿠키 기반 방식이라면 프레임워크의 CSRF·Origin 검증 설정과 쿠키 속성을 확인합니다. 테스트용 다른 출처에서 요청할 때의 거부 동작도 승인된 환경에서 확인합니다.
- **중단 기준:** 인증되지 않은 요청이 보호된 작업을 수행하거나, 신뢰할 수 없는 출처의 상태 변경 요청을 적절한 검증 없이 받아들이면 수정합니다.

[OWASP CSRF 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)은 사용하는 프레임워크의 내장 보호를 우선 활용하도록 안내합니다. 쿠키를 설계할 때는 `Secure`, `SameSite`, `HttpOnly`의 목적을 구분하고 사용하는 인증 라이브러리와 호환되는 구성을 적용합니다. 무조건 속성을 추가하다가 클라이언트 인증 흐름을 깨뜨리지 않도록 확인해야 합니다.

CORS는 사용자 권한 검사가 아닙니다. 브라우저에서 다른 출처의 응답을 읽는 조건을 제한해도 서버에 직접 요청하는 호출자를 인증해 주지는 않습니다. ‘CORS 오류가 나니 안전하다’고 판단해서는 안 됩니다.

## 8. 결제와 웹훅

- [ ] **점검 항목:** 금액·상품·주문 소유자·결제 상태를 서버에서 확인하고, 웹훅 발신자 검증과 중복 처리가 있는지 확인합니다.
- **확인 방법:** 제공업체의 테스트 모드에서 정상 결제와 실패·취소를 구분합니다. 서명이 없거나 맞지 않는 웹훅은 거부되는지, 같은 이벤트를 재전송해도 포인트나 권한이 중복 지급되지 않는지 확인합니다.
- **중단 기준:** 브라우저의 결제 성공 화면만으로 유료 권한을 주거나, 서명 없는 요청이 결제 완료 처리를 유발하면 배포를 멈춥니다.

결제 완료 페이지로 이동했다는 사실과 실제 결제가 완료됐다는 사실은 다릅니다. 클라이언트가 보낸 가격을 그대로 청구 기준으로 삼지 말고, 서버의 상품·주문 정보를 대조해야 합니다.

[Stripe 웹훅 문서](https://docs.stripe.com/webhooks)는 원본 요청 본문을 사용한 서명 검증, 중복 이벤트 처리, 이벤트 순서가 보장되지 않는다는 점을 설명합니다. 다른 결제 서비스를 쓴다면 그 서비스의 검증 절차를 따릅니다. 서명 비밀값을 공개 API 키와 혼동하지 않는 것도 중요합니다.

결제를 사용하지 않는 서비스라면 이 항목은 ‘해당 없음’으로 기록할 수 있습니다. 다만 나중에 결제를 추가할 때 다시 점검해야 합니다.

## 9. 운영 설정과 의존성

- [ ] **점검 항목:** 테스트용 관리자 경로·디버그 화면·공유 계정이 남아 있지 않고, 배포·DB·저장소 관리자 계정과 의존성을 관리하는지 확인합니다.
- **확인 방법:** 운영 주소의 HTTPS 인증서와 리다이렉트, 개발·미리보기·운영 환경의 DB와 키가 의도대로 분리돼 있는지 확인합니다. 배포 계정의 MFA, 팀 권한, 미리보기 접근 제한을 검토하고 사용 중인 패키지와 보안 공지를 확인합니다. 실제 데이터를 미리보기 환경에 복제했다면 같은 수준의 보호가 필요합니다.
- **중단 기준:** 테스트용 인증 생략 경로가 살아 있거나, 실제로 노출된 취약 기능에 적용할 조치가 없는 상태라면 공개를 보류합니다.

Node.js 프로젝트에서는 [npm audit](https://docs.npmjs.com/cli/v11/commands/npm-audit) 같은 도구가 알려진 의존성 취약점을 확인하는 데 도움을 줍니다. 하지만 ‘취약점 0개’가 자체 코드의 권한 검사와 설정까지 안전하다는 뜻은 아닙니다. 보고서가 사용하는 레지스트리로 의존성 정보를 전송한다는 점도 조직 정책에 맞게 확인합니다.

`npm audit fix --force`를 무조건 적용하는 대신 영향 범위와 버전 변경을 검토하고 테스트해야 합니다. AI가 권한 오류를 해결하겠다며 인증 검사나 RLS를 제거하거나, 의존성을 출처가 불분명한 패키지로 바꾸도록 제안한다면 그대로 수용하지 않는 편이 맞습니다.

## 10. 로그와 복구

- [ ] **점검 항목:** 비밀값을 남기지 않으면서 인증 실패·권한 거부·중요 작업을 추적할 수 있고, 데이터를 복구할 방법이 있는지 확인합니다.
- **확인 방법:** 테스트 계정으로 의도적인 인증 실패와 잘못된 입력을 발생시킨 뒤 로그를 봅니다. 요청 ID와 오류 원인을 찾을 수 있는지, 토큰·비밀번호·민감한 본문이 그대로 남지 않는지 확인합니다. 별도 환경에 백업을 복원해 필요한 행과 파일이 돌아오는지도 확인합니다.
- **중단 기준:** 민감한 값이 로그로 퍼지거나, 보존이 필요한 데이터를 잃었을 때 복구할 수단이 없으면 먼저 보완합니다.

[OWASP 로깅 지침](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)은 인증·인가 실패 등을 기록하되 액세스 토큰·비밀번호·주요 비밀값은 로그에서 제외하도록 안내합니다. 요청과 응답 전체를 출력하는 디버그 로그는 개발 중에는 편해도 운영에서는 개인정보 유출 경로가 될 수 있습니다.

백업도 대상이 중요합니다. [Supabase 백업 문서](https://supabase.com/docs/guides/platform/backups)에 따르면 DB 백업에는 Storage API로 저장한 파일 원본이 포함되지 않습니다. DB와 파일, 환경 설정, 복구에 필요한 접근 권한을 구분해 준비해야 합니다.

또한 이전 코드를 다시 배포하는 것과 DB 변경을 되돌리는 것은 별개입니다. 스키마 변경 뒤 이전 배포가 실행 가능한지, 문제가 생겼을 때 누가 어떤 기능부터 끌 수 있는지 정해두는 것이 좋습니다.

## AI에게 맡길 점검 요청

‘보안 문제 없게 고쳐줘’보다 **무엇을 검사하고 어떤 증거를 남길지** 지정하는 편이 낫습니다. 코드에 접근할 수 있는 AI 도구에는 다음처럼 요청할 수 있습니다.

```text
이 저장소의 배포 전 보안 검토를 해줘. 우선 코드를 변경하지 말고 조사해.

범위:
- 비밀키가 클라이언트 번들·응답·로그에 노출되는 경로
- API와 서버 액션의 인증, 객체별 권한, 관리자 권한 검사
- DB 및 파일 저장소의 접근 정책
- 입력·파일·외부 URL 처리와 유료 API 호출 제한
- 결제 웹훅 검증, 운영 설정, 로그와 복구 준비

각 항목은 파일·함수 위치, 위험 조건, 확인 근거,
테스트 환경에서의 재현 방법, 최소 수정안을 정리해줘.

키·토큰 원문과 실제 개인정보는 출력하지 마.
운영 API 호출, DB 수정, 키 회전, 결제, 고부하 테스트는 하지 마.
인증·RLS·검증을 끄는 방식으로 오류를 해결하지 마.
실행하지 않은 테스트는 '미실행'으로 표시해.
안전하다고 판단했다면 확인한 범위와 남은 한계도 적어줘.
```

AI가 ‘문제없음’이라고 답했다면 코드 위치와 테스트 결과를 함께 확인해야 합니다. 특히 A·B 계정의 권한 분리와 유료 작업 제한은 성공 경로만 읽고 판단하기 쉽습니다. 수정 후에는 문제를 재현했던 테스트가 막히는지와 정상 기능이 유지되는지를 둘 다 확인합니다.

## 배포 승인과 재점검

점검 기록은 복잡할 필요가 없습니다. **항목, 기대 결과, 실제 결과, 근거, 담당자**가 남으면 됩니다. 상태는 ‘통과’, ‘실패’, ‘미확인’, ‘해당 없음’으로 나누고, 실행하지 않은 항목을 통과로 채우지 않습니다. ‘해당 없음’에는 기능을 사용하지 않는 이유를 적습니다.

핵심은 모든 위험을 체크 표시로 지웠다고 선언하는 것이 아닙니다. 비밀 노출과 권한 우회처럼 공개 전에 막아야 할 문제를 찾아 수정하고, 아직 검증하지 못한 범위를 알고 배포하는 것입니다. 로그인·관리자·결제·파일 업로드를 추가하거나 DB 정책을 바꾸면 관련 항목을 다시 확인해야 합니다.

민감한 개인정보나 큰 금액을 다루는 서비스라면 이 체크리스트만으로 배포를 승인하기보다 별도의 전문 검토를 받는 편이 좋겠습니다. **AI가 기능 구현을 도와줄 수는 있어도, 어떤 권한으로 누구의 데이터를 다루게 할지는 서비스 운영자가 결정하고 검증해야 합니다.**
