AI에게 청구서에서 금액을 뽑아 JSON으로 돌려달라고 요청했다고 해보겠습니다. JSON 파싱도 되고, 필요한 필드도 있고, 금액 타입도 정수입니다. 그렇다면 이 값을 그대로 데이터베이스에 저장하거나 다음 Agent에게 넘겨도 괜찮을까요?

**Structured Outputs는 응답의 형식을 맞추는 기능이지, 그 안에 들어간 값이 원본과 일치한다는 보증은 아닙니다.** 형식 오류를 줄여주는 효과는 분명하지만, 합계가 맞는지와 실제 청구서의 금액인지 확인하는 일은 여전히 남습니다.

이번에는 OpenAI 공식 문서가 설명하는 보장 범위를 살펴보고, Windows에서 JSON Schema 검증과 업무 규칙 검사를 비교해봤습니다. 모델/API 호출 없이, 의도적으로 오류를 넣어 만든 청구서 형태의 테스트 데이터를 로컬에서 검사했습니다. 모델의 정확도나 청구서 인식 성능을 비교한 실험은 아닙니다.

## JSON mode와 스키마 계약

“JSON으로만 답해줘”라고 프롬프트에 적는 것과 API에서 출력 형식을 지정하는 것은 다릅니다. [OpenAI 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs)는 JSON mode와 Structured Outputs의 차이를 **유효한 JSON인지, 지정한 스키마까지 따르는지**로 구분합니다.

JSON mode에서는 파싱 가능한 JSON을 얻더라도 애플리케이션이 기대한 필드와 타입까지 보장되는 것은 아닙니다. 예를 들어 `total`이라는 필드가 필요했는데 `amount`가 오거나, 정수 대신 문자열이 오면 그다음 처리가 달라집니다.

Structured Outputs는 개발자가 지정한 JSON Schema를 기준으로 필요한 필드, 타입, `enum`에 넣은 허용 값 등을 제한합니다. 여기서 스키마는 “응답은 이런 모양이어야 한다”는 계약이라고 생각하면 됩니다. 지원되는 스키마와 모델을 사용하고 정상적으로 응답이 완료된 경우의 계약이며, 거절이나 미완료 응답은 별도로 처리해야 합니다.

이 차이는 단순히 보기 좋은 JSON을 얻는 것보다 실용적입니다. 응답을 카드 UI에 표시하거나, 분류 결과를 저장하거나, 다음 작업의 입력으로 넘길 때 매번 키 이름과 타입을 추측하지 않아도 되기 때문입니다. 반대로 사람이 읽을 자유로운 설명만 필요하다면 굳이 복잡한 스키마부터 만들 필요는 없습니다.

### 응답 형식과 도구 호출

OpenAI Responses API에서 응답 자체의 구조를 지정하는 경로는 `text.format`입니다. `type: "json_schema"`, `strict: true`, 그리고 사용할 스키마를 지정하는 방식입니다. Chat Completions의 `response_format` 예제를 Responses API에 그대로 옮기면 안 됩니다.

모델이 애플리케이션의 함수를 호출하도록 연결하려는 경우에는 function calling을 사용합니다. 최종 답변의 형식과 도구에 전달할 인자의 형식은 구분해서 설계하는 편이 좋습니다. **올바른 형식의 인자가 만들어졌다는 것과 그 작업을 실행해도 된다는 것도 별개의 판단**입니다.

## 청구서 데이터의 검증 조건

실험에서는 세금이나 할인 없이 항목 금액을 더하면 총액이 되는 단순한 청구서를 가정했습니다. 기준 데이터는 `INV-001`, 통화는 `KRW`, 항목 금액은 `10000`과 `20000`, 총액은 `30000`입니다. 실제 청구서를 읽은 것이 아니라, 비교할 정답을 고정해둔 테스트용 데이터입니다.

사용한 스키마는 다음과 같습니다. `schema.json`이라는 이름으로 저장하면 뒤의 짧은 코드를 실행할 수 있습니다.

```json
{
  "type": "object",
  "properties": {
    "invoice_id": { "type": "string" },
    "currency": { "type": "string", "enum": ["KRW"] },
    "line_amounts": {
      "type": "array",
      "items": { "type": "integer" }
    },
    "total": { "type": ["integer", "null"] }
  },
  "required": ["invoice_id", "currency", "line_amounts", "total"],
  "additionalProperties": false
}
```

`required`는 키가 반드시 있어야 한다는 뜻이고, `additionalProperties: false`는 정의하지 않은 키를 받지 않겠다는 뜻입니다. [JSON Schema의 object 설명](https://json-schema.org/understanding-json-schema/reference/object)에서 확인할 수 있듯이, 일반 JSON Schema에서는 `properties`에 키를 적는 것만으로 이 두 조건이 생기지 않습니다.

OpenAI Structured Outputs는 JSON Schema 전체가 아니라 일부를 지원합니다. 공식 문서는 루트가 객체여야 하고, 모든 필드를 `required`에 넣으며, 객체에 `additionalProperties: false`를 설정하도록 안내합니다. 값이 없을 수 있는 필드는 키를 생략하는 대신 `null`을 허용하는 방식으로 표현할 수 있습니다.

그래서 위 스키마의 `total`은 키 자체는 필수지만 값은 정수 또는 `null`입니다. 정보가 없을 때 임의의 숫자로 채우지 않고 “확인 필요”로 넘길 자리를 만든 것입니다. 물론 `null`을 허용한다고 모델이 항상 모르는 것을 정확히 구분하는 것은 아닙니다.

이 스키마는 로컬 validator로 검사했습니다. **로컬 JSON Schema 검증 성공이 제공사 API의 스키마 수용 여부까지 확인해주는 것은 아닙니다.** 실제 API에 붙일 때는 해당 모델과 API가 지원하는 스키마 범위를 따로 확인해야 합니다.

## 형식 검증을 통과한 잘못된 값

Windows 빌드 `26200`, Python `3.11.16`, `jsonschema 4.26.0`에서 테스트 데이터 8개를 검사했습니다. JSON 문자열을 `json.loads`로 파싱한 뒤, `Draft202012Validator`로 스키마를 검증했습니다. 이 단계를 통과한 데이터만 합계 계산과 기준 데이터 대조로 넘겼습니다.

| 테스트 데이터 | JSON 파싱 | 스키마 검증 | 이후 검사 결과 |
| --- | --- | --- | --- |
| 기준 데이터와 같은 값 | 통과 | 통과 | 검토 후보로 전달 |
| `total` 키 누락 | 통과 | 실패 | 업무 검사 미실행 |
| `total`을 문자열 `"30000"`으로 변경 | 통과 | 실패 | 업무 검사 미실행 |
| 정의하지 않은 `approved` 키 추가 | 통과 | 실패 | 업무 검사 미실행 |
| 항목은 그대로, 총액만 `35000` | 통과 | 통과 | 합계 불일치 |
| 항목을 `20000`, `25000`, 총액을 `45000`으로 변경 | 통과 | 통과 | 기준 데이터와 불일치 |
| 청구서 번호만 `INV-999`로 변경 | 통과 | 통과 | 기준 데이터에서 찾지 못함 |
| 총액을 `null`로 설정 | 통과 | 통과 | 확인 필요로 분기 |

모든 데이터가 유효한 JSON이었고, 그중 5개는 스키마도 통과했습니다. 하지만 기준 데이터와 합계까지 맞아 검토 후보로 전달된 것은 첫 번째뿐이었습니다. 이 숫자는 **준비한 테스트 케이스의 결과이지 모델의 오류율이나 성공률이 아닙니다.**

특히 두 가지 차이가 중요했습니다. 총액만 `35000`으로 바꾼 경우에는 정수라는 조건을 충족하므로 스키마를 통과했습니다. 항목과 총액을 함께 바꿔 `45000`으로 맞춘 경우에는 덧셈 검사도 통과했지만, 기준 데이터와는 달랐습니다. **내부적으로 말이 되는 값과 원본에 근거한 값은 다를 수 있습니다.**

### 합계 불일치의 최소 재현

앞의 스키마를 `schema.json`에 저장하고 `jsonschema 4.26.0`이 설치된 환경에서 다음 코드를 실행하면, 스키마를 통과한 뒤 합계 검사에서 실패하는 차이를 확인할 수 있습니다.

```python
import json
from pathlib import Path
from jsonschema import Draft202012Validator

schema = json.loads(Path("schema.json").read_text(encoding="utf-8"))
Draft202012Validator.check_schema(schema)
validator = Draft202012Validator(schema)

data = {
    "invoice_id": "INV-001",
    "currency": "KRW",
    "line_amounts": [10000, 20000],
    "total": 35000,
}

validator.validate(data)
print("schema: pass")
print("sum_matches:", sum(data["line_amounts"]) == data["total"])
```

실행 결과는 다음과 같습니다.

```text
schema: pass
sum_matches: False
```

여기서 발견한 것은 Structured Outputs의 고장이 아닙니다. **스키마에 표현한 조건과 애플리케이션이 필요로 하는 조건이 달랐던 것**입니다. 고정된 허용 값이나 범위처럼 스키마로 표현할 수 있는 규칙은 활용하되, 이번 합계 관계와 신뢰할 원본과의 일치 여부는 별도 코드로 확인했습니다.

실제 청구서에는 세금, 할인, 반올림 등이 있으므로 단순 합계 검사를 그대로 적용하면 정상 데이터도 거절할 수 있습니다. 또한 이 실험의 원본 대조는 고정한 딕셔너리와의 비교입니다. PDF나 이미지에서 금액을 정확히 읽는 문제까지 해결한 결과는 아닙니다.

## 거절·미완료·정보 부족의 분기

업무 규칙을 잘 작성해도 그 앞에서 응답이 정상 완료됐는지 먼저 확인해야 합니다. OpenAI 문서는 안전상 거절인 `refusal`과 출력 토큰 제한 등으로 인한 미완료 응답을 예외 상황으로 안내합니다. Responses API의 `status`가 `incomplete`라면 `incomplete_details`도 확인할 대상입니다.

이런 응답을 정상 데이터처럼 파싱하거나, 빠진 금액을 `0`으로 채워 다음 단계에 보내면 안 됩니다. `0`은 “확인하지 못했다”가 아니라 실제 금액이 없다는 뜻으로 처리될 수 있기 때문입니다.

정상 응답 안에서도 정보 부족은 따로 표현하는 편이 좋습니다. 이번 실험의 `total: null`은 스키마에 맞는 데이터였지만 업무 검사에서는 `needs_review`로 보냈습니다. API 차원의 거절·미완료와, 업무 데이터 안에서 값이 확인되지 않은 상황은 서로 다른 분기입니다.

공식 문서는 입력이 스키마와 전혀 관련 없을 때 형식을 맞추려다 잘못된 내용이 나올 가능성도 설명합니다. 청구서가 아닌 문서를 넣었는데 청구서 필드를 반드시 채우라고 요구하는 상황을 생각하면 이해하기 쉽습니다. 프롬프트에 정보 부족 처리 기준을 적고, 스키마에도 그 상태를 담을 수 있어야 합니다. 이후에는 애플리케이션이 자동 처리를 멈추도록 연결해야 의미가 있습니다.

## Agent에 결과를 넘기는 기준

저라면 Structured Outputs를 “검증이 끝난 응답”이 아니라 **검증하기 쉬운 응답을 얻는 출발점**으로 사용하겠습니다. 키 이름과 타입이 일정해지면 후속 검사를 예측 가능한 코드로 작성할 수 있다는 것이 가장 큰 장점입니다.

실무에서는 각 단계의 실패 이유를 구분해두는 편이 좋습니다.

- **응답 상태 확인:** 거절·미완료 응답을 정상 데이터와 분리합니다.
- **스키마 검증:** 계약에 맞는 필드와 타입인지 확인합니다.
- **업무 규칙 검사:** 금액 관계, 허용 상태 전환 등 서비스의 조건을 코드로 검사합니다.
- **원본 대조:** 청구서 번호나 금액이 신뢰할 수 있는 자료와 맞는지 확인합니다. 모델이 작성한 “검증 완료” 문구를 근거로 삼지 않습니다.
- **실행 판단:** 저장·발송·결제처럼 상태가 바뀌는 작업은 필요한 권한과 승인 조건을 따로 확인합니다.

매번 실패하면 모델에게 같은 요청을 다시 보내는 방식은 추천하지 않습니다. 출력이 미완료된 경우와 원본에 정보가 없는 경우는 해결 방법이 다릅니다. 후자는 재시도보다 원본 보완이나 사람의 검토가 필요할 수 있습니다. 반복 호출에는 시간과 API 사용량도 추가됩니다.

평가할 때도 JSON 파싱 성공만 집계하지 않는 편이 좋겠습니다. 형식 오류, 업무 규칙 위반, 원본 불일치, 정보 부족을 나눠 기록하면 무엇을 고쳐야 하는지 알기 쉽습니다. 프롬프트를 고칠 문제인지, 스키마가 빠뜨린 조건인지, 입력 자료의 문제인지 구별할 수 있기 때문입니다.

값의 정확성까지 보장하지 않는다고 해서 Structured Outputs가 불필요한 것은 아닙니다. 형식이 안정되면 후속 검사를 작성하고 오류의 원인을 찾기가 쉬워집니다. **형식을 일정하게 만드는 일은 맡기고, 그 값을 믿고 사용할 근거는 애플리케이션에서 확인하는 것**이 적절한 역할 분담이라고 생각합니다.
