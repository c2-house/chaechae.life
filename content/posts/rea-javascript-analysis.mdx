### 목차

## 들어가며

앱의 검색이나 내보내기 기능을 이해하려고 코드를 열었는데, 시작점과 실제 처리 함수가 서로 다른 파일에 있으면 어디부터 따라가야 할지 막막합니다. 배포된 Electron 앱처럼 여러 파일이 묶여 있는 경우에는 더 그렇습니다.

[REA](https://github.com/morluto/rea)는 이런 조사에 필요한 도구를 코딩 에이전트와 터미널에 제공하는 오픈소스 프로젝트입니다. 이름은 **Reverse Engineer Anything**의 약자입니다. 역공학은 프로그램이나 배포 파일을 살펴보고 내부 동작을 알아내는 작업인데요. REA는 분석 결과뿐 아니라 어느 파일·위치에서 나온 근거인지, 무엇을 아직 모르는지도 함께 돌려줍니다.

**직접 만든 JavaScript 샘플**로 REA 설치, 정적 분석, 결과 조회, MCP 등록을 순서대로 확인했습니다. 테스트 환경은 Windows x64, Node.js 22.23.2, npm 10.9.8, REA 6.4.0입니다.

## REA와 코딩 에이전트의 역할

REA 자체를 새로운 챗봇이라고 생각하면 사용법이 헷갈립니다. REA는 분석 도구이고, Claude Code나 Codex 같은 에이전트는 그 도구가 반환한 자료를 읽고 다음 조사나 설명을 이어갑니다.

사용 경로는 두 가지입니다.

- **CLI**: 터미널에서 분석 명령을 직접 실행합니다. AI 계정이나 에이전트 연결 없이도 이 글의 JavaScript 정적 분석을 할 수 있습니다.
- **MCP**: 에이전트가 외부 도구를 호출하는 연결 방식입니다. REA의 MCP 서버를 등록하면 자연어 요청을 받은 에이전트가 분석 도구를 사용할 수 있습니다.

공식 프로젝트는 네이티브 바이너리, JavaScript·Electron 앱, .NET 어셈블리, 웹사이트 등의 분석을 안내합니다. 다만 모두 같은 준비물로 동작하지는 않습니다. 네이티브 코드의 깊은 분석은 Hopper·Ghidra·IDA 같은 별도 엔진을 사용하고, 웹사이트 관찰은 브라우저가 필요합니다. **JavaScript 정적 분석에는 그 네이티브 엔진이 필요하지 않습니다.**

예를 들어 Electron의 내보내기 버튼은 화면 코드에서 시작해 preload와 IPC를 거쳐 메인 프로세스에 있는 파일 저장 함수로 이어질 수 있습니다. IPC는 프로세스 사이에서 메시지를 주고받는 통로입니다. REA의 의미는 파일을 하나 읽는 데 그치지 않고 이런 연결과 근거를 조사에 활용할 수 있다는 데 있습니다.

## 설치 환경과 첫 실행

### Node.js와 분석 대상

REA 6.4.0은 Node.js `22.x의 22.19 이상`, `24.x의 24.11 이상`, 또는 `26 이상`을 요구합니다. 공식 설치 문서는 23·25와 사전 출시 버전을 지원 대상에서 제외합니다.

터미널에서 먼저 확인합니다.

```bash
node --version
npm --version
```

이 글의 명령은 Windows에서는 **Git Bash**를 기준으로 합니다. Linux에서는 정적 JavaScript 분석에도 프로세스 소유권 확인을 위한 procps 호환 `ps`가 PATH에 있어야 한다는 공식 조건이 있습니다. 네이티브 분석 엔진을 설치할 때는 엔진별 운영체제 요구사항을 확인하세요.

대상은 본인이 작성했거나 분석 권한을 받은 파일로 한정하세요. 회사 코드·고객 데이터가 들어 있는 실제 앱 대신, 아래의 자작 샘플로 결과의 모양부터 확인하겠습니다.

### 프로젝트 안에만 설치하기

기존 서비스 저장소 밖에서 새 폴더를 만들고 실행합니다. 전역 설치나 에이전트 설정 변경은 필요하지 않습니다.

```bash
mkdir rea-lab
cd rea-lab
npm install --ignore-scripts --omit=optional --no-audit --no-fund rea-agents@6.4.0
npx --no-install rea --version
```

버전 출력은 `6.4.0`입니다. JavaScript 실습에서는 `--ignore-scripts`와 `--omit=optional`로 설치 스크립트와 선택 의존성을 생략합니다. 뒤에서 쓰는 `--no-install`은 설치된 실행 파일을 사용합니다.

2026년 10월 14일 확인한 npm 최신 배포판은 6.4.0이었고, 해당 GitHub 릴리스는 10월 11일에 공개됐습니다. 재현을 위해 버전을 고정했습니다. 이후 최신 버전으로 시작하려면 [공식 설치 문서](https://github.com/morluto/rea/blob/main/docs/installation.md)와 해당 버전의 도움말을 다시 확인하는 편이 좋습니다. 저장소의 `main` 설명과 실제 npm 배포판에 들어 있는 기능이 항상 같지는 않습니다.

## 자작 샘플의 첫 정적 분석

`rea-lab` 아래에 `sample` 폴더를 만들고 편집기로 다음 세 파일을 저장합니다. REA를 설치한 상위 폴더와 분석할 샘플을 나눠야 `node_modules`까지 분석 대상으로 넣는 일을 피할 수 있습니다.

```text
rea-lab/
  node_modules/
  sample/
    package.json
    main.js
    search.js
```

`sample/package.json`은 시작 파일과 모듈 형식을 알려줍니다.

```json
{"name":"rea-search-sample","version":"1.0.0","type":"module","main":"main.js"}
```

`sample/main.js`는 검색 함수를 가져와 호출합니다.

```javascript
import { searchNotes } from "./search.js";
const notes = ["Alpha", "Beta"];
console.log("search-result", searchNotes(notes, "AL"));
```

`sample/search.js`에는 대소문자를 구분하지 않는 검색 함수를 넣습니다.

```javascript
export function searchNotes(notes, query) {
  const needle = query.toLowerCase();
  return notes.filter(note => note.toLowerCase().includes(needle));
}
```

이제 `rea-lab`에서 분석을 실행하고 결과를 파일에 저장합니다.

```bash
npx --no-install rea analyze-javascript-application ./sample --json > analysis.json
```

이 명령은 샘플을 실행하는 `node sample/main.js`와 다릅니다. REA가 파일을 텍스트로 읽고 문법과 연결 관계를 분석합니다. 터미널에 진행 메시지가 보여도 최종 JSON은 `analysis.json`에 저장됩니다. 출력 파일은 분석 대상인 `sample` 밖에 두세요.

실제 앱을 대상으로 바꿀 때는 `./sample` 대신 권한을 확보한 **추출된 앱 디렉터리 또는 ASAR 파일**을 지정합니다. ASAR는 Electron 앱의 파일들을 묶는 아카이브 형식입니다. 경로에 공백이 있으면 `"D:/apps/my sample"`처럼 따옴표로 감싸면 됩니다.

## 분석 결과와 근거 읽기

### 파일 연결과 원본 위치

큰 JSON 전체를 처음부터 읽을 필요는 없습니다. `rea-lab`에 `read-result.mjs`를 만들고 필요한 항목부터 추립니다.

```javascript
import { readFileSync } from "node:fs";

const evidence = JSON.parse(readFileSync("analysis.json", "utf8"));
const result = evidence.normalized_result;
console.log("statistics:", result.statistics);

for (const edge of result.graph.edges) {
  if (edge.relation !== "imports" || edge.properties.module_link_kind !== "import") continue;
  console.log({
    imported: edge.properties.imported_name,
    resolved: edge.properties.resolved_path,
    status: edge.properties.resolution_status,
    source: edge.evidence.location.value
  });
}
console.log("limitations:", evidence.limitations);
```

```bash
node read-result.mjs
```

이번 결과에서는 관련 파일 3개, 파싱한 JavaScript 파일 2개, 파싱 실패 0개를 확인했습니다. import 관계에는 `searchNotes`, 해석된 경로 `search.js`, 상태 `resolved`가 있었고, 근거 위치는 `main.js`의 1행을 가리켰습니다. **그래프의 import 이름과 근거 위치를 `main.js`의 첫 줄과 대조하세요.**

<Image src="/rea-javascript-analysis/03-analysis.webp" alt="실제 REA 분석 결과에서 JavaScript 파일 2개와 searchNotes import 관계가 확인된 화면" caption="CLI 분석 결과에서 추린 파일 통계, import 관계, 분석 범위." />

이 샘플에서는 통계의 `modules`가 0이어도 그래프 안에는 소스 모듈과 import 관계가 있었습니다. 따라서 숫자 하나를 보고 “코드를 못 읽었다”고 결론 내리기보다 `parsed_javascript_files`, 그래프, 원본 위치를 함께 확인하는 편이 정확합니다.

### 요약 조회와 분석 한계

REA에는 저장한 Evidence에서 요약을 뽑는 `inspect-analysis-view`도 있습니다. Evidence는 분석 대상의 식별 정보, 결과, 근거와 한계를 함께 담은 기록입니다. `make-view.mjs`를 다음과 같이 저장합니다.

```javascript
import { readFileSync, writeFileSync } from "node:fs";
const evidence = JSON.parse(readFileSync("analysis.json", "utf8"));
writeFileSync("view-input.json", JSON.stringify({
  source: { kind: "inline", evidence },
  view: { kind: "summary" }
}));
```

```bash
node make-view.mjs
npx --no-install rea inspect-analysis-view view-input.json --json > summary.json
```

`summary.json`의 `normalized_result.summary.coverage`에서 `application.status`는 `complete`, `semantic.status`는 `unknown`이었습니다. 파일 구조 분석은 끝났고, 동적 표현식이나 난독화된 경로처럼 정적으로 추적하기 어려운 부분은 `limitations`에서 확인할 수 있습니다.

검색 함수의 반환값까지 확인하려면 별도 실행 증거가 필요합니다. 여기서는 직접 작성한 안전한 샘플이므로 다음 명령으로 대조했습니다.

```bash
node sample/main.js
```

실제 출력은 다음과 같았습니다.

```text
search-result [ 'Alpha' ]
```

위 출력은 **Node.js로 직접 작성한 샘플을 실행해 확인한 반환값**입니다. 출처를 모르는 프로그램은 정적 분석까지만 진행하세요.

## 에이전트 연결과 자연어 요청

CLI 분석이 목적이라면 여기까지로도 충분합니다. 자연어로 추가 조사를 맡기고 싶을 때만 MCP를 연결하면 됩니다.

### 설정 계획과 적용

공식 설치 경로는 `npx rea-agents@latest setup`입니다. 실행하면 사용할 에이전트를 선택하고 변경 계획을 검토한 뒤 승인하는 방식입니다. 패키지 다운로드 승인과 REA의 설정 변경 승인은 별개입니다.

연결 대상을 명시하고 싶다면 다음처럼 먼저 계획을 조회할 수 있습니다. `codex`는 Codex용 값이며, Claude Code는 `claude_code`, Cursor는 `cursor`를 사용합니다.

```bash
npx --no-install rea setup --client codex --dry-run --json
```

`plannedActions`에서 **설정 파일 경로와 skill 설치 경로**를 확인하세요. REA는 MCP 서버를 등록하고 분석 절차를 안내하는 skill을 함께 설치합니다.

이 계획이 원하는 사용자 환경을 가리키고 변경에 동의한다면 아래 명령으로 적용할 수 있습니다. `--yes`는 실제 설정 변경을 승인하는 옵션이므로, 경로를 보지 않고 붙이는 용도로 사용하지 않는 편이 좋겠습니다.

```bash
npx --no-install rea setup --client codex --yes --json
npx --no-install rea doctor --client codex --json
```

위 명령은 현재 사용자의 에이전트 설정을 변경할 수 있습니다. 설정 등록은 사용자 경로를 임시 폴더로 분리한 환경에서 확인했습니다. 로컬 설치 경로를 참조하는 설정이라면 연결을 유지하는 동안 `rea-lab` 폴더를 같은 위치에 두세요.

<Image src="/rea-javascript-analysis/02-setup.webp" alt="격리된 Codex 설정 등록과 doctor 검사에서 healthy true, environment_healthy false가 함께 나온 실제 결과" caption="임시 사용자 폴더의 등록 및 진단 결과. Codex 등록은 aligned, 전체 환경 상태는 false입니다." />

이번에는 `setup.status`가 `ready`였고, Codex 등록과 skill 설치가 적용됐습니다. 이후 `doctor --client codex`는 `healthy: true`를 반환했습니다. 반면 전체 환경의 `environment_healthy`는 `false`였는데, Ghidra·IDA 같은 네이티브 엔진이 없었기 때문입니다. 이 상태에서도 앞의 JavaScript 정적 분석은 완료됐습니다.

### 첫 자연어 요청

설정을 적용한 다음에는 에이전트를 재시작하거나 MCP 연결을 다시 열어야 합니다. **doctor가 설정 파일을 정상으로 판단하는 것과 실행 중인 에이전트가 도구에 연결된 것은 별개**입니다. 에이전트의 MCP 상태와 도구 목록에서 REA 연결을 확인한 뒤 요청합니다.

아래는 같은 샘플에 사용할 요청 예시입니다. 경로는 자신의 `sample` 절대 경로로 바꿉니다.

```text
REA로 D:/rea-lab/sample을 정적으로 분석해 주세요.
앱을 실행하거나 파일을 수정하지 마세요.
main.js에서 가져오는 검색 함수가 어느 파일에 정의되어 있는지 찾고,
import 관계, 원본 파일과 행 위치, evidence_id를 제시해 주세요.
확인된 사실과 추론, 아직 알 수 없는 점을 나눠 설명해 주세요.
```

에이전트의 말투가 그럴듯한지보다 **실제 도구 호출과 반환된 근거가 있는지**를 봐야 합니다. `main.js`와 `search.js`의 관계를 제시했는지, 실행하지 않은 동작을 실행 결과처럼 설명하지 않는지 확인하면 됩니다.

## 결과가 부족할 때의 확인 순서

설치부터 막힌다면 `node --version`, `npx --no-install rea --version`, 해당 명령의 `--help` 순서로 확인하세요. 지원하지 않는 Node 버전이나 다른 프로젝트의 REA를 사용하고 있지 않은지 먼저 구분할 수 있습니다.

분석 파일은 생겼지만 필요한 관계가 없다면 다음처럼 범위를 좁혀봅니다.

1. **대상 경로**: 앱 폴더가 맞는지, `node_modules`가 있는 실습 상위 폴더를 넣지 않았는지 확인합니다.
2. **읽기와 파싱**: `statistics.parse_failures`, `invalid_utf8_files`, `limitations`를 확인합니다.
3. **정적 관계의 한계**: 경로를 문자열 결합으로 만들거나 실행 중에 모듈을 선택하면 정적 분석에서 미확정으로 남을 수 있습니다.
4. **에이전트 연결**: CLI는 되는데 에이전트에 도구가 없다면 등록 대상과 재시작 여부부터 확인합니다.

추가로 `trace-application-feature`는 저장한 Evidence에서 특정 모듈이나 API와 연결된 그래프를 따라갑니다. 이번 샘플을 `module` 종류의 `search.js`로 추적했을 때는 연결 그래프가 나왔지만, `string` 종류의 `search-result`로 조회했을 때는 `no-match`였습니다. 실제 코드에 문자열이 있어도 해당 그래프의 검색 대상과 맞지 않을 수 있다는 뜻입니다. 먼저 원본 Evidence의 모듈과 위치를 확인하고, [공식 워크플로 문서](https://github.com/morluto/rea/blob/main/docs/javascript-application-workflows.md)에 맞는 seed 종류로 좁히는 편이 좋습니다.

## 로컬 분석과 데이터 전송의 경계

REA의 공식 설명은 분석이 로컬에서 이루어진다는 것입니다. 그러나 MCP로 연결하면 **분석 결과를 에이전트가 받습니다.** 클라우드 모델을 쓰는 에이전트라면 도구 결과에 포함된 코드 조각·경로·문자열 등이 모델 요청에 포함될 수 있으므로, 모델 제공자의 데이터 처리 정책과 에이전트 설정을 별도로 확인해야 합니다.

설치에는 npm 다운로드가 필요합니다. REA는 MIT 라이선스이며, 함께 사용하는 모델과 분석 엔진에는 각자의 이용 조건과 요금이 적용됩니다.

다른 앱의 인증·라이선스·DRM을 우회하거나 비밀값을 추출하는 용도로 범위를 넓히지 마세요. 정적 분석과 달리 실행 관찰 기능은 프로그램을 시작하거나 상호작용할 수 있습니다. 분석 권한과 실행 권한을 구분하고, 회사 자료라면 도구 결과의 외부 전송 허용 여부도 먼저 확인해야 합니다.

작은 소스 파일 두 개만 읽으려면 편집기로 직접 보는 편이 더 간단합니다. REA를 검토할 이유는 파일과 프로세스 사이의 관계를 반복해서 따라가야 하거나, 에이전트의 설명을 원본 근거와 대조하고 싶을 때입니다. 처음부터 “앱 전체를 복제해 줘”라고 맡기기보다, **한 기능의 시작점과 연결 관계를 찾고 원본에서 확인하는 작업**부터 시작하는 것을 권합니다.
