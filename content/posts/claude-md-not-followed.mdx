### 목차

## 들어가며

`CLAUDE.md`에 “테스트를 확인하고 작업을 끝내라”고 적었는데 Claude Code가 수정 완료라고만 답하거나, 프로젝트에서 쓰지 않는 패키지 관리자를 반복해서 선택할 때가 있습니다.

**현재 세션에 지침이 들어왔는지 먼저 확인하세요.** 파일이 로딩됐다면 적용 경로와 지침 사이의 충돌을 살펴봅니다. 반드시 차단해야 하는 작업은 도구 권한으로 제한합니다.

이 글은 2026년 10월 13일 확인한 [Claude Code 메모리 문서](https://code.claude.com/docs/en/memory)와 [설정 진단 문서](https://code.claude.com/docs/en/debug-your-config)를 바탕으로 한 점검 안내입니다.

## 지침 로딩과 실제 준수

`CLAUDE.md`는 프로젝트의 작업 방식과 주의사항을 세션에 전달합니다. 로딩 여부는 파일 목록에서, 작업 준수 여부는 변경 내역과 테스트 결과에서 확인합니다.

| 상태 | 확인할 증거 | 그것만으로 알 수 없는 것 |
| --- | --- | --- |
| 지침 로딩 | 시작 시 로딩 목록이나 하위 파일의 `Loaded` 표시 | 이후 모든 작업에서 지침을 지키는지 |
| 작업에서의 준수 | 실제 diff, 실행한 명령과 결과 | 다른 작업에서도 항상 지키는지 |
| 실행 제한 | 권한·훅·외부 시스템의 통제와 차단 결과 | 규칙 문장만으로 통제가 생겼는지 |

## 시작 위치와 로딩 확인

먼저 **문제가 발생한 프로젝트에서 실행 중인 Claude Code 세션**을 확인합니다. 터미널에서 `claude --version`으로 버전을 기록하고, 아래 슬래시 명령은 운영체제 셸이 아니라 Claude Code 대화 입력창에 넣습니다.

1. `/context`를 실행하고 **Memory files**에서 시작 시 로딩돼야 할 `CLAUDE.md`의 경로를 확인합니다.
2. `/memory`로 파일 위치를 찾아 열고, 저장된 내용이 의도한 지침인지 확인합니다.
3. 파일을 고쳤다면 기존 변경사항을 보존한 상태에서 같은 프로젝트의 새 세션을 열어 시작 시 로딩을 다시 확인합니다.

**`/memory`에 경로가 있다는 사실만으로 로딩을 판정하지는 마세요.** 현재 공식 문서에 따르면 `/memory`는 아직 존재하지 않는 사용자·프로젝트 지침 파일의 위치도 보여줍니다. 시작할 때 실제로 들어온 파일은 `/context`에서 구분하는 편이 정확합니다.

프로젝트 지침의 기본 위치는 `./CLAUDE.md` 또는 `./.claude/CLAUDE.md`입니다. `~/.claude/CLAUDE.md`는 여러 프로젝트에 적용되는 사용자 지침이고, `./CLAUDE.local.md`는 해당 프로젝트의 개인 지침입니다. 여기서 `~`는 홈 디렉터리, `./`는 해당 위치의 디렉터리를 뜻합니다.

실행 위치도 중요합니다. 공식 문서는 Claude Code가 **현재 작업 디렉터리와 그 상위 디렉터리의 지침을 시작 시 읽는다**고 설명합니다. 프로젝트가 아닌 상위 폴더에서 시작하면, 프로젝트 안의 지침은 시작 시 지침이 아니라 하위 폴더 지침으로 취급될 수 있습니다. 같은 이름의 다른 checkout이나 worktree에서 실행한 것은 아닌지도 봅니다.

시작 시 파일이 빠져 있다면 다음을 확인합니다.

- 파일명이 정확히 `CLAUDE.md`인지, 실제로는 `CLAUDE.md.txt`로 저장되지 않았는지
- 편집기에서 열어둔 프로젝트와 Claude Code의 작업 폴더가 같은지
- `claudeMdExcludes`에 해당 파일을 제외하는 패턴이 있는지
- 실행 명령이나 도구의 실행 설정이 지침 로딩을 끄고 있지 않은지
- `/config`에 **Project instructions** 항목이 있는 환경이라면 `managed-only`로 설정돼 있지 않은지. 이 값은 시작 시 사용자·프로젝트 지침을 제외하므로, 의도한 설정인지 먼저 확인합니다.

예를 들어 [CLI 문서](https://code.claude.com/docs/en/cli-reference)의 `--bare`는 `CLAUDE.md` 자동 탐색을 생략하고, `--safe-mode`는 사용자 정의 지침 등을 끈 상태로 시작합니다. 이런 모드로 시작한 뒤 파일이 안 보이는 것을 곧바로 모델의 지시 불이행으로 판단하면 안 됩니다. 조직에서 관리하는 설정은 임의로 끄지 말고 `/status`로 적용 출처를 확인하세요.

## 하위 폴더와 경로별 규칙

프로젝트 루트의 파일은 보이는데 `src/api/CLAUDE.md`는 안 보인다면, 바로 위치를 옮기기 전에 **지연 로딩**을 확인합니다. 하위 디렉터리의 지침은 세션 시작 시 전부 넣는 대신, 해당 폴더의 파일을 다룰 때 로딩됩니다.

공식 문서가 안내하는 확인 방법은 간단합니다. 편집기나 셸로 하위 `CLAUDE.md`를 만든 뒤, Claude에게 **같은 폴더의 다른 파일을 읽도록 요청**합니다. 지침이 로딩될 때 터미널에 경로와 함께 `Loaded` 줄이 나타나는지 봅니다. 시작 시 `/context` 목록에 없었다는 이유만으로 실패라고 판단하지 않는 것이 포인트입니다.

### 특정 파일에만 적용할 규칙

API 코드에만 필요한 지침을 루트 파일에 계속 추가하기보다 `.claude/rules/`의 경로별 규칙으로 분리할 수 있습니다. 아래는 `.claude/rules/api-review.md`에 둘 수 있는 **설명용 예시**입니다.

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API 변경 검토

- API 오류 형식을 바꾸기 전에 기존 오류 처리 코드를 읽는다.
- 응답 필드를 변경하면 영향을 받는 호출부와 테스트 경로를 함께 보고한다.
- 실행하지 못한 테스트는 통과로 쓰지 않고 이유를 적는다.
```

`paths`는 프로젝트 파일 경로에 맞춰 바꿔야 합니다. 실제 코드가 `apps/server/src/` 아래에 있다면 위 패턴은 원하는 파일을 가리키지 않습니다. 파일 확장자가 `.tsx`인데 `.ts`만 지정한 경우도 구분해야 합니다.

[경로별 규칙 문서](https://code.claude.com/docs/en/memory#path-specific-rules)에 따르면 `paths`가 없는 규칙은 조건 없이 로딩됩니다. 또 YAML 문법이 잘못되면 frontmatter를 무시하고 경로 조건이 없는 규칙처럼 로딩할 수 있습니다. “문법이 틀렸으니 안전하게 비활성화됐겠지”라고 생각하면 반대로 적용 범위가 넓어질 수 있습니다.

### 파일을 읽히는 확인 요청

연습용 파일을 대상으로 아래처럼 물어봅니다.

```text
src/api/example.ts를 읽고, 이 파일을 변경할 때 적용할
프로젝트 규칙을 세 항목으로 정리해줘.
파일을 수정하거나 명령을 실행하지는 말아줘.
근거로 확인한 규칙 파일의 경로와 해당 문장도 함께 적어줘.
```

`src/api/example.ts`를 실제 파일 경로로 바꾼 뒤 **로딩 표시와 답변에 인용된 근거를 규칙 원문과 대조합니다.**

원본을 보호해야 한다면 복사본을 사용하거나 도구를 읽기 전용으로 제한하세요. 로딩 확인에는 민감정보가 없는 파일을 사용합니다.

## 읽었는데도 어기는 지침

파일이 로딩됐고 적용 경로도 맞는다면 문장을 더 많이 추가하기보다 **서로 다른 뜻으로 해석할 여지와 충돌**을 줄입니다.

공식 문서에 따르면 Claude Code는 발견한 지침을 문맥에 이어 붙입니다. 사용자 지침의 “항상 npm 사용”과 프로젝트 지침의 “이 저장소는 pnpm 사용”이 함께 들어오면 두 지침의 적용 범위를 조정하세요.

먼저 사용자 지침, 프로젝트 지침, `CLAUDE.local.md`, 관련 `.claude/rules/`를 함께 확인합니다. 오래된 규칙은 지우거나 적용 범위를 좁히고, 조직의 규칙과 충돌한다면 담당자와 기준을 맞춥니다.

### 확인 가능한 문장으로 수정

예를 들어 “테스트를 잘 하고 완료해”는 무엇을 실행하고 어디에 결과를 남길지 불명확합니다. npm 프로젝트에 실제로 `test`와 `lint` 스크립트가 있다는 전제라면 다음처럼 바꿀 수 있습니다.

```markdown
# 작업 완료 기준

- 변경한 코드와 관련된 테스트를 먼저 확인한다.
- 작업을 마치기 전에 npm test와 npm run lint를 실행한다.
- 완료 보고에 실행한 명령과 성공·실패 결과를 적는다.
- 실행하지 못했다면 이유를 적고, 검증 완료라고 표현하지 않는다.
```

`package.json`에 실제로 정의된 스크립트를 쓰고, 실패하면 로그에서 원인을 확인하세요.

공식 문서는 `CLAUDE.md`를 **200줄 미만**으로 관리하라고 권장합니다. 파일 크기는 4 MiB까지 전체를 읽고, 그보다 크면 건너뜁니다. 자동 메모리의 `MEMORY.md`는 시작 시 **200줄 또는 25KB 중 먼저 도달하는 한도**까지 읽습니다.

길어진 지침은 내용의 목적에 따라 나눕니다. `@path` import로 파일만 쪼개면 시작 시 가져오는 내용 자체는 줄지 않습니다. 특정 코드에만 필요한 내용은 `paths` 규칙으로, 특정 작업의 긴 절차는 스킬로 분리하는 편이 맞습니다.

버전이 `2.1.283` 이상이고 내장 `/claude-api` 스킬을 사용할 수 있다면 `/doctor prompt-audit`도 선택지입니다. 공식 안내상 오래되거나 충돌하는 지침과 수정 제안을 보고하며, 적용을 요청하기 전에는 파일을 바꾸지 않습니다. 다만 모델을 통한 검토 기능이므로 사용량과 자료 전달이 허용되는 환경에서만 실행하고, 제안은 diff로 확인하세요.

## 강제가 필요한 작업의 경계

“항상 테스트하라”는 작업 관례와 “운영 데이터는 절대로 삭제할 수 없어야 한다”는 요구는 같은 수준의 문제가 아닙니다.

[권한 문서](https://code.claude.com/docs/en/permissions)와 [훅 안내](https://code.claude.com/docs/en/hooks-guide)는 모델의 판단과 별개로 도구 실행을 제한하거나 특정 시점에 처리를 실행하는 방법을 설명합니다. 무엇을 보장해야 하는지에 따라 수단을 나눠야 합니다.

- **코딩 방식과 보고 형식:** `CLAUDE.md`에 구체적인 작업 지침을 남깁니다.
- **특정 도구·작업의 승인 또는 차단:** 권한 설정을 검토하고 `/permissions`에서 적용된 규칙을 확인합니다.
- **도구 실행 전 검사나 실행 후 처리:** 적절한 이벤트의 훅을 구성하고 `/hooks`에서 로딩 여부를 확인합니다.
- **운영 자원의 접근 제한:** 읽기 전용 계정, 최소 권한, 보호 브랜치 등 실제 시스템에서도 제한합니다.

명령 문자열을 기준으로 차단하는 훅을 쓴다면 다른 명령이나 도구로 같은 동작을 했을 때도 차단되는지 확인하세요.

**보호할 대상과 허용할 작업을 먼저 정한 뒤** 실제 실행 경로에 맞춰 제한을 설정하세요.

## 수정 뒤 완료 확인

점검은 규칙 파일을 저장했다고 끝나지 않습니다. 처음 문제가 발생한 작업을 작은 범위로 다시 확인해야 합니다.

1. **시작 시 로딩:** 같은 프로젝트의 새 세션에서 `/context`로 루트 지침의 경로를 확인합니다.
2. **조건부 로딩:** 하위 폴더나 경로별 규칙이라면 대상 파일을 읽게 하고, 관련 로딩 표시와 지침 원문을 대조합니다.
3. **작업 결과:** 승인한 작은 변경에서 diff와 실제 테스트 결과를 확인합니다.
4. **실행 제한:** 권한이나 훅을 바꿨다면 연습용 저장소나 테스트 자원에서 허용·차단 결과를 확인합니다.

`/compact` 뒤에 다시 놓치는 경우도 구분합니다. 공식 문서상 프로젝트 루트의 `CLAUDE.md`는 다시 읽혀 문맥에 들어가고, 하위 지침과 경로별 규칙은 필요할 때 다시 로딩됩니다. 대화에만 적었던 요구인지, 아직 해당 하위 파일을 다루지 않았는지부터 확인하는 편이 좋습니다.

그래도 같은 문제가 남으면 버전, 실행 위치, 지침 파일의 상대 경로, 최소한의 규칙, 문제가 난 작업과 관찰 결과를 모읍니다. 비밀값과 개인 경로를 제거한 작은 재현 자료가 있어야 지원 문의에서도 로딩 문제인지 준수 문제인지 나눠볼 수 있습니다.
