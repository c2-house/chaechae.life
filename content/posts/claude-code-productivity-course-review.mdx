### 목차

## `CLAUDE.md`에 무엇을 남길 것인가

강의 초반에 먼저 눈에 들어온 건 `CLAUDE.md`였습니다. 새 작업을 시작할 때마다 Claude Code에 프로젝트 구조와 검사 명령을 반복해서 알려주고 있다면, `CLAUDE.md` 파일에 공통으로 적용할 내용을 적어둘 수 있습니다.

4차시에서는 `CLAUDE.md`에 프로젝트의 목적과 주요 규칙을 정리하는 방법을 설명합니다. 7차시의 게시글 편집기 예제가 이 이야기를 더 쉽게 풀어줍니다. 편집기의 화면 흐름과 컴포넌트 구조를 별도 문서로 옮기고, `CLAUDE.md`에는 편집기 작업을 할 때 그 문서를 찾아보라는 안내를 남기는 방식입니다.

<Image alt="CLAUDE.md에서 게시글 편집기의 상세 문서를 가리키는 강의 예제" caption="CLAUDE.md에서 게시글 편집기의 상세 문서를 가리키는 강의 예제" src="/claude-code-productivity-course-review/03-claude-md-editor-example.png" />

개인적으로는 이 예제가 가장 바로 적용해볼 만하다고 생각했습니다. 프로젝트 지침을 보면 좋은 내용을 발견할 때마다 한 줄씩 추가하고 싶어질 때가 있는데 **공통 규칙과 특정 기능에만 필요한 설명을 구분하면 무엇을 빼도 되는지 판단하기 쉬워집니다.**

## 훅과 스킬로 정리하는 반복 작업

10차시에서는 Claude Code가 파일을 작성하거나 수정한 뒤 프로젝트의 린트 검사를 실행하는 훅을 설정합니다. 파일 변경이라는 계기가 생기면 미리 지정한 검사가 실행됩니다. 매번 `수정했으면 검사도 해줘`라는 문장을 붙이던 상황을 떠올리면, 왜 이 기능을 쓰는지 이해하기 쉽습니다.

<Image alt="PostToolUse에서 Write와 Edit 작업 이후 pnpm lint를 실행하는 훅 설정" caption="PostToolUse에서 Write와 Edit 작업 이후 pnpm lint를 실행하는 훅 설정" src="/claude-code-productivity-course-review/04-lint-hook.png" />

11차시의 스킬 예제는 브랜치 상태 확인, 테스트와 빌드, 커밋과 PR 생성까지의 순서를 `SKILL.md`에 정리합니다. 같은 일을 맡길 때 필요한 절차와 판단 기준을 적어두고 다시 사용하는 형태입니다.

두 예제를 이어서 보면 역할이 선명해집니다. **훅은 검사할 시점을 정하고, 스킬은 반복하는 일의 순서를 정합니다.** 개인 프로젝트에 적용한다면 파일을 고친 뒤 린트를 돌리는 것부터 시작하고, 매번 비슷하게 진행하는 PR 준비 과정을 스킬로 정리해보면 좋겠다고 생각했습니다.

## 여러 에이전트와 팀으로 확장하는 방법

아직 영상을 다 보지 못한 중후반부는 스크립트로 확인했습니다. 13차시에는 GitHub 이슈를 읽은 뒤 Playwright로 로컬 앱의 이미지 업로드 문제를 재현하고, 수정 후 다시 확인하는 예제가 나옵니다. MCP로 각각의 도구를 연결했을 때 개발 과정에서 어떤 역할을 맡길 수 있는지 보여주는 사례입니다.

18차시에서는 블로그 검색 기능 구현을 백엔드, 프론트엔드, QA 역할로 나눕니다. 19차시는 Git worktree로 여러 세션의 작업 폴더를 분리하는 방법을, 20차시는 스킬과 훅을 플러그인으로 묶어 팀원과 공유하는 방법을 설명합니다. 사람의 역할을 나누는 것처럼, 에이전트에도 **맡길 일과 수정할 공간을 함께 정해준다**는 관점이 흥미로웠습니다.

<Image alt="두 Claude 세션이 한 폴더에서 작업하는 경우와 Git worktree로 폴더를 분리한 경우를 비교한 도식" caption="두 Claude 세션이 한 폴더에서 작업하는 경우와 Git worktree로 폴더를 분리한 경우를 비교한 도식" src="/claude-code-productivity-course-review/05-worktree-separation.png" />

21차시의 하네스 엔지니어링도 앞부분과 연결해서 볼 만합니다. 프로젝트 지침으로 작업 방향을 알려주고, 린트나 테스트로 결과가 기준을 충족하는지 확인하는 방식입니다. 이후에는 Cowork, Design, 용도별 플러그인까지 이어져 개발 외 업무에 적용하는 예제도 살펴볼 수 있습니다.

## 살짝 아쉬웠던 자막 표기

강의를 보면서 아쉬웠던 건 일부 자막의 용어 표기였습니다. 제품명 `Claude Code`를 설명하는 대목에서 자막에 `클라우드 코드`라고 표시된 부분이 있었습니다.

<Image alt="Claude Code가 클라우드 코드로 표시된 강의 자막" caption="Claude Code를 클라우드 코드로 표기한 자막" src="/claude-code-productivity-course-review/01-subtitle-claude-code.png" fullWidth={false} />

프로젝트 지침 파일을 설명할 때는 `CLAUDE.md`가 `clod.md`로 표시되기도 했습니다. 코딩 도구를 이미 쓰는 분이라면 문맥으로 알아볼 수 있겠지만, 처음 배우는 분은 자막을 보고 그대로 파일 이름을 만들거나 검색할 수 있습니다. 제품명이나 파일명처럼 직접 입력하는 용어는 정확하게 표시되면 좋겠습니다.

5차시의 계획 모드가 좋은 출발점입니다. 예제에서는 블로그에 좋아요 기능을 추가하기 전에 구현 계획부터 검토합니다. 파일 정리처럼 평소에 하던 일도 실제로 실행하기 전에 어떤 기준으로 처리할지 먼저 확인해볼 수 있겠다는 생각이 들었습니다.
