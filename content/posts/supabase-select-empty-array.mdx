Supabase Dashboard에서는 데이터가 보이는데 앱에서는 목록이 비어 있습니다. AI에게 수정해달라고 했더니 RLS를 끄거나 관리자 키로 바꿔보라는 제안을 받았다면, 그 변경부터 적용하지 않는 편이 좋습니다. **빈 배열은 데이터가 없다는 뜻일 수도 있지만, 지금 요청한 사용자에게 보이는 행이 없다는 뜻일 수도 있기 때문입니다.**

[Supabase 공식 지원 문서](https://supabase.com/docs/guides/troubleshooting/why-is-my-select-returning-an-empty-data-array-and-i-have-data-in-the-table-xvOPgx)도 RLS 정책 누락·조건 불일치와 조회 필터를 주요 원인으로 설명합니다. 다만 처음부터 권한을 풀면 정상 조회와 데이터 노출을 구분하기 어렵습니다. **오류 여부 → 연결 대상과 필터 → 요청 사용자의 로그인 → 테이블 권한과 RLS** 순서로 범위를 좁혀보겠습니다.

이 글은 2026년 10월 5일 확인한 공식 문서를 바탕으로, `supabase-js`의 일반 테이블 `select`를 점검하는 안내입니다. 아래 코드는 기존 앱에 맞춰 사용하는 진단 예시이며, 특정 Supabase 프로젝트에서 장애를 재현하거나 해결한 결과는 아닙니다. 뷰·RPC·복잡한 조인 쿼리는 별도 권한과 실행 방식도 확인해야 합니다.

## 빈 배열과 요청 실패의 구분

먼저 화면의 ‘목록 없음’이 아니라 **원래 조회의 `data`와 `error`를 함께 확인**합니다. 앱에서 `data ?? []`처럼 값을 처리하면, 요청에 실패해 `data`가 없는 상황도 빈 목록으로 보일 수 있습니다.

일반적인 배열 조회에서 `error`가 없고 `data`가 `[]`라면, 그 요청의 조건과 권한으로 반환할 행이 없다는 뜻입니다. 반대로 `error`가 있다면 먼저 오류 코드에 따라 조사해야 합니다. 둘을 모두 ‘RLS 때문에 안 됨’으로 묶지 않습니다.

| 관찰한 결과 | 먼저 확인할 항목 |
| --- | --- |
| `error` 없음, `data`가 빈 배열 | 연결 대상·필터·요청 사용자·조회 정책 |
| `42501` 권한 오류 | 스키마·테이블·열 등 필요한 권한과 오류 메시지 |
| 인증 관련 오류 | 프로젝트 URL과 키 조합, 사용자 세션과 만료 상태 |
| 행이 반환되는데 화면만 비어 있음 | 화면 필터·상태 갱신·렌더링 코드 |

`42501`도 무조건 같은 원인은 아닙니다. [RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)는 테이블 작업 권한이 없으면 정책을 평가하기 전에 이 오류가 발생할 수 있다고 설명합니다. 오류 메시지에 표시된 대상부터 확인하세요. 쓰기 요청의 정책 위반까지 같은 빈 배열 문제로 처리하지는 않습니다.

또한 `.single()`처럼 한 행을 요구하는 조회는 결과 형식과 오류 조건이 다릅니다. 이 글에서 말하는 빈 배열은 우선 `.select()`의 배열 응답을 기준으로 합니다.

## 프로젝트와 조회 조건 확인

권한 설정을 바꾸기 전에, **Dashboard에서 보고 있는 테이블과 앱이 요청하는 테이블이 같은지**부터 확인합니다. 개발용 프로젝트에는 데이터를 넣고, 배포한 앱은 다른 프로젝트를 조회하고 있을 수도 있습니다.

1. 문제가 발생한 앱에서 개발자 도구의 **Network**를 열고 해당 목록 조회를 실행합니다.
2. Supabase Data API로 직접 요청한다면 목적지 호스트와 `/rest/v1/` 뒤의 테이블 이름을 확인합니다. 앱 서버를 경유한다면 서버의 Supabase 클라이언트 설정을 대조합니다.
3. 같은 프로젝트의 Dashboard에서 스키마·테이블·확인할 테스트 행을 찾습니다.
4. 원래 쿼리의 `.eq()`, `.in()`, 날짜 범위, 페이지 범위 등 조건을 하나씩 대조합니다.

예를 들어 DB에는 `status = 'draft'`인 행만 있는데 앱이 `published`만 조회한다면 빈 배열이 정상입니다. 페이지 범위가 데이터 끝을 넘어간 경우도 살펴보세요. 로그인 사용자 ID로 필터링한다면 값이 준비되기 전에 조회를 시작하는 코드가 없는지도 확인합니다.

필터 영향을 확인할 때는 **승인된 테스트 환경에서, 같은 낮은 권한의 클라이언트를 유지한 채** 필요한 열과 소수의 행만 조회합니다. RLS가 유지되어 있어도 필터를 없애면 그 사용자가 볼 수 있는 다른 데이터까지 조회할 수 있으므로, 운영 테이블 전체를 출력하는 방식은 피하는 편이 좋습니다.

Network의 요청 헤더·HAR 파일에는 토큰과 쿠키가 들어갈 수 있습니다. 공개 이슈나 AI 대화에는 원문을 올리지 말고 호스트·테이블 이름·오류 코드 등 필요한 정보만 민감정보를 제거해 전달하세요. 배포 환경만 다르다면 [Vercel 환경변수 점검 글](/blog/vercel-env-not-updating)처럼 실제 배포에 적용된 설정도 확인할 차례입니다.

## 조회에 사용하는 클라이언트의 로그인 상태

화면에 프로필이 보인다는 사실만으로 **DB를 조회하는 클라이언트에도 같은 세션이 전달됐다고 확정할 수는 없습니다.** 브라우저에서는 로그인했지만 서버 쪽 클라이언트에는 쿠키가 전달되지 않은 경우처럼, 실행 위치가 다를 수 있습니다.

아래 함수는 [공식 `getUser()`](https://supabase.com/docs/reference/javascript/auth-getuser)와 [`select()`](https://supabase.com/docs/reference/javascript/select) 문법을 조합한 점검 예시입니다. 기존 데이터 조회가 실행되는 위치에서 **그 조회에 쓰는 `supabase` 객체**를 넘깁니다. `notes`와 `id`는 예시 테이블·열 이름이므로 자신의 테스트 데이터에 맞게 바꾸세요.

```javascript
async function inspectNotesRead(supabase) {
  const { data: authData, error: authError } =
    await supabase.auth.getUser();

  const { data, error, status } = await supabase
    .from('notes')
    .select('id')
    .limit(1);

  console.log({
    userVerified: Boolean(authData?.user),
    authErrorCode: authError?.code ?? null,
    readStatus: status,
    readErrorCode: error?.code ?? null,
    rowCount: Array.isArray(data) ? data.length : null,
  });
}

// 기존 앱에서 만든, 실제 조회용 클라이언트를 전달합니다.
await inspectNotesRead(supabase);
```

토큰·사용자 객체·행 내용을 통째로 출력하지 않고, 사용자 확인 여부와 오류 코드·반환 개수만 남깁니다. 이 함수는 원래 쿼리의 필터를 제외한 최소 조회이므로 **원래 쿼리 결과와 비교하는 용도**입니다. 실행 후에는 임시 진단 코드와 로그를 정리합니다.

`getUser()`는 현재 세션을 바탕으로 Auth 서버에 네트워크 요청을 보내 사용자를 확인합니다. `userVerified`가 참이면 그 호출에서 사용자를 확인한 것이지만, 모든 DB 요청의 권한이 통과했다는 뜻은 아닙니다. 다음 조회 전에 세션이 바뀌거나, 별도의 `Authorization` 설정이 DB 요청을 덮어쓰는 코드도 점검해야 합니다.

- **로그인 전용 목록인데 사용자 확인 실패:** 로그인 완료 시점, 세션 갱신, 같은 클라이언트 사용 여부를 먼저 봅니다. 인증 오류와 단순 비로그인 상태도 나눠 확인합니다.
- **사용자는 확인되지만 최소 조회도 빈 배열:** 해당 사용자의 테스트 행이 실제로 있는지 확인한 뒤 RLS의 대상 역할과 조건을 봅니다.
- **최소 조회는 되지만 원래 쿼리만 빈 배열:** 원래 쿼리의 필터·범위·조인 조건으로 돌아갑니다. 최소 조회가 다른 행을 반환했을 가능성도 있으므로 목표 행을 기준으로 비교합니다.
- **공개 목록을 비로그인으로 조회:** 사용자 확인 실패 자체가 장애는 아닙니다. 공개 데이터에 필요한 `anon` 권한과 조회 정책이 있는지를 확인합니다.

Next.js 등 SSR 앱에서는 브라우저와 서버의 클라이언트를 구분해야 합니다. [공식 SSR 가이드](https://supabase.com/docs/guides/auth/server-side/creating-a-client)는 쿠키 기반 세션 저장과 전달을 안내합니다. 서버에서 빈 결과가 나온다고 브라우저 코드로 옮기거나 관리자 키를 넣기보다, 요청의 쿠키를 처리하는 기존 SSR 클라이언트 경로를 먼저 확인하는 편이 맞습니다.

## 테이블 권한과 RLS 정책

여기서 두 가지를 나눠 보면 이해하기 쉽습니다. **테이블 권한은 그 역할이 조회 작업을 할 수 있는지**, **RLS 정책은 그 조회에서 어떤 행을 볼 수 있는지**를 결정합니다.

따라서 테이블에 `SELECT` 권한이 있어도, RLS가 켜져 있고 적용되는 조회 정책이 없으면 행이 보이지 않을 수 있습니다. 반대로 정책이 있어도 테이블을 조회할 권한 자체가 없다면 권한 오류가 납니다. 두 설정 중 하나만 확인해서는 부족합니다.

Dashboard에서 대상 테이블의 RLS 활성화 여부와 정책 목록을 확인합니다. SQL에 익숙하다면 **해당 프로젝트의 SQL Editor**에서 다음처럼 정책 목록을 읽을 수도 있습니다. `public`과 `notes`를 자신의 스키마·테이블 이름으로 바꾸면 됩니다. 이 쿼리는 정책을 추가하거나 변경하지 않습니다.

```sql
select
  policyname,
  permissive,
  roles,
  cmd,
  qual,
  with_check
from pg_policies
where schemaname = 'public'
  and tablename = 'notes';
```

이 쿼리는 [PostgreSQL의 `pg_policies` 뷰](https://www.postgresql.org/docs/current/view-pg-policies.html)에 있는 필드를 조회합니다. 확인할 지점은 다음과 같습니다.

- **`cmd`:** `SELECT` 또는 조회를 포함하는 `ALL` 정책인지 봅니다. `INSERT` 정책만 만들어두면 조회 정책을 대신하지 않습니다.
- **`roles`:** 요청 역할에 적용되는지 봅니다. 로그인 사용자는 일반적으로 `authenticated`, 비로그인 요청은 `anon`입니다. `public`은 PostgreSQL의 모든 역할에 적용된다는 의미이므로 이름이 `authenticated`가 아니라는 이유만으로 오류로 판단하지 않습니다.
- **`qual`:** 기존 행을 보이게 하는 `USING` 조건입니다. 소유자 ID·팀 멤버십·공개 상태 등 어떤 조건이 참이어야 하는지 읽습니다.
- **`with_check`:** 추가·수정되는 행의 조건입니다. 이것만 확인하고 조회가 허용됐다고 생각하지 않습니다.

정책 목록이 없다는 것만으로 RLS가 켜져 있는지는 알 수 없습니다. **테이블의 RLS 활성화 상태도 별도로 확인**해야 합니다. 테이블 작업 권한은 Dashboard의 권한 설정이나 프로젝트에서 관리하는 마이그레이션과 함께 대조합니다.

그리고 SQL Editor에서 직접 `select`가 성공했다는 사실을 앱의 권한 검증으로 사용하면 안 됩니다. [PostgreSQL 문서](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)에 따르면 슈퍼유저·`BYPASSRLS` 역할은 RLS를 우회하고, 테이블 소유자도 보통 정책 적용을 받지 않습니다. **관리자 조회 성공과 앱 사용자의 조회 성공은 다른 결과**입니다.

## 소유자 조건과 실제 데이터 대조

개인 메모처럼 작성자만 읽는 테이블은 보통 다음 의미의 조건을 사용합니다. 아래는 **정책 조건을 이해하기 위한 예시**이며, 기존 정책에 그대로 추가하라는 변경 명령은 아닙니다.

```sql
(select auth.uid()) = user_id
```

`auth.uid()`는 요청한 사용자의 ID를 반환합니다. 이 값이 해당 행의 `user_id`와 같아야 한다는 뜻입니다. 다음 항목을 비공개로 대조하면 원인을 더 좁힐 수 있습니다.

1. 확인하려는 테스트 행의 `user_id`에 실제 소유자 ID가 저장됐는지 확인합니다. `null`이거나 다른 테스트 계정의 ID일 수 있습니다.
2. 앱이 로그인한 계정과 그 행의 소유자가 같은지 확인합니다. 이메일 문자열이나 화면의 닉네임을 사용자 UUID 대신 저장하지 않았는지도 봅니다.
3. 데이터 조회가 로그인 완료 후 실행되고 있는지 확인합니다. 인증된 사용자 정보가 없는 요청에서는 `auth.uid()`가 `null`이며, 같은지 비교하는 조건이 참이 되지 않습니다.
4. 팀 공유 데이터라면 개인 소유자 조건만으로 충분한지 확인합니다. 소유자가 아닌 팀원도 읽어야 한다면 서비스의 멤버십 규칙에 맞는 정책이 필요합니다.

Supabase Auth의 **익명 로그인 사용자**와 **아예 로그인하지 않은 `anon` 요청**도 다릅니다. 공식 RLS 문서에 따르면 익명 로그인 사용자도 `authenticated` 역할을 사용합니다. ‘익명’이라는 말만 보고 정책 대상을 `anon`으로 바꾸면 의도와 어긋날 수 있습니다.

정책을 수정해야 한다면 먼저 기대 접근 범위를 적고, 테스트 환경에서 해당 조건만 고칩니다. 여러 정책이 있을 때는 하나만 떼어 보지 않습니다. PostgreSQL의 기본 permissive 정책들은 `OR`로 조합되므로, 이미 넓게 허용하는 정책이 남아 있으면 좁은 정책을 추가해도 접근 범위가 줄어들지 않을 수 있습니다. restrictive 정책은 추가 제한으로 `AND` 결합되며, 이것만 만들었다고 조회를 허용하는 정책이 생기는 것은 아닙니다.

오류가 사라지게 하려고 모든 행의 `user_id`를 현재 계정으로 바꾸는 것도 해결책은 아닙니다. 잘못 저장된 데이터의 소유권은 별도로 확인하고, 입력·저장 코드의 원인을 수정해야 합니다. 변경 전 정책 정의와 필요한 복구 절차를 남기고, 운영 반영은 정상 조회와 권한 차단을 함께 검증한 뒤 진행합니다.

## 피해야 할 우회와 수정 후 확인

빈 목록을 채우는 가장 빠른 변경이 안전한 해결은 아닙니다. 특히 다음 방식은 피해야 합니다.

- **RLS 비활성화:** 테이블 권한이 있는 다른 요청에도 데이터가 열릴 수 있습니다.
- **비공개 테이블에 `anon` 대상 `USING (true)` 추가:** 로그인하지 않은 방문자까지 조회할 수 있게 만드는 변경입니다.
- **secret·`service_role` 키로 앱 클라이언트 교체:** 관리자 권한으로 조회되는 것을 사용자 권한이 고쳐진 결과로 착각할 수 있습니다. 브라우저에 넣으면 비밀키 노출도 발생합니다.

공개 키와 관리자 키의 차이가 헷갈린다면 [Supabase API 키 전환 글](/blog/supabase-publishable-key-migration)의 역할 구분을 함께 참고하세요. 키의 종류를 바꾸는 것과 사용자별 접근 정책을 고치는 것은 별도 작업입니다.

수정 후에는 개인정보가 없는 **테스트 계정 A·B와 각각의 테스트 행**으로 원래 앱의 조회를 다시 확인합니다. 아래는 ‘자기 메모만 읽는 서비스’의 완료 기준 예시입니다. 공개 목록이나 팀 공유 목록이라면 서비스 의도에 맞춰 기대 결과를 먼저 바꿔야 합니다.

| 확인 상황 | 기대 결과 |
| --- | --- |
| A로 로그인하고 A의 메모 조회 | 준비한 A의 행이 반환됨 |
| A로 로그인하고 B의 메모 조회 | B의 행이 반환되지 않음 |
| B로 로그인하고 B의 메모 조회 | 준비한 B의 행이 반환됨 |
| 로그아웃 후 비공개 메모 조회 | 비공개 행이 반환되지 않음 |
| 원래 필터와 새로고침을 적용한 앱 | 허용된 목록이 유지되고 오류가 숨겨지지 않음 |

차단 결과는 설정에 따라 빈 배열이나 권한 오류일 수 있습니다. **반드시 `403`이 나와야 한다는 기준보다, 허용한 데이터는 보이고 허용하지 않은 데이터는 전달되지 않는지가 중요합니다.** 조회만 확인했다고 추가·수정·삭제 정책까지 검증한 것으로 기록하지도 않습니다.

## 원인이 남았을 때의 조사 범위

같은 프로젝트·같은 클라이언트·같은 사용자·같은 테스트 행으로 대조했는데도 설명되지 않는다면, 더 이상 정책을 넓히지 말고 쿼리 범위를 확인합니다. 일반 테이블이 아닌 뷰인지, RPC 내부가 다른 역할로 실행되는지, `!inner` 조인으로 결과가 줄어드는지, 앱 서버가 이전 응답을 캐시하는지 등을 분리해 볼 차례입니다.

지원 요청에는 SDK 버전과 브라우저·서버 중 실행 위치, 테이블과 정책의 최소 구조, 민감정보를 제거한 조회 코드, 오류 코드와 A·B 계정의 기대·관찰 결과를 남기면 됩니다. JWT 원문, 관리자 키, 실제 사용자 데이터 전체는 필요하지 않습니다.

결국 이 문제에서 확인할 것은 **‘테이블에 데이터가 있나’와 ‘이 요청이 그 데이터를 볼 수 있나’의 차이**입니다. RLS를 끄고 목록이 보이는 데서 끝내지 않고, 원래 사용자의 정상 조회와 다른 사용자의 접근 차단을 함께 확인해야 수정이 끝났다고 판단할 수 있습니다.
