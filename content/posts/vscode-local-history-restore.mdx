### 목차

## 들어가며

VS Code에서 코드를 고치고 저장했는데, 조금 전 내용이 더 나았다는 사실을 뒤늦게 알아차릴 때가 있습니다. Git에 커밋하지 않았다면 이전 내용을 어디서 찾아야 할지 막막해지죠. 이때 먼저 확인할 곳이 **탐색기의 Timeline에 있는 로컬 기록**입니다.

Microsoft Visual Studio Code에는 저장한 파일의 내용을 따로 보관하는 기능이 내장되어 있습니다. 기록이 남아 있다면 이전 버전을 열어 현재 파일과 비교하고 복원할 수 있습니다. 별도 확장을 설치할 필요는 없지만, **모든 저장 순간과 삭제한 파일이 반드시 남아 있는 것은 아닙니다.**

이 글은 Windows의 VS Code를 기준으로 설명합니다. 2026년 10월 27일, Windows 11과 VS Code 1.139.1의 별도 시험 환경에서 가상 텍스트 파일을 두 번 저장하고 이전 내용과 비교해봤습니다. 복원 확인창까지 열었으나 확정 조작은 진행하지 않았습니다. 아래 복원·삭제 파일 찾기 절차는 공식 안내와 해당 버전의 구현을 바탕으로 정리했습니다.

## Timeline에서 저장 기록 찾기

먼저 추가 수정이나 덮어쓰기를 잠시 멈춥니다. 현재 파일에도 살려야 할 부분이 있다면 **지금 내용부터 다른 파일에 복사해 보관**하세요. 아직 저장하지 않은 편집 내용은 디스크의 파일 복사에 포함되지 않으므로, 편집기 안의 내용도 따로 보관해야 합니다.

그다음 이전 기록을 찾습니다.

1. VS Code에서 문제가 생긴 파일을 엽니다.
2. 왼쪽 **탐색기 / Explorer**를 엽니다. Windows에서는 `Ctrl+Shift+E`를 사용할 수 있습니다.
3. 탐색기 아래의 **타임라인 / Timeline**을 펼칩니다.
4. `File Saved` 같은 저장 항목에서 되돌리고 싶은 시점을 찾습니다. 항목의 날짜와 시간을 확인하고, 현재 선택한 파일이 맞는지도 봅니다.
5. 원하는 항목을 우클릭해 **Compare with File**을 선택합니다. 곧바로 복원하지 않고 현재 파일과 차이를 먼저 보는 단계입니다.

Timeline이 아예 보이지 않는다면 탐색기의 제목 영역을 우클릭해 Timeline 표시 여부를 확인하세요. Timeline은 열려 있는 파일을 따라 바뀌므로, 폴더만 선택한 상태보다 **복구 대상 파일을 편집기에서 연 상태**로 확인하는 것이 분명합니다.

이 화면의 파일은 Git 저장소 없이 열었습니다. Timeline에 나타난 두 항목은 Git 커밋이 아니라 **VS Code에서 저장한 로컬 기록**입니다. Git을 사용하는 프로젝트에서는 커밋과 로컬 저장 기록이 함께 보일 수 있으므로, Timeline의 필터에서 `Local History`가 표시 대상인지 확인하세요.

## 이전 내용 비교와 복원

### 비교 화면의 읽는 순서

시험 파일에는 처음에 `Button label: Start trial`과 `Status: reviewed`를 저장했습니다. 이후 `Button label: Buy now`와 `Status: needs review`로 바꿔 저장하고, 앞선 기록의 **Compare with File**을 열었습니다.

/>

화면에서 이전 기록에는 `Start trial`, 현재 파일에는 `Buy now`가 남아 있는 것을 확인할 수 있습니다. **비교 화면을 여는 것만으로 현재 파일이 복원되지는 않습니다.** 색상만 보고 판단하지 말고 탭 제목의 기록 시각, 파일 이름, 되살릴 문장까지 함께 확인하세요.

예를 들어 버튼 문구만 되돌리고 나머지 수정은 유지하고 싶다면 파일 전체 복원보다 **이전 기록의 필요한 부분만 복사**하는 편이 낫습니다. 화면의 차이가 크면 현재 작업본을 옆에 두고 빠지는 내용이 없는지 확인합니다.

### 파일 전체 복원

선택한 기록의 전체 내용으로 돌아가려면 다음 순서로 진행합니다.

1. 현재 작업본과 저장하지 않은 편집 내용을 별도로 보관했는지 확인합니다.
2. Timeline에서 앞서 비교한 항목을 우클릭해 **Restore Contents**를 선택합니다.
3. 확인창의 파일 이름을 확인합니다. 이 창에는 **저장하지 않은 변경사항이 버려진다**는 경고가 표시됩니다.
4. 해당 시점의 전체 내용으로 바꾸는 것이 맞을 때만 **Restore**를 누릅니다.
5. 원래 경로의 파일을 다시 열어 필요한 문장과 남겨야 할 내용이 맞는지 확인합니다. 프로젝트 코드라면 관련 실행이나 테스트도 확인합니다.

복원은 이전 내용을 별도 참고 자료로 띄우는 작업이 아니라 **대상 파일의 내용을 교체하는 작업**입니다. 이번 버전의 공식 구현도 이 동작을 구분하고 있습니다. 잘못된 시점을 골랐거나 현재 수정도 필요하다면 취소하고 비교 화면에서 필요한 부분만 옮기세요.

완료 기준은 복원 버튼을 눌렀다는 사실이 아닙니다. 위 예제라면 원래 파일에 `Start trial`과 `reviewed`가 돌아왔는지, 유지하려던 다른 내용이 사라지지 않았는지 확인해야 합니다. 쓰기 권한 등으로 복원 오류가 나면 복구가 끝난 것으로 보지 말고, 기록을 읽어 별도 파일에 보관하는 방법부터 검토하세요.

## 삭제한 파일의 기록 찾기

파일 자체가 없어졌다면 탐색기에서 선택할 수 없습니다. 그렇다고 같은 이름의 빈 파일을 먼저 만들 필요는 없습니다. VS Code에는 파일 전체의 로컬 기록을 찾는 별도 명령이 있습니다.

1. Windows에서 `Ctrl+Shift+P`로 명령 팔레트를 엽니다.
2. **Local History: Find Entry to Restore**를 검색해 실행합니다. 한글 UI에서는 `Local History` 또는 `로컬 기록`으로 관련 명령을 찾을 수 있습니다.
3. 목록에서 삭제한 파일을 찾습니다. 같은 이름이 여러 개라면 **원래 폴더 경로**까지 대조합니다.
4. 해당 파일의 기록 중 원하는 시점을 선택해 내용을 엽니다.
5. 내용이 맞다면 편집기 제목 영역의 **Restore Contents** 복원 아이콘을 이용합니다. 확인창을 읽고 복원한 뒤 원래 경로에 파일이 생겼는지 확인합니다.

이 명령은 이름과 달리 목록에서 항목을 고르는 순간 곧바로 덮어쓰는 기능이 아닙니다. 현재 파일이 있으면 비교 화면을 열고, 파일이 없으면 기록의 내용을 열어 확인하도록 되어 있습니다. 복원 여부는 내용을 본 뒤 결정하면 됩니다.

파일 이름이 목록에 없거나 필요한 시점이 없다면 로컬 기록만으로 복구할 수 있다고 단정할 수 없습니다. 이 경우에는 휴지통, Git에 남아 있는 버전, 별도 백업이나 클라우드 저장소의 버전 기록을 차례로 확인해야 합니다. VS Code의 기록과 Windows 휴지통은 서로 다른 복구 경로입니다.

## 누락된 기록의 확인 순서

### 표시 필터와 기록 설정

Timeline이 비어 있다고 곧바로 기록이 모두 삭제됐다고 판단하지는 마세요. 먼저 **대상 파일과 필터**를 확인한 뒤 설정을 살펴봅니다. Windows에서 `Ctrl+,`로 설정을 열고 `local history`를 검색하면 관련 항목을 찾을 수 있습니다.

VS Code 1.139.1의 기본값과 확인할 내용은 다음과 같습니다. 사용자 설정이나 작업 영역 설정에서 값을 바꿨다면 그 값이 적용될 수 있습니다.

- **Enabled** — `workbench.localHistory.enabled`. 기본값은 켜짐입니다. 기록이 생성될 당시 꺼져 있었다면 지금 켠다고 과거 내용이 생기지는 않습니다.
- **Max File Size** — `workbench.localHistory.maxFileSize`. 기본값은 **256 KB**입니다. 이보다 큰 파일은 기록 대상에서 제외됩니다.
- **Max File Entries** — `workbench.localHistory.maxFileEntries`. 기본값은 **파일당 50개**입니다. 한도를 넘으면 오래된 항목부터 버려집니다.
- **Exclude** — `workbench.localHistory.exclude`. 파일 경로나 패턴으로 기록 대상에서 제외했는지 확인합니다.
- **Merge Window** — `workbench.localHistory.mergeWindow`. 기본값은 **10초**입니다. 같은 출처의 저장이 이 간격 안에 이어지면 마지막 항목을 새 내용으로 교체할 수 있습니다.

특히 마지막 설정 때문에 **저장을 여러 번 했다고 같은 수의 기록이 남는 것은 아닙니다.** 자동 저장을 켜둔 경우에도 모든 키 입력을 독립된 버전으로 보관한다고 생각하면 안 됩니다. 설정값을 늘리는 것은 이후 기록을 위한 선택이지, 이미 사라진 기록을 되살리는 방법은 아닙니다.

기록이 없는 원인을 찾겠다며 `Local History: Delete All` 같은 삭제 명령을 실행하거나 사용자 데이터 폴더를 정리하지 마세요. 필요한 복구 자료까지 없앨 수 있습니다.

### 다른 환경과 외부 도구의 변경

로컬 파일의 기록은 로컬 사용자 데이터에 보관되고, 원격 파일은 원격 환경의 사용자 데이터에 보관될 수 있습니다. WSL이나 SSH 원격 작업이었다면 **그때 작업한 환경에서 해당 파일을 열었는지** 먼저 확인하세요. 다른 PC나 별도 VS Code 인스턴스에서 같은 이름의 파일을 열었다고 이전 기록이 함께 따라온다고 가정하면 안 됩니다.

또한 로컬 기록은 컴퓨터 전체의 파일 변경을 감시하는 백업 프로그램이 아닙니다. 외부 터미널의 AI 코딩 도구나 다른 편집기가 파일을 바꿨다고 해서, 그 도구의 모든 중간 수정이 VS Code에 저장되어 있다고 볼 수는 없습니다. 실제 Timeline에 남은 내용과 시점을 확인해야 합니다.

한 번도 파일로 저장하지 않은 새 문서 역시 이 글의 로컬 저장 기록과는 구분해야 합니다. 열린 편집기와 실행 취소, 미저장 문서의 복구 가능성을 먼저 확인하고, 기록이 있을 것이라는 기대만으로 창을 닫거나 앱 데이터를 지우지 않는 편이 좋습니다.

## 다음 수정 전에 남길 기준점

로컬 기록은 실수했을 때 확인할 만한 안전망이지만, 프로젝트의 복구 전략 전체를 맡기기에는 범위가 작습니다. 파일별 기록이므로 여러 파일을 함께 바꾼 작업을 일관된 한 상태로 되돌리는 용도와도 다릅니다.

AI에게 큰 수정을 맡기기 전이라면 현재 변경사항을 검토하고, 비밀키나 개인정보가 포함되지 않았는지 확인한 뒤 **의미 있는 Git 커밋이나 별도 백업**을 남기는 편이 낫습니다. 일부 파일만 복원했다면 서로 맞물리는 설정과 코드가 다른 시점으로 섞이지 않았는지도 확인해야 합니다.

지금 필요한 것이 문장 하나인지, 파일 전체인지, 프로젝트 전체인지 먼저 나누세요. 문장 하나는 비교 화면에서 골라 옮기고, 파일 전체는 보관해둔 현재 작업본과 대조한 뒤 복원하는 식으로 범위를 좁히면 남아 있는 작업까지 잃을 위험을 줄일 수 있습니다.
